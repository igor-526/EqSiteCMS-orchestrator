# Proposal

## Why

Задачи `docs/tasks/106_statistics_deleting.md` и `docs/tasks/107_seo_pages_merge.md` изменяют одни и те же очереди Метрики: удаление интеграции должно очищать накопленную статистику, а добавление нормализации — объединять уже накопленные страницы. Общий change задаёт единый арбитраж, чтобы повторная привязка, парсинг и merge не возвращали удалённые данные и не теряли статистику.

## What Changes

- При удалении привязки счётчика или аккаунта со связанным счётчиком атомарно сохранять запрос очистки и outbox в yandex-service; ya-metrica-service отменяет ожидающие старые задания, дожидается текущих и удаляет статистики страниц и запросов ограниченными батчами.
- Сериализовать операции по конюшне: удаление выше merge, merge выше нового парсинга. PostgreSQL — источник истины; NATS и Celery доставляют повторяемые сигналы, не держат долгие операции неподтверждёнными.
- После добавления параметра или хеша нормализации SEO строит ограниченные пакеты соответствий старых UUID каноническим; отдельная очередь Метрики переносит суммы исходных метрик, затем надёжно отчитывается. SEO удаляет лишние страницы только после подтверждённой безопасности, сохраняя канонические UUID и aliases.
- **BREAKING (семантика данных):** добавление правила больше не оставляет исторические страницы навсегда раздельными. PATCH/DELETE правил не запускают ретроактивное разъединение; автоматического восстановления исходных вариантов нет.
- Оба подтверждения удаления в CMS показывают расширяемый список потерь и порядок восстановления; кнопка доступна через 5 секунд с обратным отсчётом в скобках.
- Затронутые HTTP-контракты и access matrix находятся в delta specs: существующие DELETE аккаунта/привязки и POST нормализации, внутренний GET привязки с lifecycle-полями; новые публичные endpoints не вводятся. Остальные строки matrix фиксируют регрессию rebind/resolve/parse.

## Capabilities

### New Capabilities

- `metrica-maintenance-protocol`: надёжная доставка очистки и merge, батчи, результаты, корреляция и безопасное завершение.

### Modified Capabilities

- `metrica-parse-queue`: отмена ожидающих заданий и tenant-арбитраж с обслуживанием.
- `metrica-parse-command-consumer`: устойчивое ожидание команды при maintenance вместо ACK с пропуском.
- `yandex-metrica-gateway`: атомарное удаление привязки с очисткой и lifecycle-watermark для повторной привязки.
- `yandex-oauth-accounts`: удаление связанного счётчика и постановка очистки до потери FK-контекста.
- `seo-normalization`: ретроактивная канонизация после добавления правила.
- `seo-entity-resolution`: внутреннее удаление source страниц после merge без нового пользовательского CRUD.
- `seo-page-normalization-settings`: транзакционное планирование фоновой нормализации и границы POST/PATCH/DELETE.
- `cms-seo-yandex-ui`: последствия удаления и пятисекундное подтверждение.

## Impact

Код и собственные Alembic-миграции: `services/yandex-service`, `services/ya-metrica-service`, `services/seo-service`; UI: `services/frontend`. Обновляются AsyncAPI трёх сервисов, их README/настройки, существующие worker/dispatcher и инфраструктурные тесты. Основной backend остаётся gateway без новой бизнес-логики и без планового изменения кода; регрессионные HTTP-проверки обязательны. Root tooling, Redis DB allocation, сеть, deployment, `site-*`, SEO queries/pages как справочники при очистке Метрики, новые интеграции и progress UI не входят в scope.

**Блокирующее предусловие apply:** закончить текущую параллельную задачу, отдельно получить одобрение этого плана и перед apply сверить финальные, синхронизированные контракты `105-seo-role` и его зависимости. SEO-only здесь — целевой контракт совместимости, не признание незавершённого кода утверждённым. Если финал 105 отличается, сначала пересмотреть matrix и план, не делать fallback на ADMIN. Планирование не трогает текущую задачу, стек или чужие файлы.

Профиль при реализации — QG-FULL (NATS и миграции). Техническая готовность `applyRequires` не отменяет пользовательский approval gate. Предложения для подтверждения: очистка только при фактическом удалении связанного счётчика (не несвязанного аккаунта), ретроактивность только POST правил, merge использует существующую аддитивную семантику `users`, без обещания уникальных посетителей между URL.
