## Context

Текущая реализация NATS Jetstream в основном backend (`services/backend`) использует `app.state.nats_client` для хранения клиента, что нарушает принципы Dependency Injection и SOLID. В микросервисах `notification-service` и `email-service` уже реализована корректная архитектура с использованием Dependency Injector.

Основные проблемы:
1. Несогласованность архитектуры между основным backend и микросервисами
2. Нарушение принципа инверсии зависимостей
3. Отсутствие стандартизированной документации по работе с NATS Jetstream

## Goals / Non-Goals

**Goals:**
- Унифицировать архитектуру работы с NATS Jetstream во всех сервисах
- Заменить `app.state.nats_client` на Dependency Injector в основном backend
- Создать документацию по протоколам NATS Jetstream
- Обновить инструкции backend агента

**Non-Goals:**
- Изменение бизнес-логики сервисов
- Модификация существующих NATS потоков (SITE_EVENTS, NOTIFICATION_COMMANDS)
- Добавление новых NATS потоков или подписчиков
- Изменение конфигурации NATS сервера

## Decisions

### 1. Использование Dependency Injector вместо app.state

**Решение**: Заменить `app.state.nats_client` на контейнер Dependency Injector в основном backend.

**Обоснование**:
- Соответствие архитектуре микросервисов (notification-service, email-service)
- Соблюдение принципа инверсии зависимостей (SOLID)
- Улучшение тестируемости и модульности
- Централизованное управление жизненным циклом NATS клиента

**Альтернативы рассмотрены**:
- Сохранение `app.state` - отклонено из-за нарушения архитектурных принципов
- Использование FastAPI Depends напрямую - отклонено из-за сложности управления жизненным циклом

### 2. Структура NATS конфигурации

**Решение**: Вынести настройки NATS в отдельный класс `NatsSettings` с префиксом `NATS_`.

**Обоснование**:
- Единообразие с микросервисами
- Четкое разделение конфигурации
- Упрощение тестирования и валидации

### 3. Документация протоколов

**Решение**: Создать отдельную спецификацию `nats-jetstream-protocols` и обновить `backend-domain-capabilities`.

**Обоснование**:
- Четкое разделение ответственности
- Возможность ссылаться на протоколы из разных частей системы
- Обеспечение консистентности реализации

## Risks / Trade-offs

### Риски

1. **Нарушение обратной совместимости** → Миграция будет поэтапной с сохранением работоспособности
2. **Сложность Dependency Injector** → Использование проверенных паттернов из микросервисов
3. **Необходимость тестирования** → Создание unit тестов для DI контейнера

### Trade-offs

1. **Дополнительная сложность vs. архитектурная чистота** → Выбрана архитектурная чистота
2. **Время разработки vs. долгосрочная поддержка** → Выбрана долгосрочная поддержка
