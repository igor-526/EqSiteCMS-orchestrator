# Spec Delta — cms-seo-yandex-ui

## Purpose

Раздел SEO в CMS frontend: навигация, вкладки Яндекс.Метрики и Яндекс.Вебмастера, управление привязкой счётчика Метрики и аккаунтами Яндекса через универсальный двухшаговый визард.

## ADDED Requirements

### Requirement: Пункт меню SEO

Боковое меню CMS MUST содержать пункт «SEO» с иконкой `RiseOutlined` из `@ant-design/icons`, ведущий на `/seo`. Пункт MUST быть видим только пользователям с существующей ролью `ADMIN`; при открытом `/seo` пункт активен, а заголовок страницы — «SEO». Отдельная роль SEO и новый серверный scope MUST NOT вводиться; локальный permission adapter MUST проверять только ADMIN без наследования SUPERUSER/DEVELOPER.

#### Scenario: Пользователь с ролью ADMIN
- **WHEN** в меню входит пользователь с ролью `ADMIN`
- **THEN** пункт «SEO» с иконкой виден, клик открывает `/seo`, пункт выделен как активный

#### Scenario: Пользователь без роли ADMIN
- **WHEN** в меню входит пользователь без роли ADMIN (включая SUPERUSER, DEVELOPER, USER_MANAGER и отсутствие ролей)
- **THEN** пункт «SEO» не отображается

### Requirement: Страница SEO с вкладками

`/seo` MUST быть Protected Admin UI (anonymous → редирект на `/login`) и отображать вкладки «Яндекс.Метрика» (по умолчанию) и «Яндекс.Вебмастер». Пользователь без роли ADMIN при прямом заходе MUST видеть состояние «недостаточно прав» без вызовов `/api/yandex/**`.

#### Scenario: Открытие раздела
- **WHEN** пользователь с ролью ADMIN открывает `/seo`
- **THEN** видны две вкладки, активна «Яндекс.Метрика»

#### Scenario: Прямой заход без роли ADMIN
- **WHEN** пользователь без роли ADMIN (включая SUPERUSER/DEVELOPER) открывает `/seo` по URL
- **THEN** отображается forbidden-состояние, запросы к `/api/yandex/**` не отправляются

### Requirement: Заглушка Яндекс.Вебмастера

Вкладка «Яндекс.Вебмастер» MUST показывать сообщение, что функционал находится в разработке, и MUST NOT выполнять API-вызовы.

#### Scenario: Открытие вкладки
- **WHEN** пользователь переключается на «Яндекс.Вебмастер»
- **THEN** отображается заглушка «Функционал в разработке», сетевых запросов нет

### Requirement: Блок привязки Яндекс.Метрики

Вкладка «Яндекс.Метрика» MUST содержать блок, загружающий `GET /api/yandex/metrica/connection` и показывающий состояния загрузки, ошибки (с повтором), «не привязано» и «привязано».

#### Scenario: Не привязано
- **WHEN** ответ содержит `counter: null`
- **THEN** блок сообщает, что Яндекс.Метрика не привязана, и показывает кнопку «Привязать», открывающую визард

#### Scenario: Привязано
- **WHEN** ответ содержит привязку
- **THEN** блок показывает номер счётчика и данные аккаунта (отображаемое имя, логин, email, телефон при наличии) и кнопку «Отвязать»

#### Scenario: Ошибка загрузки
- **WHEN** запрос завершается ошибкой
- **THEN** блок показывает сообщение ошибки и кнопку повтора, без кнопок мутаций

### Requirement: Отвязка счётчика через подтверждение

Отвязка счётчика MUST выполняться только после подтверждения в модальном окне; подтверждение вызывает `DELETE /api/yandex/metrica/connection`, защищено от двойной отправки и после успеха обновляет блок до состояния «не привязано».

#### Scenario: Подтверждение
- **WHEN** пользователь нажимает «Отвязать» и подтверждает
- **THEN** выполняется DELETE, блок переходит в «не привязано», показывается уведомление об успехе

#### Scenario: Отмена
- **WHEN** пользователь закрывает модалку подтверждения
- **THEN** запрос не отправляется, привязка остаётся

#### Scenario: Ошибка отвязки
- **WHEN** backend отвечает ошибкой (включая `401/403`)
- **THEN** модалка остаётся открытой с сообщением ошибки, блок не меняется

### Requirement: Универсальный двухшаговый визард

Визард MUST быть модальным окном из двух шагов: шаг 1 — выбор аккаунта Яндекса, шаг 2 — слот цели, передаваемый конфигурацией (заголовок шага и компонент, получающий выбранный аккаунт и колбэк завершения). Переход на шаг 2 возможен только при выбранном аккаунте; доступен возврат на шаг 1.

#### Scenario: Навигация по шагам
- **WHEN** пользователь выбирает аккаунт и нажимает «Далее»
- **THEN** визард показывает шаг 2 цели с выбранным аккаунтом; «Назад» возвращает на шаг 1 с сохранённым выбором

#### Scenario: Без выбранного аккаунта
- **WHEN** аккаунт не выбран
- **THEN** кнопка «Далее» недоступна

#### Scenario: Расширяемость цели
- **WHEN** визард открывается с другой конфигурацией цели (например, будущий выбор хоста Вебмастера)
- **THEN** шаг 1 переиспользуется без изменений, а шаг 2 рендерит переданный компонент цели

### Requirement: Шаг выбора аккаунта Яндекса

Шаг 1 MUST загружать `GET /api/yandex/accounts` (limit/offset, «Показать ещё» при `items < total`), показывать загрузку, ошибку, пустое состояние и последним пунктом — «Добавить аккаунт», запускающий OAuth-поток. Каждый аккаунт отображает имя, логин и email.

#### Scenario: Список аккаунтов
- **WHEN** у конюшни есть аккаунты
- **THEN** отображаются аккаунты и последним пунктом «Добавить аккаунт»

#### Scenario: Пустой список
- **WHEN** аккаунтов нет
- **THEN** отображается подсказка добавить аккаунт и пункт «Добавить аккаунт»

#### Scenario: Догрузка
- **WHEN** `total` больше числа загруженных аккаунтов и пользователь нажимает «Показать ещё»
- **THEN** запрашивается следующая страница с `offset` = числу загруженных, элементы добавляются в конец

### Requirement: Отвязка аккаунта Яндекса через подтверждение

У каждого аккаунта шага 1 MUST быть действие отвязки, выполняемое только после модалки подтверждения, которая предупреждает, что привязка счётчика через этот аккаунт тоже будет удалена. После успеха список аккаунтов и блок привязки обновляются, выбор сбрасывается, если отвязан выбранный аккаунт.

#### Scenario: Отвязка аккаунта
- **WHEN** пользователь подтверждает отвязку аккаунта
- **THEN** выполняется `DELETE /api/yandex/accounts/{id}`, аккаунт исчезает из списка, блок привязки перезагружается

#### Scenario: Аккаунт уже отсутствует
- **WHEN** backend отвечает `404`
- **THEN** показывается сообщение, список аккаунтов перезагружается

### Requirement: Шаг выбора счётчика Метрики

Цель «Яндекс.Метрика» MUST загружать `GET /api/yandex/metrica/counters` для выбранного аккаунта с поиском (debounce 300 мс, сброс `offset` в 0) и пагинацией `limit/offset`; выбор счётчика и «Привязать» вызывают `POST /api/yandex/metrica/connection`. Успех закрывает визард и обновляет блок.

#### Scenario: Привязка счётчика
- **WHEN** пользователь выбирает счётчик и нажимает «Привязать»
- **THEN** выполняется POST с `yandex_account_id` и `counter_id`, визард закрывается, блок показывает привязанный счётчик

#### Scenario: Поиск сбрасывает offset
- **WHEN** пользователь на второй странице вводит строку поиска
- **THEN** после debounce запрос уходит с `offset=0` и `search`

#### Scenario: Ошибка счётчиков
- **WHEN** backend отвечает ошибкой при загрузке счётчиков или привязке
- **THEN** шаг показывает сообщение ошибки, визард остаётся открытым, выбранный аккаунт сохраняется

### Requirement: Защита мутаций SEO на UI

Кнопки мутаций (привязать, отвязать, добавить аккаунт) MUST быть доступны только при роли ADMIN и защищены от двойной отправки; роль ADMIN повторно проверяется в hook перед вызовом API. Отказ backend `401/403` MUST отображаться пользователю.

#### Scenario: Локальный отказ без ADMIN
- **WHEN** пользователь без ADMIN, включая SUPERUSER/DEVELOPER, пытается запустить мутацию через hook
- **THEN** локальная проверка отклоняет действие, API не вызывается

#### Scenario: Двойной клик
- **WHEN** пользователь дважды быстро нажимает кнопку подтверждения мутации
- **THEN** отправляется ровно один запрос

#### Scenario: Отказ backend
- **WHEN** мутация получает `403`
- **THEN** пользователь видит сообщение об отсутствии прав, состояние UI не меняется
