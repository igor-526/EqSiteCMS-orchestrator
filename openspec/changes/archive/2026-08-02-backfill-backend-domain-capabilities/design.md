## Контекст

Пакет BE-2 охватывает десять исторических задач и один будущий spec-файл. Evidence берётся только из назначенных строк `historical-task-manifest.md`, backend code/tests и итоговых reports; task-файлы и legacy plans описывают намерение, но не доказывают runtime-контракт. Change является документационным backfill и не меняет сервисы или main specs.

## Цели / Не-цели

**Цели:**

- Свести подтверждённые доменные, persistence, media и DTO-контракты в capability `backend-domain-capabilities`.
- Зафиксировать endpoint access matrix с фактическими anonymous/authenticated результатами.
- Сохранить `G-002` и отсутствующее live evidence как явные gaps.
- Обеспечить трассировку задач 002, 004, 006, 007, 009, 010, 011, 013, 014 и 019.

**Не-цели:**

- Изменять runtime, миграции, тесты, UI, consumer rendering или main specs.
- Устранять gaps в рамках backfill.
- Описывать access platform из BE-1 или frontend/consumer поведение.

## Решения

### 1. Один capability объединяет tightly-coupled backend-домен

Требования группируются по наблюдаемым бизнес-контрактам, а не по одному spec на историческую задачу. Это сохраняет зарезервированный ownership BE-2 и позволяет reviewer проверить дубли внутри одного файла. Альтернатива с десятью capabilities отклонена как механическое копирование task-структуры.

### 2. Нормативными становятся только claims с runtime evidence

Код определяет текущую структуру и зависимости, tests подтверждают edge cases, reports — live HTTP результаты. Где report отсутствует, матрица указывает `gap`, а не предполагаемый статус. В частности, наличие unit-каталогов не превращается в утверждение о полном аудите или полном access-покрытии (`G-002`).

### 3. Access matrix группирует эквивалентные endpoint-семейства

Пути с одинаковой dependency/access-моделью объединяются wildcard-строками, но исключение `/api/news-cms`, pedigree и проверенные page-data endpoints выделяются отдельно. Tenant service key является контекстом Public Read, а не CMS auth-cookie. Роли указываются только на уровне, подтверждённом evidence: `admin` для news и «пользователь с требуемым scope» для остальных Protected Write.

### 4. Исторические отклонения сохраняются как фактический контракт

Для authenticated пользователя без pedigree scope report 011 фиксирует `400`, хотя общая policy ожидает `403`. Backfill MUST сохранить это как выявленное отклонение для access-review, а не нормализовать результат без runtime change.

## Риски / Компромиссы

- [Сгруппированный wildcard может скрыть различие отдельных маршрутов] → Reviewer сверяет каждое семейство с кодом и reports до sync.
- [Последующие изменения runtime сделали часть старого report устаревшей] → При конфликте приоритет имеет текущий код плюс наиболее поздний live report; конфликт блокирует sync.
- [Unit evidence принимается за полную проверку] → `G-002` явно запрещает такой вывод.
- [Access gaps воспринимаются как иной access class] → Матрица отделяет класс от отсутствующего подтверждения конкретного HTTP-статуса.

## План миграции

1. Создать и строго валидировать apply-ready delta change без runtime-изменений.
2. Выполнить backend и access review tasks 5.3–5.4 родительского change.
3. После устранения findings отдельная task 5.5 синхронизирует и архивирует пакет.
4. При blocking finding исправляется этот delta change; main specs до sync не затрагиваются.

## Открытые вопросы

Блокирующих вопросов для создания backfill нет. Live gaps задач 004/009 и полный аудит `G-002` остаются незакрытыми до появления отдельного evidence.
