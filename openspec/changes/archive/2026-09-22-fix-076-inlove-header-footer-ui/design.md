## Context

Change собирает шесть мелких визуальных доработок `services/site-ksk-inlove` из `docs/tasks/076_inlove_footer_and_header_improvement.md`. Ранее (`069`/`075`) уже фиксировалось требование к позиции маркера активного пункта в dropdown «Услуги» header: маркер не должен «отрываться» вниз от строки текста (issue 075: «точка ... находится не напротив пункта, а чуть ниже»). Текущая задача (076) сообщает регресс в противоположную сторону: маркер теперь рендерится поверх текста, перекрывая буквы. Обе нормативные цели («не оторван вниз» и «не перекрывает текст») одновременно выполнимы: маркер должен быть небольшим индикатором прямо под строкой текста, визуально примыкающим к ней, — это и зафиксировано в обновлённом requirement `inlove-site-shell`. Реализация в этой планировочной сессии не проверялась напрямую против исходного кода `site-ksk-inlove` (сервис не был чекаутнут в это рабочее дерево — корневой репозиторий является только orchestration-монорепо, см. `services.manifest`); исполнитель Site Consumer обязан сверить фактическую DOM/CSS-структуру header/footer с howto `agents/howto/site-ksk-inlove-design.md` перед правкой.

Footer до этого change не имел собственного нормативного требования к маркеру активного пункта и к точному способу визуального выделения группы «Услуги» (спецификация ссылалась на «согласовано с header»). Пользователь явно просит для footer другой, более лёгкий стиль группы (без рамки и стрелки, только отступ), поэтому footer и header намеренно расходятся в оформлении группы «Услуги»; полная синхронизация сохраняется только для порядка пунктов, primary phone и набора каналов.

Зелёный (`tone="forest"`) CTA-блок в конце нескольких страниц — часть переиспользуемого `Section`/`Button` каталога `inlove-ui-components`, а не одной страницы; пользователь привёл `/uslugi/zanyatiya` только как пример. `design_system_specification.md` (§61 «Dark sections») отдельно описывает paттерн «CTA: Ivory background; Forest text» для крупного финального Contact CTA/Footer перехода — это другой, более тяжёлый паттерн, который пользователь не просил менять. Явный запрос — «оставить цвет, добавить белую окантовку» — трактуется как самостоятельное правило для `Button` внутри `tone="forest"`, не как замена существующего Ivory-CTA паттерна.

## Goals / Non-Goals

**Goals:**
- Дать Site Consumer executor однозначные, непротиворечивые requirement-дельты для всех шести пунктов задачи.
- Явно развести header и footer в оформлении группы «Услуги», не ломая существующую нормативную синхронизацию по порядку/телефону/каналам.
- Обозначить единый, переиспользуемый источник исправления для зелёных CTA-блоков (`Section`/`Button` в `inlove-ui-components`), а не точечный фикс на одной странице.

**Non-Goals:**
- Не пересматривается паттерн «Dark sections» (§61) для крупного финального Contact CTA/Footer перехода — это отдельный, не затронутый задачей паттерн.
- Не меняется backend/API, access matrix или any endpoint contract — изменения полностью презентационные.
- Не вводится новый capability и не переименовываются существующие пути `openspec/specs/**`.

## Decisions

- **Один Site Consumer execution unit на реализацию + один на browser QA.** Объём — CSS/JSX правки в 3-4 компонентах одного сервиса (`SiteHeader`, `SiteFooter`, `ContactSection`, `Section`/`Button` в `src/ui/**`), без миграций и без пересечения с другими профилями — укладывается в бюджет одного unit (~8-12 действий) для правок + отдельный unit для QA на контрольных viewport (320/768/1024/1440), как в примере 4 `AGENTS.md`.
- **Маркер активного пункта — единое требование «под текстом, без отрыва».** Формулировка одновременно закрывает старый баг (075: маркер оторван вниз) и новый (076: маркер перекрывает текст), избегая противоречия между requirement-версиями при archive.
- **Footer «Услуги»: отступ вместо контейнера/стрелки, синхронизация header ослаблена явно.** Существующий scenario «Footer синхронизирован с header» переписан, чтобы не утверждать идентичное визуальное оформление группы — иначе delta вступила бы в противоречие сама с собой.
- **Зелёные CTA-блоки чинятся на уровне design-системы, а не постранично.** Новое требование добавлено в `inlove-ui-components` (`Section tone="forest"` + `Button`), чтобы правка автоматически применилась ко всем текущим и будущим страницам с этим паттерном, а не только к `/uslugi/zanyatiya`.
- **Белая окантовка кнопки — аддитивное свойство, а не смена варианта.** Явно сохраняется текущий `variant`/цвет заливки `Button`; добавляется только border/outline — по буквальному запросу пользователя «оставим цвет».

## Risks / Trade-offs

- [Реализация в коде может отличаться от предположений этой планировочной сессии, так как `services/site-ksk-inlove` не был доступен при propose] → Site Consumer executor обязан сверить фактическую разметку header/footer/ContactSection/Section/Button с DOM перед правкой и, если структура существенно отличается, вернуть Router `partial` с уточнением вместо угадывания.
- [Ослабление «Footer синхронизирован с header» может восприниматься как снижение консистентности бренда] → Явно ограничено только оформлением группы «Услуги» (рамка/стрелка/отступ); порядок пунктов, primary phone, иконки каналов и вся остальная синхронизация остаются обязательными.
- [Новое requirement для `tone="forest"` затронет все страницы с этим паттерном одновременно] → Это осознанный выбор (см. Decisions); QA-unit обязан проверить каждую страницу, использующую `Section tone="forest"` с CTA (как минимум `/uslugi/zanyatiya`, `/uslugi/progulki`, `/uslugi/postoy`), а не только пример из задачи.
