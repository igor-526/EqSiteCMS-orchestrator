# Spec Delta

## Purpose

Хранение неагрегированной дневной статистики Яндекс.Метрики по страницам входа и поисковым фразам конюшни так, чтобы её можно было корректно агрегировать по дням, диапазонам и месяцам, сортировать по любому показателю и фильтровать в рамках одной конюшни.

## ADDED Requirements

### Requirement: Две таблицы статистики по видам

ya-metrica-service SHALL хранить статистику набора «страницы» (dimensions `ym:s:date`, `ym:s:startURL`) в таблице `metrica_page_stats` и набора «запросы» (dimensions `ym:s:date`, `ym:s:lastSearchPhrase`) в таблице `metrica_search_query_stats`. Строка SHALL соответствовать одной конюшне, одной календарной дате и одной SEO-сущности (страница или поисковая фраза).

#### Scenario: Строка набора «страницы»
- **WHEN** задание «страницы» сохраняет строку API за `2026-10-23` для URL, который seo-service резолвит в UUID страницы `P`
- **THEN** в `metrica_page_stats` существует строка с `equestrian_id` конюшни, `stat_date=2026-10-23`, `page_id=P`, а `metrica_search_query_stats` не изменяется

#### Scenario: Строка набора «запросы»
- **WHEN** задание «запросы» сохраняет строку API с непустой фразой, которую seo-service резолвит в UUID `Q`
- **THEN** в `metrica_search_query_stats` существует строка с `equestrian_id`, `stat_date` и `search_query_id=Q`

### Requirement: Аддитивные колонки метрик

Каждая таблица SHALL хранить аддитивные целые неотрицательные колонки: `visits`, `users`, `pageviews`, `bounces` (визиты с отказом) и `visit_duration_seconds` (суммарная длительность визитов). `bounces` SHALL вычисляться как `round(bounceRate × visits / 100)`, `visit_duration_seconds` — как `round(avgVisitDurationSeconds × visits)`; `bounces` MUST NOT превышать `visits`. EAV/JSON-хранение метрик MUST NOT использоваться.

#### Scenario: Преобразование значений API
- **WHEN** API возвращает metrics `[30.0, 30.0, 59.0, 16.66666667, 1.96666667, 114.86666667]`
- **THEN** сохраняются `visits=30`, `users=30`, `pageviews=59`, `bounces=5`, `visit_duration_seconds=3446`

#### Scenario: Недопустимые значения отклоняются хранилищем
- **WHEN** запись пытается сохранить отрицательное значение колонки либо `bounces` больше `visits`
- **THEN** PostgreSQL отклоняет запись constraint'ом, и строка не сохраняется

### Requirement: Производные средние колонки

Каждая таблица SHALL содержать вычисляемые хранилищем (generated stored) колонки `bounce_rate = bounces × 100 / visits`, `page_depth = pageviews / visits` и `avg_visit_duration_seconds = visit_duration_seconds / visits`, округлённые до 8 знаков и равные 0 при `visits=0`. Колонки SHALL пересчитываться автоматически при любом изменении аддитивных колонок и быть доступны для сортировки.

#### Scenario: Совпадение с API
- **WHEN** сохранена строка `visits=30`, `pageviews=59`, `bounces=5`, `visit_duration_seconds=3446`
- **THEN** `bounce_rate=16.66666667`, `page_depth=1.96666667`, `avg_visit_duration_seconds=114.86666667` — как в исходном ответе API

#### Scenario: Нулевые визиты
- **WHEN** у строки `visits=0`
- **THEN** все три производные колонки равны 0 без ошибки деления

### Requirement: Уникальность конюшня–дата–сущность

Комбинация `(equestrian_id, stat_date, page_id)` в `metrica_page_stats` и `(equestrian_id, stat_date, search_query_id)` в `metrica_search_query_stats` SHALL быть уникальной на уровне БД. Сохранение строки с существующим ключом SHALL выполняться как upsert, а не как ошибка или дубликат.

#### Scenario: Конфликт ключа не создаёт дубликат
- **WHEN** две операции сохранения пишут одну и ту же конюшню, дату и сущность
- **THEN** в таблице остаётся ровно одна строка с этим ключом

### Requirement: Повторный парсинг заменяет значения

Если строку с ключом пишет другое задание, чем то, что записало её последним (повторный парсинг той же даты), аддитивные колонки SHALL заменяться значениями нового задания. Замена применяется только между заданиями и MUST NOT применяться к нескольким строкам API одного задания, попавшим в один ключ.

#### Scenario: Повторный парсинг сегодняшнего дня
- **WHEN** задание A сохранило за `2026-10-26` для страницы `P` `visits=12`, а позже задание B получает для того же ключа `visits=20`
- **THEN** строка содержит `visits=20` и остальные значения из задания B, количество строк не меняется

### Requirement: Агрегация строк API с одним UUID после нормализации

Если в одном задании несколько разных значений измерения (например, URL с отброшенными seo-service query-параметрами) резолвятся в один UUID, их статистика SHALL агрегироваться в одну строку: визиты, просмотры, отказы и суммарная длительность суммируются, поэтому доля отказов, глубина и среднее время визита становятся средними, взвешенными по визитам. `users` SHALL суммироваться как верхняя оценка. Правило SHALL действовать внутри страницы API и между страницами API.

#### Scenario: Два URL в один UUID внутри страницы API
- **WHEN** за одну дату пришли `/services/rides/tours?utm_source=a` (`visits=3`, `pageviews=6`, `bounceRate=0`, `avgVisitDurationSeconds=100`) и `/services/rides/tours` (`visits=1`, `pageviews=1`, `bounceRate=100`, `avgVisitDurationSeconds=20`), и seo-service резолвит оба в страницу `P`
- **THEN** сохраняется одна строка `P`: `visits=4`, `pageviews=7`, `bounces=1`, `visit_duration_seconds=320`, то есть `bounce_rate=25`, `page_depth=1.75`, `avg_visit_duration_seconds=80`

#### Scenario: Совпадение UUID на разных страницах API
- **WHEN** строка для ключа `K` пришла на первой странице API, а другая строка, резолвящаяся в тот же `K`, — на следующей странице того же задания
- **THEN** аддитивные колонки второй строки прибавляются к уже сохранённым, а не заменяют их

#### Scenario: Арифметическое среднее не используется
- **WHEN** агрегируются строки с `visits=99, bounceRate=0` и `visits=1, bounceRate=100`
- **THEN** итоговый `bounce_rate` равен 1, а не 50

### Requirement: Сверка окна задания при успехе

При успешном завершении задания строки той же конюшни и того же набора с датами в окне задания, которые не были записаны этим заданием, SHALL удаляться. В итоге окно отражает последний полный срез API.

#### Scenario: Исчезнувшая сущность
- **WHEN** предыдущий парсинг сохранил за `2026-10-21` страницу `P2`, а новое успешное задание за `2026-10-21..2026-10-25` строку для `P2` не получило
- **THEN** строка `P2` за `2026-10-21` удаляется, строки других конюшень, других наборов и дат вне окна не затрагиваются

#### Scenario: Задание не завершилось
- **WHEN** задание завершилось статусом `failed`
- **THEN** сверка окна не выполняется и ранее сохранённые строки не удаляются

### Requirement: Фильтрация по конюшне без списка сущностей

Каждая строка статистики SHALL содержать `equestrian_id`, а таблицы SHALL иметь индекс с ведущими `(equestrian_id, stat_date)`, чтобы выборка всей статистики конюшни за диапазон дат выполнялась без передачи в SQL списка страниц или фраз. Строки одной конюшни MUST NOT попадать в выборку другой.

#### Scenario: Изоляция конюшен
- **WHEN** у конюшни A есть 3 строки, у конюшни B — 2 строки за одну дату, и выполняется выборка по `equestrian_id=A`
- **THEN** возвращаются только 3 строки конюшни A

#### Scenario: Последняя записанная дата
- **WHEN** у конюшни A в `metrica_page_stats` максимальная дата `2026-10-25`, а в `metrica_search_query_stats` — `2026-10-20`
- **THEN** хранилище отдаёт последнюю дату отдельно по каждому набору: `2026-10-25` для страниц и `2026-10-20` для запросов; для конюшни без строк — отсутствие даты

### Requirement: SEO-сущности не хранятся в сервисе метрики

Таблицы статистики SHALL хранить только UUID сущности из seo-service, без исходного URL, нормализованного пути или текста фразы. Межсервисный внешний ключ на seo-service MUST NOT создаваться.

#### Scenario: Отсутствие текста сущности
- **WHEN** проверяется схема таблиц статистики после миграции
- **THEN** в них нет колонок с URL, путём или текстом фразы, есть только `page_id` либо `search_query_id` типа UUID
