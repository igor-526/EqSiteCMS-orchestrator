## Why

Локальная таблица `site_settings` для tenant `inlove` сейчас содержит универсальный набор настроек, хотя публичный сайт уже имеет фиксированную структуру и получает бизнес-сущности из профильных API. Перед отдельным будущим переносом таблицы нужно привести именно локальные данные и их потребление к минимальному, однозначному контракту, не перенося данные во внешнюю среду в рамках этого change.

## What Changes

- **BREAKING** Сократить управляемый администратором набор `site_settings` tenant `inlove`: удалить строки action 1 и данные услуг action 5, оставив только явно разрешённые настройки actions 2, 3, 4 и 6.
- Заменить универсальную модель блока «О клубе» четырьмя строковыми ключами `about_1_title`, `about_1_text`, `about_2_title`, `about_2_text`; второй блок необязателен и показывается только при одновременно заполненных title и text.
- Инициализировать эти четыре ключа явно редакционными заглушками, которые администратор сможет заменить после локальной коррекции.
- Оставить один управляемый телефон `contacts.primary_phone` для header, footer и контактов; удалить legacy `header.contact_phone` и список `contacts.phones`.
- Разнести управляемые контактные данные по отдельным ключам для адреса, координат и ссылок, сохранив существующие значения там, где они подтверждены задачей.
- Удалить дублирующий `contacts.address_alternative`; он не входит в итоговый каталог и consumer contract.
- Перевести страницы услуг на профильные Public Read API: группа находится по стабильному, не редактируемому администратором имени, а описание и карточки поступают из API. Неуправляемые дополнительные тексты страницы остаются статическими в consumer-коде только там, где они нужны дизайну.
- По read-only inventory локальной БД у tenant `inlove` нет строк `horse_service`; до consumer-переключения создать три отсутствующие группы с точными именами `Занятия`, `Прогулки`, `Постой` отдельной идемпотентной локальной data operation.
- До удаления строк проверить фактических потребителей ключей в CMS Frontend и `site-ksk-inlove`; обязательные UI-константы из удаляемых настроек перенести в consumer/service layer и покрыть регрессиями.
- Выполнить идемпотентную коррекцию только локальной PostgreSQL и зафиксировать проверяемый inventory до/после. Экспорт, копирование или перенос таблицы в stand/production либо другую БД не входят в change.
- API-маршруты и их классы доступа не меняются; change использует существующие Public Read `GET` и Protected Write site-settings endpoints.

## Capabilities

### New Capabilities

- `inlove-site-settings-curation`: канонический локальный набор управляемых настроек tenant `inlove`, правила преобразования данных и граница будущего переноса таблицы.

### Modified Capabilities

- `inlove-site-shell`: header, footer и контакты используют один телефон и сокращённый набор site settings с безопасными fallback.
- `inlove-content-pages`: блок «О клубе» переходит на два текстовых блока, а удалённые универсальные настройки перестают быть источником контента.
- `inlove-services-pages`: описания и карточки услуг поступают из профильного API, а группа выбирается по фиксированному имени, не управляемому через site settings.

## Impact

- Локальные данные: строки `site_settings` tenant `inlove` в PostgreSQL; требуется воспроизводимая и идемпотентная операция с evidence до/после, без переноса таблицы.
- Backend: существующие модели/repository/service/API используются без нового endpoint или изменения схемы; нужны локальные data operations для трёх отсутствующих `horse_service` и последующей коррекции `site_settings`.
- Site Consumer: `services/site-ksk-inlove/**` — адаптер настроек, shell/контакты, about и страницы услуг, тесты.
- CMS Frontend: только аудит generic CRUD и регрессия; продуктовые изменения не ожидаются, если не обнаружится key-specific зависимость.
- Контракты: существующие `GET /api/site_settings*` и профильные GET услуг остаются Public Read с tenant selector; `POST/PATCH/DELETE /api/site_settings*` остаются Protected Write.
