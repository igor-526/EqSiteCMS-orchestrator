# Proposal

## Why

При привязке email текущий frontend показывает просьбу перейти по ссылке из письма, но ни он, ни backend, ни create в email-service не запускают отправку подтверждения. Отправка запускается только отдельной кнопкой повторной отправки; необходимо замкнуть этот поток на backend без обязательного изменения frontend.

Исходный запрос: `docs/tasks/112_email_confirmation_on_bind.md`. Локализация основана на коде, не на воспроизведении SMTP-доставки.

## What Changes

- В body `POST /api/emails` добавить необязательный строгий boolean `send_confirmation`, по умолчанию `true`. Текущий frontend без нового поля автоматически получает запуск подтверждения при привязке; `false` сохраняет прежний режим «только сохранить».
- После успешного downstream create и проверки валидного `EmailResponse` для неподтверждённого адреса переиспользовать существующий HTTP `POST /emails/send-confirmation` email-service. Флаг не передаётся peer-сервису.
- Сохранить `201` и прежнюю схему успешного ответа. Успех означает сохранение адреса и принятие задачи существующим flow, но не доставку в ящик.
- При ошибке второго HTTP-шага вернуть контролируемый `502` с безопасным сообщением о сохранённом email и возможности повтора. Сохранение не откатывать; повтор того же адреса идемпотентен для ресурса, но может повторно поставить письмо в очередь. Уже подтверждённый адрес не отправлять и не сбрасывать его состояние.
- Owner-only boundary и существующие методы/публичные confirmation-исключения не менять. Полная access matrix с anonymous/authenticated сценариями находится в delta spec и design.
- `PATCH /api/emails`, delete, private read и ручной resend/confirm покрываются регрессией; автоматизация отправки при смене адреса через PATCH не входит в scope.

**Совместимость:** JSON входа/успешного ответа совместим с текущим frontend, однако default намеренно меняет побочный эффект существующего POST и добавляет возможность частичного успеха с `502`. Клиенты, которым нужна прежняя семантика без отправки, явно передают `false`. Это не обещание полной поведенческой обратной совместимости.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `email-backend-proxy`: опциональный флаг в create, последовательная оркестрация сохранения и постановки подтверждения, безопасные ошибки и сохранение access boundary.

## Impact

Изменяется только `services/backend`: request DTO, API-проброс, `EmailProxyService`, валидация ответа HTTP-клиента и зависимые unit/интеграционные тесты. Необходимые пути и ownership перечислены в design/tasks.

Frontend, email-service и notification-service не меняются. Новых ENV, миграций, таблиц, NATS subjects/envelopes и Celery-задач нет. Подтверждение уже идёт через HTTP → Celery → SMTP, не через notification NATS flow.

До approval — только эти артефакты. После реализации — единый `QG-LITE`; sync/повторная validation/archive выполняет Router после итогового вердикта и соответствующих approval gates.
