## Context

EqSiteCMS — монорепозиторий с микросервисной архитектурой. Backend построен на FastAPI с Clean Architecture (core/api/repositories), SQLAlchemy ORM, Alembic миграциями. Frontend — Next.js с FSD-структурой.

**Текущее состояние:**
- Таблица `users` содержит поля: `id`, `equestrian_id`, `username`, `password`, `first_name`, `last_name`, `middle_name`, `created_at`, `updated_at`
- Роли (scopes) хранятся в таблице `user_scopes`, связи — в `user_scope_relations`
- Существующие роли: `SUPERUSER`, `ADMIN`, `DEVELOPER`
- Сидирование ролей через JSON-файл `services/backend/src/core/seeds/user_scopes.json`
- Уже существует `SoftDeleteMixin` в `core/entities/base.py` (поля `is_deleted`, `deleted_at`)
- Защита эндпоинтов через dependency `get_current_user`, проверка scope через репозиторий

**Ограничения:**
- Soft-delete модель уже определена в `SoftDeleteMixin`, но не используется в User
- Сервисный endpoint `GET /api/service/users` использует `X-Service-Key`, а не user auth
- Публичная регистрация отключена (hardcoded в AuthService)

## Goals / Non-Goals

**Goals:**
- Добавить роль `USER_MANAGER` для делегирования управления пользователями администраторам конюшни
- Реализовать soft-delete для пользователей (без физического удаления из БД)
- Добавить механизм блокировки пользователей
- Создать Backend API для полного CRUD управления пользователями с фильтрацией, пагинацией, сортировкой
- Создать Frontend CMS страницу управления пользователями с таблицей и модальными окнами
- Обновить сервисный endpoint для исключения удалённых/заблокированных пользователей

**Non-Goals:**
- Восстановление удалённых пользователей через UI (только через БД разработчиком по запросу UM)
- Публичная регистрация пользователей
- Изменение логики авторизации/аутентификации
- Управление конюшнями (equestrians) из UI управления пользователями
- Изменение email-service или site-consumer
- Аудит-логирование действий UM
- Массовые операции блокировки/удаления

## Decisions

### 1. Модель данных: расширение существующей таблицы users

**Решение:** Добавить поля `is_deleted`, `deleted_at`, `is_blocked` в таблицу `users` через Alembic миграцию.

**Альтернативы:**
- Отдельная таблица `user_status` — отклонено, избыточная сложность для 3 булевых/временных полей
- Использование отдельной таблицы `deleted_users` — отклонено, усложняет запросы

**Обоснование:** `SoftDeleteMixin` уже существует в проекте, поля минимально инвазивны, не нарушают существующие FK.

### 2. Роль USER_MANAGER как scope

**Решение:** Добавить `USER_MANAGER` в `user_scopes.json` с фиксированным UUID, обновить сидер.

**Альтернативы:**
- Отдельная таблица ролей — отклонено, не соответствует текущей архитектуре
- Флаг в таблице users — отклонено, не гибко, не поддерживает множественные роли

**Обоснование:** Единый механизм scopes уже используется для SUPERUSER, ADMIN, DEVELOPER.

### 3. Endpoint для управления пользователями

**Решение:** Создать отдельный файл `services/backend/src/api/user_management.py` с router prefix `/api/user-management`.

**Альтернативы:**
- Расширить существующий `users.py` — отклонено, разные уровни доступа (me vs управление другими)
- Использовать admin namespace — рассмотрено, но `/api/user-management` более явно

**Обоснование:** Чёткое разделение ответственности: `/api/users` — профиль текущего пользователя, `/api/user-management` — администрирование.

### 4. Проверка доступа: dependency для UM/SU

**Решение:** Создать dependency `require_user_management` который проверяет наличие scope `USER_MANAGER` или `SUPERUSER` у текущего пользователя.

**Обоснование:** Следует паттерну существующих dependencies. SUPERUSER имеет все права по определению.

### 5. Фильтрация в сервисном endpoint

**Решение:** Добавить условие `WHERE is_deleted = false AND is_blocked = false` в запрос `GET /api/service/users`.

**Обоснование:** Заблокированные и удалённые пользователи не должны попадать в выдачу для сервисов.

### 6. Endpoint получения ролей

**Решение:** `GET /api/user-management/roles` — Protected Write, поддерживает поиск по `scope_name` (регистронезависимое regex).

**Альтернативы:**
- Public GET — отклонено, список ролей не нужен публичным сайтам
- Захардкодить на фронтенде — отклонено, не гибко при добавлении ролей

### 7. Фронтенд: FSD-структура

**Решение:** 
- Страница: `services/frontend/src/app/(protected)/users/page.tsx`
- Фичи: `services/frontend/src/features/user-management/` (компоненты таблицы, модальных окон, API-хуки)
- Кнопка в sidebar: добавить в `src/widgets/sidebar/`

**Обоснование:** Следует FSD-паттерну, аналогично существующим разделам (horses, news, prices).

### 8. Восстановление удалённых пользователей

**Решение:** Восстановление удалённых пользователей НЕ реализуется через UI. Разработчик выполняет прямой SQL-запрос к БД по запросу UM.

**Обоснование:** Текущая логика восстановления не доработана. UM обращается к разработчику, который вручную сбрасывает `is_deleted=false`, `deleted_at=null`.

### 9. Отсутствие аудит-логирования

**Решение:** Действия UM (создание, удаление, блокировка) НЕ логируются в audit-таблицу.

**Обоснование:** По требованию заказчика, аудит не требуется на данном этапе.

## Risks / Trade-offs

**[Risk] Миграция существующих данных** → Миграция добавит поля с дефолтами `is_deleted=false`, `is_blocked=false`. Существующие пользователи останутся активными. Rollback: удалить добавленные поля.

**[Risk] Нарушение FK-связей при soft-delete** → Удалённые пользователи останутся в БД с FK. При необходимости полного удаления потребуется ручная очистка разработчиком.

**[Risk] Производительность запросов с фильтрацией** → Добавить индексы на `is_deleted`, `is_blocked` для оптимизации WHERE-условий.

**[Trade-off] Восстановление только через БД** → Упрощает UI и бизнес-логику, но требует доступа разработчика для восстановления.

**[Trade-off] Отсутствие аудита** → Упрощает реализацию, но не позволяет отслеживать историю действий UM.

## Migration Plan

1. Создать Alembic миграцию: добавить `is_deleted`, `deleted_at`, `is_blocked` в `users`
2. Добавить индексы на `is_deleted`, `is_blocked`
3. Обновить `user_scopes.json`: добавить `USER_MANAGER`
4. Деплой backend с миграцией и обновлённым сидером
5. Деплой frontend с новой страницей управления

**Rollback:** Удалить миграцию (downgrade), откатить `user_scopes.json`, удалить frontend-страницу.
