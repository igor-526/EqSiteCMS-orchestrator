# CMS — метрики запросов

## MODIFIED Requirements

### Requirement: Таблицы сохранённых SEO-данных
CMS SHALL показывать страницы и запросы своей конюшни таблицами на одноимённых вкладках `/seo`. Колонки MUST содержать значение и дату создания; обе таблицы MUST дополнительно содержать справа колонки периода из `metrics_table` ответа. Чтение MUST использовать существующие GET backend с ответом `items/total` (для обеих таблиц — также `metrics_table`). Редактирование, создание и удаление страниц и запросов MUST NOT предлагаться.

#### Scenario: Данные и состояния
- **WHEN** ADMIN открывает вкладку «Страницы» или «Запросы»
- **THEN** загружается соответствующий список, показаны значение и дата, UUID служит стабильным ключом; loading, пустой ответ и ошибка с повтором различимы, ошибка не выдаётся за пустой успех

#### Scenario: Длинное значение
- **WHEN** страница или запрос содержит длинное значение
- **THEN** оно не перекрывает дату/колонки метрик/контролы, полное значение доступно через подсказку; путь страницы не превращается в выдуманный URL домена

### Requirement: Серверные фильтр и сортировка в заголовке
Фильтрация SHALL находиться исключительно в заголовке колонки значения. Фильтр MUST передавать `search` с debounce 300 мс и trim; очистка убирает параметр. Сортировка таблицы запросов MUST использовать `query/-query`, `created_at/-created_at` или `metric:<дата>/-metric:<дата>` колонки периода. Сортировка таблицы страниц MUST использовать `page/-page`, `created_at/-created_at` или `metric:<дата>/-metric:<дата>` колонки периода; одновременно активна не более одной сортировки, очистка убирает `ordering`. Фильтров по колонке «Создано», колонкам периода и UUID MUST NOT быть.

#### Scenario: Поиск и очистка
- **WHEN** ADMIN вводит поисковую подстроку в заголовке, затем очищает фильтр
- **THEN** запрос после debounce содержит search и offset=0; очистка выполняется сразу с offset=0 без search, символы %, _ и обратная косая черта не превращаются клиентом в шаблон

#### Scenario: Сортировка и её сброс
- **WHEN** ADMIN переключает сортировку значения по возрастанию, убыванию и сбрасывает её
- **THEN** API получает соответственно разрешённое поле, поле с минусом и отсутствие ordering; каждый переход сбрасывает offset=0, индикатор соответствует запросу

#### Scenario: Единый паттерн обеих таблиц
- **WHEN** ADMIN открывает «Страницы» либо «Запросы»
- **THEN** иконка поиска находится в стандартной области фильтра справа в шапке колонки значения, как в «Услуги и цены», без отдельной залитой кнопки рядом с названием; открывается выпадающая панель с полем и отдельной кнопкой «Очистить», а не только крестиком внутри поля

#### Scenario: Применённый фильтр и черновик
- **WHEN** ADMIN вводит строку с внешними и внутренними пробелами
- **THEN** draft поля сохраняет введённые пробелы; trim выполняется перед запросом; синяя иконка отражает непустой применённый search, а не ещё не применённый draft; Enter не обходит debounce и не переключает сортировку

#### Scenario: Явная очистка и закрытие панели
- **WHEN** ADMIN нажимает «Очистить» при применённом либо ожидающем debounce фильтре, затем закрывает и снова открывает панель
- **THEN** draft пуст, отложенный поиск отменён, search отсутствует и offset=0; ordering и limit сохранены; панель не закрывается от очистки, после повторного открытия поле остаётся пустым; обычное закрытие панели не очищает draft и не отменяет поиск

### Requirement: Верхняя пагинация таблиц
Пагинация обеих таблиц SHALL находиться справа в строке вкладок, относясь только к активной таблице. Пагинация MUST передавать серверу limit/offset, использовать total из ответа и сбрасывать offset при смене размера страницы. Состояния двух таблиц MUST быть независимы; устаревший ответ MUST NOT заменять актуальную выборку.

#### Scenario: Переходы страниц
- **WHEN** ADMIN открывает таблицу, переходит дальше и меняет размер страницы
- **THEN** начальные limit=25, offset=0; следующая страница имеет offset=25, изменение размера сбрасывает offset=0; page/pageSize в API не передаются

#### Scenario: Изоляция и гонка
- **WHEN** ADMIN переключает вкладки с разными фильтрами либо старый запрос завершается после нового
- **THEN** фильтры/сортировка/offset каждой таблицы сохраняются в пределах посещения `/seo`, отображается только актуальный результат соответствующей таблицы

### Requirement: Раскладка вкладки «Страницы»
На вкладке «Страницы» вкладки SEO SHALL располагаться слева, справа в той же строке — только пагинация таблицы страниц, кнопка «Сбросить» в стиле остальных страниц CMS и «Нормализация» (при разрешении); ниже — отдельная строка фильтров метрик. Строка вкладок и фильтры MUST оставаться видимыми: прокручивается только содержимое таблицы, колонки «Страница» и «Создано» закреплены слева. На 1366×768 элементы MUST NOT перекрываться.

#### Scenario: Прокрутка длинной таблицы
- **WHEN** ADMIN на 1366×768 открывает «Страницы» с 100 строками и 31 колонкой дней и прокручивает таблицу вниз и вправо
- **THEN** вкладки, пагинация, кнопки и фильтры остаются на месте, страница целиком не прокручивается, колонки «Страница» и «Создано» видны

#### Scenario: Другие вкладки
- **WHEN** ADMIN переключается на «Яндекс.Метрика» или «Яндекс.Вебмастер»
- **THEN** пагинация страниц, «Сбросить» и «Нормализация» в строке вкладок не показываются, поведение этих вкладок не меняется

#### Scenario: Переключение на запросы
- **WHEN** ADMIN переключается на «Запросы»
- **THEN** вместо действий страниц показаны пагинация запросов и «Сбросить», без «Нормализация»; состояние страниц не меняется

### Requirement: Колонки метрик и единственная сортировка
Таблицы страниц и запросов SHALL рендерить `metrics_table.columns` справа от «Страница»/«Запрос» и «Создано» в порядке ответа универсальным рендером: заголовок — `title`, подсказка — `hint`, ячейка — `text` из `values[row.id]`, иначе `empty_text`, выравнивание — `align`; форматировать значения CMS MUST NOT. Колонка с `sortable=true` SHALL сортироваться прямо и обратно, сортировка одной колонки снимает её с других. Индикатор MUST соответствовать `metrics_table.ordering`.

#### Scenario: Сортировка по колонке периода
- **WHEN** ADMIN нажимает на заголовок колонки `20 окт` дважды
- **THEN** запросы содержат `ordering=metric:2026-10-20`, затем `-metric:2026-10-20`, `offset=0`; индикатор только на этой колонке

#### Scenario: Переключение на другую колонку
- **WHEN** при сортировке по `20 окт` ADMIN сортирует по «Создано»
- **THEN** запрос содержит только `ordering=created_at`, индикатор с `20 окт` снят

#### Scenario: Пустые ячейки
- **WHEN** у страницы нет данных в колонке
- **THEN** в ячейке `—`, остальные ячейки строки не смещаются

### Requirement: Колонка «Создано»
Колонка «Создано» таблиц страниц и запросов SHALL показывать только дату `DD.MM.YYYY` без времени и поддерживать сортировку `created_at/-created_at`. Фильтра у колонки MUST NOT быть.

#### Scenario: Дата без времени
- **WHEN** страница создана `2026-10-23T14:05:00Z`
- **THEN** в колонке `23.10.2026`

#### Scenario: Дата создания запроса
- **WHEN** запрос создан 23.10.2026 в 14:05
- **THEN** показывается 23.10.2026 без времени, сортировка передаётся по полному created_at

## ADDED Requirements

### Requirement: Фильтры метрик запросов
«Запросы» SHALL иметь обязательные неочищаемые режим day/week/month/year, показатель из восьми `metrics-table-contract` и диапазон. Первое открытие и смена режима MUST отправлять запрос без дат с defaults day/visits при первом открытии. Серверный period MUST применяться без повторного запроса; today определяет запрет будущего. Предупреждение MUST появляться только при clamped=true.

#### Scenario: Серверный период и clamp
- **WHEN** сервер вернул скорректированный период
- **THEN** обе даты фильтра заменяются без запроса; adjusted без clamped не вызывает уведомления, clamped вызывает предупреждение с лимитом режима и итоговым диапазоном

#### Scenario: Смена режима, дат и показателя
- **WHEN** меняется режим, даты либо показатель
- **THEN** offset=0; режим запрашивает defaults без дат; режим и даты снимают metric-сортировку, показатель её сохраняет; metric-сортировка, снятая сервером, не остаётся в индикаторе

#### Scenario: Будущие единицы и обязательность
- **WHEN** ADMIN открывает picker любого из четырёх режимов
- **THEN** единицы целиком после period.today недоступны, текущая единица допустима; две даты отправляются вместе, фильтры не очищаются; клиент не рассчитывает defaults

### Requirement: Раскладка вкладки «Запросы»
Вкладки SHALL быть слева, справа на «Запросах» — только пагинация и «Сбросить». Ниже MUST быть отдельная строка метрик. На 1366×768 вкладки, действия, фильтры и заголовок MUST оставаться видимыми; вертикально прокручивается только тело. Основные колонки «Запрос» и «Создано» MUST быть закреплены слева при горизонтальной прокрутке динамических колонок. «Нормализация» MUST NOT предлагаться для запросов.

#### Scenario: Максимальная таблица
- **WHEN** ADMIN открывает 100 строк и 31 колонку дней, прокручивает вниз и вправо
- **THEN** панели/заголовок и основные колонки видимы без overlap, page scroll не заменяет прокрутку тела, динамические колонки доступны

### Requirement: Сброс запросов и защита состояния
«Сбросить» SHALL очищать применённый search, draft и единственную сортировку, отменять pending debounce, ставить offset=0 и отправлять один запрос. Mode/metric/даты/limit MUST сохраняться. Неактивная вкладка, отзыв ADMIN и поздний ответ MUST NOT перезаписывать актуальные данные или запускать чтение без разрешения. Состояния страниц и запросов MUST быть независимы.

#### Scenario: Сброс во время debounce
- **WHEN** есть применённый поиск, новый draft, сортировка, offset>0 и ADMIN нажал «Сбросить»
- **THEN** один запрос без search/ordering с offset=0, прежними mode/metric/датами/limit; поздний debounce не отправляет второй запрос

#### Scenario: Гонка и отзыв scope
- **WHEN** старый ответ пришёл после нового либо ADMIN отозван во время запроса
- **THEN** устаревший ответ игнорируется; без scope нет новых вызовов и не показываются приватные данные

### Requirement: Access matrix метрик запросов в CMS
CMS SHALL читать запросы только через backend по матрице ниже, без selector и peer-вызовов. Причина Protected GET exception — приватная аналитика ADMIN; SUPERUSER/DEVELOPER без ADMIN не допускаются. Ошибка MUST NOT выглядеть пустым успехом; 401 использует общий auth flow, 403 показывает отказ; 400/502 сохраняют фильтры и допускают повтор чтения.

#### Scenario: Anonymous и authenticated UI
- **WHEN** anonymous открывает /seo, затем ADMIN и пользователь без ADMIN открывают вкладку запросов
- **THEN** anonymous блокируется/переходит на login, ADMIN видит таблицу, без ADMIN показан отказ и hook не делает вызов; API-boundary mocks проверяют 401/403

#### Scenario: Ошибки и пустой результат
- **WHEN** API возвращает последовательно empty, 400, 502 и успех
- **THEN** состояния различимы, ошибки не стирают фильтры, повтор восстанавливает данные без ложного успеха

| method | path | access class | roles | expected without auth | expected with auth |
|---|---|---|---|---|---|
| GET | backend `/api/seo/search-queries` с search/ordering/limit/offset/mode/metric/date_from/date_to | Protected GET exception | только ADMIN | `401` | ADMIN `200` с metrics_table; без ADMIN `403`; невалидный query `400`; downstream/DTO failure `502` |
