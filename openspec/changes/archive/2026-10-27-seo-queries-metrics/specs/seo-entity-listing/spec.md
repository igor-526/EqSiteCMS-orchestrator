# Список запросов с метриками

## MODIFIED Requirements

### Requirement: Список поисковых запросов конюшни
`GET /api/search-queries` SHALL возвращать `200` с `{"items": [{"id", "query", "created_at"}], "total", "metrics_table"}` только для конюшни из `X-Equestrian-Id`. `total` MUST учитывать поиск и не зависеть от пагинации или наличия статистики. `metrics_table` SHALL соответствовать `metrics-table-contract`, version=1, row_key="id", с ячейками только текущей страницы. Один запрос MUST оставаться одной строкой независимо от числа дней статистики.

#### Scenario: Только своя конюшня
- **WHEN** у конюшни A два запроса, у B — один, и запрашивается список A
- **THEN** `items` содержит два запроса A, `total` равен 2, метрики относятся только к A

#### Scenario: Пустая выборка
- **WHEN** поиск не нашёл запросов
- **THEN** `items=[]`, total=0, metrics_table содержит разрешённый период и колонки с пустыми values; table peer не вызывается

### Requirement: Сортировка
Параметр `ordering` SHALL принимать `query`/`-query` для запросов, `page`/`-page` для страниц; обе сущности также принимают `created_at`/`-created_at` и `metric:<YYYY-MM-DD>`/`-metric:<YYYY-MM-DD>`. Без параметра список MUST сортироваться по `created_at` по убыванию. Вторичный ключ `id` MUST делать порядок детерминированным. Другое значение, включая некорректную дату в `metric:`, MUST давать `400`.

#### Scenario: Сортировка по умолчанию
- **WHEN** запросы созданы последовательно `X`, затем `Y`, и `ordering` не передан
- **THEN** `Y` идёт раньше `X`

#### Scenario: Сортировка по значению
- **WHEN** запрашивается `ordering=-page`
- **THEN** страницы упорядочены по `page` по убыванию

#### Scenario: Сортировка страниц по дате создания
- **WHEN** страницы созданы последовательно `A`, затем `B`, и запрашивается `ordering=created_at`
- **THEN** `A` идёт раньше `B`

#### Scenario: Неизвестная сортировка
- **WHEN** запрашивается `ordering=page` для запросов, `ordering=query` для страниц либо `ordering=metric:2026-13-40`
- **THEN** ответ `400`

#### Scenario: Полный timestamp запросов
- **WHEN** два запроса созданы в один день в разное время и выбрана сортировка created_at либо -created_at
- **THEN** сортировка использует полный timestamp и id в том же направлении, а не показанную дату

## ADDED Requirements

### Requirement: Период и форматирование запросов
Список запросов SHALL принимать `mode`, `metric`, `date_from/date_to` по `seo-metrics-period` и использовать все восемь показателей модели запросов по `metrics-table-contract`. SEO SHALL разрешать период своей настройкой `SEO_UTC_OFFSET_HOURS` и формировать готовые title/hint/text существующими правилами. Невалидный mode/metric, одиночная, некорректная или обратная дата MUST давать `400` до чтения данных и peer.

#### Scenario: Defaults и календарь
- **WHEN** без дат по очереди запрошены day/week/month/year
- **THEN** сервер возвращает соответственно 7 дней/4 недели/6 месяцев/2 года, включая текущую единицу, не включая будущие даты

#### Scenario: Clamp второй даты
- **WHEN** сегодня 26.10.2026, запрошено day с 01.09.2026 по 26.10.2026
- **THEN** итог 01.09–01.10, clamped=true, 31 колонка; первая дата не сдвигается

#### Scenario: Форматы и разреженность
- **WHEN** получены ноль, отсутствие данных, дробь и длительность, включая неделю на стыке лет
- **THEN** ноль показан как ноль, отсутствие как `—`; text/title/hint соответствуют metrics-table-contract без второго формата для запросов

### Requirement: SQL поток списка запросов
При существующей metric-колонке сортировки SEO SHALL получить M6 ранжирование, применить его вместе с tenant/search в SQL до limit/offset, затем получить M5 для UUID текущей страницы и всех buckets. Без metric-сортировки M6 MUST NOT вызываться. SQL-сортировка по агрегату ставит запросы без данных последними в обоих направлениях, далее default created_at desc/id desc. Агрегация и сортировка в памяти MUST NOT выполняться.

#### Scenario: Глобальная сортировка и поиск
- **WHEN** ранжировано больше одной страницы, применены search и offset
- **THEN** выдаётся срез полного SQL-ранжирования после поиска, total считает все найденные сущности, UUID без статистики остаются в списке

#### Scenario: Колонка вне периода
- **WHEN** синтаксически валидная metric-дата не является ключом разрешённого периода
- **THEN** ranking не вызывается, применяется default порядок, metrics_table.ordering=null

### Requirement: Пакетность и отказы списка запросов
На один валидный запрос списка SEO SHALL выполнять два SQL (выборка и count), не более двух peer-вызовов; при пустой выборке M5 MUST NOT вызываться. Любой не-200, таймаут, транспортная ошибка, невалидная схема или несовпадение metric/direction peer MUST давать безопасный `502`, без частичного успеха. Периоды, форматирование и сортировка SHALL возвращать фактически применённые значения.

#### Scenario: SQL/N+1
- **WHEN** с SQL-логированием сравниваются limit=5,50,100 и 1,31 колонка, с ранжированием и без
- **THEN** два SQL SEO, один SQL на каждый peer; peer-вызовы равны 1 без ranking и 2 с ranking для непустой страницы, не растут с размером

#### Scenario: Ошибка Метрики
- **WHEN** M5/M6 недоступен, возвращает 400 или невалидное тело
- **THEN** SEO отвечает 502 с безопасным detail, не выдаёт ошибку как отсутствие статистики

Доступ изменённого endpoint нормативно задан полной матрицей и anonymous/authenticated scenarios в delta `seo-peer-http-contract` этого change.
