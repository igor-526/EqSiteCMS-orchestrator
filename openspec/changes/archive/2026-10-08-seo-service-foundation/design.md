## Context

EqSiteCMS строит микросервисную инфраструктуру для SEO-анализа. Новый `seo-service` становится центральным оркестратором, который:
- Принимает запросы от основного `backend` и отвечает данными из общих сущностей
- Хранит общие сущности (search queries, site paths) — детальная схема будет определена в отдельной задаче
- Хранит расписание парсингов (parsing schedules)
- Ставит задачи парсерам через NATS JetStream
- Результаты парсинга остаются в сервисах-парсерах, seo-service не собирает их обратно

Текущее состояние:
- Есть `fastapi-template` для создания новых сервисов
- Инфраструктура `docker-compose.yml` поддерживает PostgreSQL, NATS, Redis
- Корневой `Makefile` управляет сборкой и тестированием сервисов
- `services.manifest` регистрирует микросервисы и их Git-репозитории
- Агентная архитектура определена в `AGENTS.md` и `agents/`

Ограничения:
- На данном этапе devops-инфраструктура (`.helm`, `.github`) не создаётся
- Git-репозиторий `EqSiteCMS-seo-service` существует как remote, но пока пуст
- NATS JetStream и Celery протоколы уже описаны в `agents/howto/nats-jetstream-protocols.md`

## Goals / Non-Goals

**Goals:**
- Создать работающий `seo-service` с поднятыми контейнерами БД и сервиса
- Интегрировать NATS JetStream для event-driven взаимодействия с парсерами
- Интегрировать Celery для планирования задач парсинга
- Подготовить инфраструктуру для разработки: миграции, модели, API-шаблоны
- Зафиксировать архитектурные решения в документации `docs/seo/`
- Расширить агентную архитектуру правилами работы с SEO-сервисом

**Non-Goals:**
- Реализация бизнес-логики парсинга (будет в отдельных сервисах `yandex-metrics-parser-service`, `yandex-auth-service`)
- Devops-инфраструктура (`.helm`, `.github`)
- Реализация конкретных API endpoint'ов (только шаблон структуры)
- Интеграция с существующим `backend` (будет в отдельном change)

## Decisions

### D1: Использование fastapi-template как основы

**Решение:** Копируем `fastapi-template` в `services/seo-service/` и адаптируем под нужды SEO-оркестратора.

**Альтернативы:**
- Создать с нуля — дольше, дублирует уже проверенную структуру
- Использовать cookiecutter — избыточно, когда есть внутренний шаблон

**Обоснование:** `fastapi-template` уже содержит Clean Architecture, миграции Alembic, интеграцию тестов, Docker-setup. Переиспользование ускоряет старт и обеспечивает консистентность с другими сервисами.

### D2: NATS JetStream для постановки задач парсерам

**Решение:** Используем NATS JetStream только для асинхронной постановки задач парсерам. Результаты парсинга остаются в сервисах-парсерах.

**Streams:**
- `SEO_TASKS` — задачи парсинга от seo-service к парсерам

**Subjects:**
- `seo.tasks.yandex_metrics` — задачи для Яндекс.Метрики (заготовка для будущих парсеров)
- Другие subjects будут добавлены при реализации соответствующих парсеров

**Важно:** Результаты парсинга НЕ возвращаются в seo-service через NATS. Каждый парсер хранит свои метрики и предоставляет их по запросу (архитектура будет детализирована в отдельной задаче).

**Альтернативы:**
- REST API между сервисами — синхронный, требует retry-логику, менее масштабируемый
- RabbitMQ — дополнительная зависимость, когда NATS уже используется в проекте

**Обоснование:** NATS JetStream обеспечивает at-least-once delivery, persistence, replay capability для задач парсинга. Уже есть в инфраструктуре. Протоколы работы описаны в `agents/howto/nats-jetstream-protocols.md`.

### D3: Celery для планирования задач парсинга

**Решение:** Используем Celery с Redis backend для периодических задач (расписание парсингов).

**Задачи Celery:**
- `schedule_parsing` — cron-задача, проверяет `parsing_schedules` в БД и ставит задачи парсерам в NATS

**Альтернативы:**
- APScheduler — проще, но не distributed, нет persistence
- Только NATS — не подходит для cron-like scheduling

**Обоснование:** Celery — стандарт для Python-экосистемы, поддерживает распределённые задачи, retry, monitoring. Redis уже используется в проекте. На данном этапе достаточно одной задачи для планирования; обработка результатов будет проработана в отдельной задаче.

### D4: PostgreSQL для хранения сущностей

**Решение:** Выделенная БД `seo_service` в существующем PostgreSQL-контейнере.

**Основные сущности:**
- `parsing_schedules` — расписание парсингов (единственная сущность на данном этапе)
- Общие сущности `search_queries` и `site_paths` будут спроектированы в отдельной задаче
- История задач парсинга (`parsing_tasks`) также будет добавлена позже при необходимости

**Альтернативы:**
- Shared БД с основным backend — смешивает ownership, усложняет миграции
- Отдельный PostgreSQL-контейнер — избыточно на данном этапе

**Обоснование:** Выделенная БД обеспечивает изоляцию данных и миграций, но использует общий контейнер для экономии ресурсов на dev-окружении.

### D5: Git-репозиторий и versioning

**Решение:** `seo-service` живёт в монорепозитории `services/seo-service/`, но также синхронизируется в отдельный Git-репозиторий `git@github.com:igor-526/EqSiteCMS-seo-service.git`.

**Initial commit включает:**
- Код сервиса
- `README.md` с описанием архитектуры
- Миграции Alembic
- Конфигурация Docker

**Ветки:** `main` и `release` инициализируются одновременно с одинаковым initial commit.

**Альтернативы:**
- Только монорепозиторий — проще, но теряем возможность независимого versioning
- Git submodule — усложняет workflow

**Обоснование:** Hybrid подход: разработка в монорепозитории (удобно для cross-service changes), но отдельный репозиторий позволяет независимое версионирование и потенциальное переиспользование в других проектах.

### D6: Документация SEO-модуля

**Решение:** Создаём `docs/seo/` с архитектурной документацией:
- `docs/seo/architecture.md` — общая архитектура SEO-модуля
- `docs/seo/services.md` — описание seo-service и будущих парсеров
- `docs/seo/protocols.md` — контракты NATS и Celery для SEO-задач

**Обоснование:** Агенты будут направляться на эту документацию при работе с SEO-инфраструктурой. Централизованное описание архитектуры упрощает онбординг и развитие модуля.

### D7: Расширение агентной архитектуры

**Решение:** Расширяем `AGENTS.md` секцией про SEO-сервисы:
- Backend-агент получает правило читать `docs/seo/` при работе с `services/seo-service/**`
- Quality Gate проверяет соответствие NATS/Celery протоколам из `agents/howto/nats-jetstream-protocols.md`

**Обоснование:** Агенты должны знать, где искать контекст для SEO-задач, и какие дополнительные проверки применять.

## Risks / Trade-offs

### R1: Сложность интеграции NATS + Celery
**Risk:** Два асинхронных механизма могут усложнить debugging и monitoring.

**Mitigation:**
- Используем structured logging с trace_id для корреляции NATS messages и Celery tasks
- Документируем flow в `docs/seo/protocols.md`
- Quality Gate проверяет соответствие протоколам из `agents/howto/nats-jetstream-protocols.md`

### R2: Выделенный Git-репозиторий требует синхронизации
**Risk:** Изменения в монорепозитории могут рассинхронизироваться с отдельным репозиторием.

**Mitigation:**
- На данном этапе initial commit синхронизируется вручную
- Автоматизация синхронизации будет в отдельном change
- `services.manifest` содержит ссылку на remote для явного контракта

### R3: Расширение docker-compose может затронуть другие сервисы
**Risk:** Изменения в общем `docker-compose.yml` могут сломать существующие сервисы.

**Mitigation:**
- Quality Gate (`QG-ENV`) проверяет health всех сервисов после изменений
- Используем Docker networks для изоляции SEO-сервисов
- Smoke-тесты существующих сервисов запускаются в `QG-LIVE`

### R4: Пустая реализация может не показать реальные проблемы интеграции
**Risk:** Без реальной бизнес-логики сложно проверить корректность архитектурных решений.

**Mitigation:**
- Включаем минимальные smoke-тесты: отправка тестового NATS message, запуск тестовой Celery task
- Документируем expected behavior в `docs/seo/protocols.md`
- Следующие changes будут реализовывать конкретные парсеры и проверять интеграцию

## Migration Plan

### Deployment Steps

1. **Подготовка инфраструктуры:**
   - Обновить `docker-compose.yml` с новыми сервисами и зависимостями
   - Создать БД `seo_service` через миграции
   - Запустить NATS streams через init-скрипт

2. **Создание сервиса:**
   - Скопировать `fastapi-template` в `services/seo-service/`
   - Адаптировать конфигурацию (DB connection, NATS, Celery)
   - Применить миграции

3. **Инициализация Git:**
   - `git init` в `services/seo-service/`
   - `git remote add origin git@github.com:igor-526/EqSiteCMS-seo-service.git`
   - `git push -u origin main` и `git push -u origin release`

4. **Документация:**
   - Создать `docs/seo/` с архитектурной документацией
   - Обновить `AGENTS.md` и `services.manifest`

5. **Verification:**
   - `make test` для seo-service
   - `stackctl doctor` для проверки health всех сервисов
   - Smoke-тест NATS и Celery интеграций

### Rollback Strategy

- Удалить `services/seo-service/` из монорепозитория
- Откатить изменения в `docker-compose.yml`, `Makefile`, `services.manifest`
- Удалить БД `seo_service` (если создавалась)
- Удалить NATS stream `SEO_TASKS`

На данном этапе rollback простой, так как ещё нет зависимостей от других сервисов.
