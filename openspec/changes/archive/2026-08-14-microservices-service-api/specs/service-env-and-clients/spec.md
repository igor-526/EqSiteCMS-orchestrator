## ADDED Requirements

### Requirement: ENV-переменная SERVICE_KEY в backend
Backend MUST использовать ENV-переменную `SERVICE_KEY` для валидации заголовка `X-Service-Key`. Значение MUST быть рандомной строкой, не пустой. При отсутствии переменной backend MUST логировать предупреждение, но продолжать работу (сервисные эндпоинты будут недоступны).

#### Scenario: SERVICE_KEY задан
- **WHEN** backend запускается с заданной `SERVICE_KEY`
- **THEN** сервисные эндпоинты доступны по `X-Service-Key`

#### Scenario: SERVICE_KEY не задан
- **WHEN** backend запускается без `SERVICE_KEY`
- **THEN** backend логирует предупреждение; запросы к `/api/service/*` возвращают `503 Service Unavailable`

### Requirement: ENV-переменные в микросервисах
Каждый микросервис, обращающийся к основному backend по HTTP, MUST иметь ENV-переменные:
- `MAIN_BACKEND_URL` — URL основного backend (например, `http://backend:8000`)
- `MAIN_BACKEND_SERVICE_KEY` — значение `X-Service-Key` для авторизации

#### Scenario: Микросервис с заданными ENV
- **WHEN** микросервис запускается с `MAIN_BACKEND_URL=http://backend:8000` и `MAIN_BACKEND_SERVICE_KEY=<ключ>`
- **THEN** микросервис может обращаться к backend по HTTP

#### Scenario: Микросервис без MAIN_BACKEND_URL
- **WHEN** микросервис запускается без `MAIN_BACKEND_URL`
- **THEN** микросервис логирует ошибку и не пытается обращаться к backend по HTTP

### Requirement: ENV-переменные для будущих межсервисных вызовов
При необходимости межсервисных HTTP-вызовов MUST добавляться ENV-переменные вида `<SERVICE_NAME>_URL` (например, `NOTIFICATION_SERVICE_URL`, `EMAIL_SERVICE_URL`). Хардкод URL или ключей в коде MUST отсутствовать.

#### Scenario: Добавление нового межсервисного URL
- **WHEN** разработчик добавляет HTTP-клиент к новому сервису
- **THEN** URL берётся из ENV-переменной, а не из хардкода

### Requirement: HTTP-клиент на aiohttp в микросервисах
Микросервисы MUST использовать библиотеку `aiohttp` для HTTP-запросов к другим сервисам. Клиенты MUST размещаться в папке `clients/` каждого микросервиса, аналогично NATS-клиентам в backend.

#### Scenario: Структура папки clients
- **WHEN** разработчик смотрит на микросервис
- **THEN** папка `clients/` содержит HTTP-клиенты к другим сервисам

#### Scenario: Использование клиента в core-слое
- **WHEN** микросервису нужно обратиться к другому сервису
- **THEN** клиент вызывается через dependency injection, а не напрямую из core

### Requirement: Обработка ошибок HTTP-клиента
Все ошибки HTTP-клиента MUST обрабатываться. При недоступности целевого сервиса backend MUST возвращать `500 Internal Server Error` с описанием проблемы, а не `502 Bad Gateway`.

#### Scenario: Микросервис недоступен
- **WHEN** backend обращается к микросервису по HTTP, но сервис недоступен
- **THEN** backend возвращает `500` с сообщением "Сервис <имя> недоступен: <описание ошибки>"

#### Scenario: Таймаут запроса к микросервису
- **WHEN** запрос к микросервису превышает таймаут
- **THEN** backend возвращает `500` с сообщением "Превышен таймаут ожидания ответа от сервиса <имя>"

#### Scenario: Невалидный ответ от микросервиса
- **WHEN** микросервис возвращает неожиданный формат ответа
- **THEN** backend возвращает `500` с сообщением "Невалидный ответ от сервиса <имя>: <описание>"

#### Scenario: Успешный ответ от микросервиса
- **WHEN** микросервис возвращает успешный ответ
- **THEN** backend обрабатывает ответ и возвращает данные клиенту
