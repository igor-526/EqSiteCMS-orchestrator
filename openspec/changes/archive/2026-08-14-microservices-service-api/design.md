## Context

EqSiteCMS — мультисервисная платформа. Помимо NATS Jetstream для асинхронных событий, микросервисы обращаются к основному backend по HTTP. В настоящее время стандартного механизма авторизации для таких запросов нет: cookie-авторизация предназначена для CMS-пользователей, `X-Equestrian-Service-Key` — для site-consumer'ов (tenant-scoped). Для межсервисных запросов нужен отдельный уровень защиты.

Микросервисы работают исключительно в локальной сети и не выставлены наружу, но backend должен контролировать, что запрос исходит от доверенного сервиса, а не от произвольного клиента.

### Текущее состояние

- **Cookie auth**: `access_token` / `refresh_token` HTTP-only cookie, используется CMS-фронтендом.
- **Equestrian key auth**: `X-Equestrian-Service-Key` header, используется site-consumer'ами для tenant-scoped Public Read.
- **Backend**: FastAPI, dependency injection через `depends/services.py`, `get_current_user`, `get_public_equestrian_context`, `get_read_equestrian_context`.
- **Микросервисы**: notification-service, email-service — используют NATS, HTTP-клиенты пока отсутствуют.

## Goals / Non-Goals

**Goals:**

- Ввести `X-Service-Key` header как третий способ авторизации, изолированный от cookie и equestrian key.
- Вынести все сервисные эндпоинты под префикс `/api/service/`.
- Реализовать первый сервисный эндпоинт `GET /api/service/users` с пагинацией и фильтрацией.
- Стандартизировать пагинацию сервисных эндпоинтов.
- Добавить ENV-переменные и HTTP-клиенты в микросервисах.
- Обновить агент `backend.md` с протоколом сервисных эндпоинтов.

**Non-Goals:**

- Изменение существующих cookie/equestrian key эндпоинтов.
- Реализация сервисных эндпоинтов, отличных от `GET /api/service/users` (будущие расширения).
- Внешний доступ к сервисным эндпоинтам (только локальная сеть).
- Реализация обратного вызова backend → микросервисы через HTTP (пока только NATS).

## Decisions

### 1. Авторизация через `X-Service-Key` header

**Решение:** Новый header `X-Service-Key`, значение которого сверяется с ENV `SERVICE_KEY`.

**Обоснование:**
- Простая реализация: достаточно одного shared secret для локальной сети.
- Не зависит от JWT/cookie — сервисы не поддерживают cookie-обмен.
- Не требует внешнего IdP.

**Альтернативы:**
- JWT токены для сервисов — избыточная сложность для локальной сети.
- mTLS — требует управления сертификатами; не в scope первой итерации.
- IP-based allowlist — ненадёжно при масштабировании в Kubernetes.

### 2. Изоляция сервисных эндпоинтов

**Решение:** Отдельный dependency `get_service_context`, который валидирует `X-Service-Key`. Cookie и equestrian key игнорируются на сервисных эндпоинтах.

**Обоснование:**
- Гарантирует, что обычные пользователи и site-consumer'ы не могут обращаться к `/api/service/*`.
- Не требует изменения существующих dependency.

### 3. Префикс `/api/service/`

**Решение:** Все сервисные эндпоинты регистрируются в отдельном APIRouter с префиксом `/api/service`.

**Обоснование:**
- Единая точка разграничения: middleware может отклонять запросы к `/api/service/` без валидного ключа.
- Легко расширять новыми подроутерами.
- Swagger-группировка.

### 4. Пагинация: limit/offset с total

**Решение:** `limit` (default=100, max=5000), `offset` (default=0). Ответ — `PaginatedEntities[T]` с полями `items` и `total`.

**Обоснование:**
- Совместимо с существующей `PaginatedEntities[T]` из `core/entities/base.py`.
- `total` позволяет клиенту определить, нужен ли следующий запрос.
- Единый стандарт для всех сервисных эндпоинтов.

**Альтернативы:**
- Cursor-based пагинация — сложнее для межсервисного взаимодействия; не в scope первой итерации.

### 5. Фильтрация пользователей

**Решение:** `GET /api/service/users` принимает:
- `equestrian_ids` (list[UUID]) — фильтр по ID конюшен (OR).
- `equestrian_service_keys` (list[str]) — фильтр по service_key конюшен (OR).
- `role` (list[str]) — фильтр по `user_scopes.scope_name` (OR).
- Комбинации фильтров — логика AND.

**Обоснование:**
- Закрывает use case: «найти всех пользователей конюшни с ролью X для отправки уведомления».
- Потенциал расширения: новые фильтры добавляются как необязательные query-параметры.

### 6. HTTP-клиенты в микросервисах

**Решение:** `aiohttp`-клиенты в папке `clients/` каждого микросервиса, аналогично NATS-клиентам в backend.

**Обоснование:**
- Единый паттерн: клиенты изолированы от core-логики.
- `aiohttp` — стандартная async-библиотека для Python.
- Обработка ошибок: вместо 502 возвращается 500 с описанием проблемы.

### 7. ENV-переменные

**Решение:**
- Backend: `SERVICE_KEY` — рандомная строка в `.env` / `.env.example`.
- Микросервисы: `MAIN_BACKEND_URL`, `MAIN_BACKEND_SERVICE_KEY`.
- Будущие межсервисные URL: `NOTIFICATION_SERVICE_URL`, `EMAIL_SERVICE_URL` и т.д.

**Обоснование:**
- Никакого хардкода ключей или адресов.
- Каждый сервис получает только те ENV, которые ему нужны.

## Risks / Trade-offs

- **[Shared secret]** → Значение `SERVICE_KEY` одинаково для всех сервисов. Компрометация одного сервиса означает компрометацию всех сервисных эндпоинтов.
  - Mitigation: сервисы работают только в локальной сети; rotation ключа через ENV.
- **[500 вместо 502]** → Пользователь не получает точного HTTP-кода от микросервиса, но получает описание проблемы.
  - Mitigation: логирование деталей на стороне backend; в будущем — retry/circuit-breaker.
- **[Single endpoint]** → `GET /api/service/users` — единственный сервисный эндпоинт. Расширение — будущие итерации.
  - Mitigation: архитектура (префикс, dependency) готова к расширению.

## Ownership и порядок реализации

- **BE-1 (Backend-агент):** все изменения в `services/backend` — middleware, dependency, роутер, репозиторий, пагинация, ENV.
- **Микросервисы (Backend-агент по аналогии):** HTTP-клиенты, ENV.
- **Quality Gate:** один общий запуск после завершения всех deliverables.
- **OpenSpec sync:** delta specs → main specs → archive.
