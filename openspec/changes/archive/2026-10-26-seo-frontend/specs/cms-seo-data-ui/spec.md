# Delta — данные SEO в CMS

## Purpose

Просмотр сохранённых страниц и поисковых запросов конюшни и управление исключениями нормализации страниц из защищённого административного раздела SEO в CMS.

## ADDED Requirements

### Requirement: Матрица доступа потребляемого API
CMS SHALL использовать только существующие backend операции по матрице ниже, без прямого обращения к seo-service. GET — существующие исключения из Public Read для внутренних SEO-данных и настроек, запись — Protected Write. Tenant MUST определяться сессией без selector из браузера; SUPERUSER/DEVELOPER без ADMIN MUST NOT заменять ADMIN.

#### Scenario: Контракт восьми операций
- **WHEN** любая потребляемая операция проверяется без сессии, с ADMIN и с другими ролями
- **THEN** ожидаются статусы матрицы; API-boundary тесты покрывают все строки (UT-SEO-01..04), UI — UT-SEO-11,15..16 и M01..M03,M09..M10

| method | path | access class | roles | expected without auth | expected with auth |
|---|---|---|---|---|---|
| GET | `/api/seo/pages` | Protected GET exception | только ADMIN | 401 | 200; без ADMIN 403; невалидный query 400; downstream error 502 |
| GET | `/api/seo/search-queries` | Protected GET exception | только ADMIN | 401 | 200; без ADMIN 403; невалидный query 400; downstream error 502 |
| GET | `/api/seo/page-normalization/blacklisted-hashes` | Protected GET exception | только ADMIN | 401 | 200; без ADMIN 403; downstream error 502 |
| GET | `/api/seo/page-normalization/blacklisted-query-params` | Protected GET exception | только ADMIN | 401 | 200; без ADMIN 403; downstream error 502 |
| POST | `/api/seo/page-normalization/blacklisted-hashes` | Protected Write | только ADMIN | 401 | 201; без ADMIN 403; значение/тело 400; дубль 409; downstream error 502 |

### Requirement: Таблицы сохранённых SEO-данных
CMS SHALL показывать страницы и запросы своей конюшни таблицами на одноимённых вкладках `/seo`. Колонки MUST содержать значение и дату создания; чтение MUST использовать существующие GET backend с ответом `items/total`. Редактирование, создание и удаление страниц и запросов MUST NOT предлагаться.

#### Scenario: Данные и состояния
- **WHEN** ADMIN открывает вкладку «Страницы» или «Запросы»
- **THEN** загружается соответствующий список, показаны значение и дата, UUID служит стабильным ключом; loading, пустой ответ и ошибка с повтором различимы, ошибка не выдаётся за пустой успех

#### Scenario: Длинное значение
- **WHEN** страница или запрос содержит длинное значение
- **THEN** оно не перекрывает дату/контролы, полное значение доступно через подсказку; путь страницы не превращается в выдуманный URL домена

### Requirement: Серверные фильтр и сортировка в заголовке
Фильтрация и сортировка SHALL находиться исключительно в заголовке колонки значения. Фильтр MUST передавать `search` с debounce 300 мс и trim; очистка убирает параметр. Сортировка MUST использовать только `page/-page` или `query/-query`, очистка убирает `ordering`. По датам/UUID фильтра и сортировки MUST NOT быть.

#### Scenario: Поиск и очистка
- **WHEN** ADMIN вводит поисковую подстроку в заголовке, затем очищает фильтр
- **THEN** запрос после debounce содержит search и offset=0; очистка выполняется сразу с offset=0 без search, символы %, _ и обратная косая черта не превращаются клиентом в шаблон

#### Scenario: Сортировка и её сброс
- **WHEN** ADMIN переключает сортировку значения по возрастанию, убыванию и сбрасывает её
- **THEN** API получает соответственно разрешённое поле, поле с минусом и отсутствие ordering; каждый переход сбрасывает offset=0, индикатор соответствует запросу

### Requirement: Верхняя пагинация таблиц
Над каждой таблицей SHALL быть только пагинация, без отдельных полей поиска, сортировки или панели фильтров. Пагинация MUST передавать серверу limit/offset, использовать total из ответа и сбрасывать offset при смене размера страницы. Состояния двух таблиц MUST быть независимы; устаревший ответ MUST NOT заменять актуальную выборку.

#### Scenario: Переходы страниц
- **WHEN** ADMIN открывает таблицу, переходит дальше и меняет размер страницы
- **THEN** начальные limit=25, offset=0; следующая страница имеет offset=25, изменение размера сбрасывает offset=0; page/pageSize в API не передаются

#### Scenario: Изоляция и гонка
- **WHEN** ADMIN переключает вкладки с разными фильтрами либо старый запрос завершается после нового
- **THEN** фильтры/сортировка/offset каждой таблицы сохраняются в пределах посещения `/seo`, отображается только актуальный результат соответствующей таблицы

### Requirement: Модалка нормализации
На «Страницах» SHALL быть кнопка «Нормализация» вне панели пагинации таблицы. Она MUST открывать модалку с вкладками «Хеш» (по умолчанию) и «Параметры», строкой input с плюсом и компактным списком с иконкой удаления справа. Списки MUST пагинироваться локально после загрузки полного ответа GET, без выдуманных API-параметров.

#### Scenario: Открытие и переключение
- **WHEN** ADMIN открывает нормализацию, меняет вкладку или страницу списка
- **THEN** показана нужная коллекция, локальная пагинация использует размер 10 и число загруженных элементов; при переключении коллекции страница сбрасывается, данные не смешиваются; loading/empty/error с повтором различимы

#### Scenario: Повторное открытие
- **WHEN** ADMIN закрывает и снова открывает модалку
- **THEN** активен «Хеш», первая страница, пустой input, нет старого подтверждения; список загружается заново, поздний ответ закрытого окна не меняет новое

### Requirement: Добавление правила нормализации
Плюс и Enter SHALL добавлять значение через POST `{"value": string}` с клиентской валидацией до запроса. После trim значение MUST быть непустым, ≤255 Unicode-символов, без пробельных/управляющих символов и `#`; у хеша удаляется один ведущий `#`, у параметра также запрещены `&`, `=`, `?`. Регистр MUST сохраняться.

#### Scenario: Успешное добавление
- **WHEN** ADMIN добавляет `" #top "` в «Хеш» или `" utm_source "` в «Параметры»
- **THEN** отправляется одно корректное значение без внешних пробелов, серверный успех 201 очищает input и обновляет коллекцию с первой страницы; сохранённые страницы и запросы не изменяются

#### Scenario: Невалидное значение и дубль
- **WHEN** введено пустое/невалидное значение либо backend отвечает 400 или 409
- **THEN** невалидный ввод блокируется до API, при backend-ошибке input и список сохраняются с безопасным сообщением, ложный успех не отображается

#### Scenario: Допустимый хеш
- **WHEN** вводится `!/catalog?x=1` в «Хеш»
- **THEN** валидация допускает значение, запреты query-параметров на него не переносятся

### Requirement: Удаление правила с отдельным подтверждением
Иконка удаления SHALL открывать отдельное модальное подтверждение с выбранным значением, не отправляя DELETE сразу. Отмена MUST сохранять список. Успешный 204 MUST обновлять коллекцию и корректировать страницу, если удалён её последний элемент; ошибка MUST NOT давать ложный успех.

#### Scenario: Подтверждение и отмена
- **WHEN** ADMIN нажимает иконку удаления, затем отменяет или подтверждает
- **THEN** отмена не делает запрос; подтверждение отправляет один DELETE по UUID и типу выбранного элемента, после 204 закрывается только подтверждение, основная модалка остаётся

#### Scenario: Уже удалённый или чужой элемент
- **WHEN** DELETE получает 404
- **THEN** показывается сообщение об отсутствии элемента, список перечитывается и пагинация корректируется, успешное удаление не объявляется

#### Scenario: Ошибка удаления
- **WHEN** DELETE завершается 400, 403, 502 или сетевой ошибкой
- **THEN** подтверждение остаётся с ошибкой и выбранным элементом, input/коллекция/страница не теряются, повтор не происходит автоматически

### Requirement: Границы доступа и безопасность мутаций
Чтение и мутации новых SEO-вкладок SHALL требовать актуальный ADMIN без наследования ролей. Действия MUST иметь guards перед вызовом API и синхронную защиту повторного submit. Во время mutation MUST блокироваться конкурирующие действия и закрытие/смена контекста. Обработка 401 MUST следовать общему auth client; 403 MUST давать видимый отказ.

#### Scenario: Anonymous для всех операций
- **WHEN** API-boundary тест вызывает любую из восьми операций без действующей сессии и сервер отвечает 401
- **THEN** используется штатный refresh/login flow, успех не имитируется; прямой anonymous заход `/seo` блокирует protected layout

#### Scenario: Authenticated ADMIN и другие роли
- **WHEN** пользователь имеет ADMIN либо только SUPERUSER/DEVELOPER/другие роли
- **THEN** ADMIN видит новые вкладки и получает результаты по access matrix; без ADMIN UI запрещён, чтение/мутации через hooks не отправляются, backend 403 не становится успешным состоянием

#### Scenario: Чужой tenant
- **WHEN** ADMIN удаляет известный UUID чужой конюшни в контрактном тесте
- **THEN** ожидается 404 по матрице; UI не принимает selector и не пытается обходить backend через peer

#### Scenario: Повтор и отзыв прав
- **WHEN** пользователь дважды нажимает плюс/подтверждение либо ADMIN отозван после показа действия
- **THEN** в pending отправляется не более одной mutation, при отзыве прав hook не делает вызов; попытка открытия mutation UI без разрешения отклоняется

#### Scenario: Ошибка перечитывания после успеха
- **WHEN** POST/DELETE успешен, но последующий GET не удался
- **THEN** UI различает завершённую mutation и ошибку обновления, предлагает повтор GET и не повторяет POST/DELETE автоматически

### Requirement: Desktop и доступность
Новые таблицы и модалки SHALL помещаться на CMS desktop 1366×768 без overlap. Управление MUST быть доступно с клавиатуры, icon-only кнопки иметь доступные имена, диалоги — заголовки и корректный возврат фокуса. Mobile/tablet MUST NOT входить в реализацию и QA этого изменения.

#### Scenario: Клавиатура и вложенное подтверждение
- **WHEN** ADMIN клавиатурой переключает вкладки, открывает фильтр/нормализацию/подтверждение и закрывает их
- **THEN** фокус виден, после подтверждения возвращается в основную модалку, после её закрытия — на кнопку; длинные строки не перекрывают иконки, input, пагинацию и диалоги на 1366×768
