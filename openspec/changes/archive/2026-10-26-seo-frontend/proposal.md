# Proposal — SEO frontend

## Why

В CMS уже есть раздел SEO и API задачи 099 для страниц, поисковых запросов и правил нормализации, но интерфейс использует только интеграцию Яндекса. Задача [100](<../../../docs/tasks/100_seo_frontend.md>) добавляет просмотр данных и управление правилами без изменения backend.

## What Changes

- Дополнить `/seo` вкладками «Страницы» и «Запросы», сохранив Метрику по умолчанию и заглушку Вебмастера.
- Показать таблицы значений и дат создания; фильтр и сортировку разместить исключительно в заголовке колонки значения, над таблицей — только пагинацию.
- На вкладке «Страницы» добавить отдельное действие «Нормализация» в строке навигации вкладок, не в панели пагинации. Модалка содержит «Хеш»/«Параметры», input с плюсом, компактный пагинированный список и иконку удаления с отдельным модальным подтверждением.
- Использовать серверные поиск/сортировку/пагинацию страниц и запросов. Для правил сделать **локальную пагинацию полного списка**: API возвращает весь список и не поддерживает `limit/offset`.
- Сохранить ADMIN-only, guards и обработку ошибок через существующий API client. Поддерживаемая CMS-платформа — desktop 1366×768; заменить устаревшее мобильное требование SEO-вкладок.
- Добавить изолированные frontend-тесты и отдельную browser QA; реализация начинается только после approval пользователя.

## Capabilities

### New Capabilities

- `cms-seo-data-ui`: просмотр SEO-данных своей конюшни и управление нормализацией в CMS через существующий admin API.

### Modified Capabilities

- `cms-seo-yandex-ui`: требование «Страница SEO с вкладками» — четыре вкладки, запрет запросов также к `/api/seo/**` без ADMIN, desktop-only вместо прежнего mobile/tablet сценария. Остальные Яндекс-сценарии не меняются.

## Impact

Изменяется только `services/frontend`: `src/types/api/seo.ts`, `src/api/seo.ts`, новые модули внутри существующей feature `src/features/seo`, локальный registry прав и интеграция в `SeoPage`. Общие таблица/пагинатор, API client, публичные сайты, backend и seo-service — read-only контекст. Новые зависимости, миграции и NATS не требуются.

Потребляются существующие операции (без изменения их контрактов):
- `GET /api/seo/pages`, `GET /api/seo/search-queries`;
- `GET`, `POST` для `/api/seo/page-normalization/blacklisted-hashes` и `/api/seo/page-normalization/blacklisted-query-params`;
- `DELETE` тех же коллекций с `/{item_id}`.

Полная access matrix этих восьми операций находится в [delta spec](<specs/cms-seo-data-ui/spec.md#access-matrix>) и [design](<design.md#access-matrix>). Все GET — существующие Protected GET exceptions: внутренние административные данные конюшни, не consumer Public Read. Запись — Protected Write, только ADMIN. PATCH существует, но UI редактирования не входит в запрос; resolve через CMS отсутствует и не добавляется. Нет массовых операций, статистики SEO, сортировки/фильтра по датам и ретроактивной перенормализации страниц.

Approval включает предложенные решения: локальную пагинацию правил; колонки «Страница/Запрос» + «Создано»; поиск/сортировку только по значению; размещение «Нормализация» вне панели пагинации. Детали и ограничения — в design.
