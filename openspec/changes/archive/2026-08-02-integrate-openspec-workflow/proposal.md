## Почему

Текущий процесс EqSiteCMS опирается на планы в `docs/plans` и не имеет единого машиночитаемого жизненного цикла изменений, хотя OpenSpec уже установлен. Нужно сделать OpenSpec каноническим источником планирования, сохранив Router-first маршрутизацию, обязательную пользовательскую проверку и профильную мультиагентную реализацию.

## Что изменяется

- Новые запросы принимаются из `docs/tasks`; `docs/plans` становится legacy/read-only источником исторического контекста.
- Для каждой новой работы сначала создаются русскоязычные OpenSpec proposal, design, delta specs и tasks; `explore` используется только по явному запросу.
- Между планированием и реализацией вводится обязательная пауза для проверки артефактов пользователем и разрешения открытых вопросов.
- Реализация запускается только после подтверждения, всегда маршрутизируется профильным агентам и делится на ограниченные независимые задачи для субагентов.
- После всех реализационных задач проводится один общий Quality Gate с доработкой замечаний, синхронизацией specs и архивированием change.
- `AGENTS.md` остаётся главным источником агентных правил; корневой `CLAUDE.md` становится коротким указателем на него, а `agents/*` фиксируют обязанности профилей в новом процессе.
- Для 23 исторических задач создаётся evidence-based, capability-oriented backfill спецификаций с полной трассировкой; неподтверждённое или расходящееся поведение оформляется как gap, а не выдаётся за реализованный контракт.
- На всех стадиях сохраняется API policy: `GET` — Public Read, `POST`/`PATCH`/`DELETE` — Protected Write; исключения документируются с причиной, статусами и тестами.

## Возможности

### Новые возможности

- `openspec-workflow`: Канонический жизненный цикл OpenSpec, русскоязычные артефакты, пользовательский approval gate, профильная мультиагентная реализация и единый Quality Gate.
- `historical-spec-backfill`: Инвентаризация 23 исторических задач, evidence-based трассировка до capability specs, пакетная синхронизация и регистрация gaps.
- `api-access-governance`: Сквозное сохранение и проверка Public Read / Protected Write контракта в proposal, specs, реализации и Quality Gate.

### Изменяемые возможности

Отсутствуют: каталог `openspec/specs` пока пуст.

## Влияние

Изменяются только репозиторные инструкции, конфигурация OpenSpec и документационные артефакты: `AGENTS.md`, `CLAUDE.md`, `agents/*.md`, `openspec/config.yaml`, `openspec/changes/**`, `openspec/specs/**`, итоговый отчёт `docs/reports/023_openspec_integration-review.md`. Runtime-код `services/backend`, `services/frontend`, `services/site-ad`, API, БД и инфраструктура этой миграцией не изменяются. Существующий dirty worktree и артефакты задачи 022 должны быть сохранены без смешивания с реализацией 023.
