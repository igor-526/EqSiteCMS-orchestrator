## ADDED Requirements

### Requirement: Полная трассировка исторических задач
Backfill SHALL содержать manifest всех 23 файлов `docs/tasks/001_*.md`–`023_*.md`, где каждая задача связана с capability, сервисом, планами, reports, evidence и состоянием реализации.

#### Scenario: Проверка полноты manifest
- **WHEN** подготовлена инвентаризация backfill
- **THEN** она содержит ровно 23 уникальных номера без пропусков и для каждого номера указывает целевую capability либо зарегистрированный gap

### Requirement: Evidence-based контракт
Исторический spec MUST описывать подтверждённое текущее поведение по фактическому коду и Quality Gate reports; текст task или legacy plan сам по себе MUST NOT считаться доказательством реализации.

#### Scenario: Task и код совпадают
- **WHEN** требование подтверждено кодом, тестами и применимым report
- **THEN** manifest помечает его `implemented`, а контракт включается в capability spec со ссылками на evidence

#### Scenario: Task не подтверждён кодом
- **WHEN** реализацию нельзя доказать либо фактическое поведение расходится с task
- **THEN** manifest использует `partial`, `superseded` или `unknown` и регистрирует gap или отдельный будущий change без ложной синхронизации

### Requirement: Группировка по возможностям
Исторические требования SHALL группироваться в main specs по устойчивым бизнес- и процессным capabilities, а не механически по одному spec на номер задачи.

#### Scenario: Несколько задач развивают одну возможность
- **WHEN** несколько исторических задач относятся к одной capability
- **THEN** их подтверждённые требования объединяются в один непротиворечивый spec с трассировкой каждого номера

### Requirement: Пакетная профильная обработка
Backfill SHALL выполняться ограниченными пакетами по сервису и capability с профильными субагентами; один субагент MUST NOT получать все 23 задачи, а один spec MUST иметь единственного владельца записи.

#### Scenario: Формируются пакеты backfill
- **WHEN** manifest распределён по backend, frontend, site-consumer и process capabilities
- **THEN** Router выдаёт независимые пакеты профильным субагентам в пределах их контекста и назначает отдельную итоговую сверку

### Requirement: Валидация и идемпотентная синхронизация
Каждый пакет delta specs SHALL проходить OpenSpec validation и review до синхронизации; повторная синхронизация без новых изменений MUST не менять main specs.

#### Scenario: Пакет готов к main specs
- **WHEN** evidence проверен, дубли устранены и validation успешна
- **THEN** delta specs синхронизируются в `openspec/specs`, повторная проверка подтверждает отсутствие незапланированных изменений, а change архивируется

### Requirement: Итоговая проверка покрытия
Финальный Quality Gate SHALL проверять покрытие 23/23, отсутствие конфликтующих или дублированных требований, валидность main specs и наличие явных gaps для неподтверждённого поведения.

#### Scenario: Backfill завершён
- **WHEN** все capability-пакеты обработаны
- **THEN** итоговый report перечисляет покрытие каждой задачи, результаты validation, gaps и вердикт готовности specs
