## Контекст

EqSiteCMS использует Router-first модель: корневой агент только маршрутизирует работу Planner, Backend, Frontend, Site Consumer и Quality Gate. Исторически Planner создавал планы в `docs/plans`, а исполнители отмечали Markdown-чеклисты. OpenSpec 1.5.0 уже установлен и исправен, но активных changes и main specs нет; `openspec/config.yaml` задаёт только `schema: spec-driven`.

Миграция охватывает репозиторные инструкции и документацию, не runtime-сервисы. В рабочем дереве присутствуют незавершённые пользовательские изменения задачи 022, поэтому реализация обязана работать по точному manifest затрагиваемых файлов и не включать посторонний diff.

## Цели / Не-цели

**Цели:**

- Сделать OpenSpec change каноническим планом после входного задания из `docs/tasks`.
- Сохранить Router-first, профильных агентов, обязательных субагентов при реализации и anti-awaiting правила.
- Обеспечить русскоязычные, проверяемые и apply-ready артефакты до начала реализации.
- Ввести обязательный пользовательский approval gate после proposal-этапа.
- Перенести подтверждённые контракты 23 исторических задач в capability-oriented main specs с трассировкой.
- Сохранить сквозную API access policy и единый итоговый Quality Gate.

**Не-цели:**

- Изменение backend, frontend, site-ad, API, схемы БД или инфраструктуры.
- Автоматическое признание старой задачи реализованной только по её формулировке.
- Создание новых реализационных планов в `docs/plans`.
- Одновременное редактирование одного spec несколькими субагентами.

## Решения

### 1. Источники истины разделяются по назначению

`docs/tasks` хранит исходный пользовательский запрос, OpenSpec change — актуальные proposal/design/specs/tasks, `openspec/specs` — синхронизированный контракт текущего поведения, `docs/reports` — доказательства Quality Gate. `docs/plans` остаётся legacy/read-only контекстом.

Альтернатива — продолжить дублировать планы в `docs/plans` — отклонена, потому что создаёт два изменяемых источника реализации.

### 2. Корневые инструкции имеют один источник истины

`AGENTS.md` содержит полный workflow. `CLAUDE.md` создаётся как короткий указатель, требующий прочитать и соблюдать `AGENTS.md`; копия правил в нём запрещена. Профильные `agents/*.md` содержат только общие обязательства и специфику профиля.

Альтернатива — синхронизировать два полных корневых файла — отклонена из-за риска расхождения.

### 3. Жизненный цикл имеет явный approval gate

Последовательность новой задачи:

1. Router читает входной файл из `docs/tasks` и делегирует планирование через `openspec-propose`.
2. Planner создаёт все apply-required артефакты на русском и выполняет status/validate.
3. Router показывает пользователю proposal, design, specs, tasks и открытые вопросы.
4. До явного подтверждения запрещены `apply`, кодовые изменения и передача реализационных задач.
5. После подтверждения Router делит tasks по зонам и назначает профильных субагентов.
6. После завершения всех зон запускается один общий Quality Gate; findings возвращаются соответствующим исполнителям.
7. После успешного повторного Quality Gate delta specs синхронизируются, change архивируется.

`explore` не является автоматической стадией и запускается только по явному запросу.

### 4. Реализация делится по ownership и контекстному бюджету

Router не пишет код и не отдаёт весь change одному исполнителю. Задача для субагента содержит завершённый deliverable, связанные файлы, access policy и команду продолжать до результата без ожидания дополнительных инструкций при отсутствии блокера. Один файл или одна tightly-coupled зона имеет одного владельца; пересекающиеся записи выполняются последовательно.

Для этой миграции ownership: общие инструкции и OpenSpec config — Backend/tooling-профиль; frontend-инструкции — Frontend; consumer-инструкции — Site Consumer; итоговая проверка — Quality Gate.

### 5. Backfill строится от capabilities и evidence

Сначала создаётся manifest 23/23 задач. Для каждой задачи фиксируются связанные plans/reports, затронутый сервис, capability, состояние `implemented`, `partial`, `superseded` или `unknown`, а также ссылки на evidence в фактическом коде и отчётах.

Спеки группируются по бизнес-возможностям, а не механически по номеру задачи. Пакеты распределяются профильным субагентам; итоговый reviewer устраняет дубли и противоречия. `partial`/`unknown` становятся зарегистрированными gaps или отдельными будущими changes. Backfill changes валидируются, синхронизируются и архивируются пакетами.

### 6. API access policy является обязательным сквозным контрактом

Каждый затрагивающий endpoint change содержит матрицу `method | path | access class | roles | without auth | with auth`. По умолчанию `GET` публичен без cookie, а `POST`/`PATCH`/`DELETE` требуют auth и права. Исключение содержит причину, ожидаемые статусы anonymous/authenticated и тесты. Planner включает контракт, профильный агент реализует, Quality Gate проверяет обе группы сценариев.

### 7. Русский язык и валидация контролируются до apply

Proposal, design, specs и tasks пишутся на русском; технические идентификаторы, пути, команды и нормативные ключевые слова формата OpenSpec могут оставаться латинскими. Перед approval выполняются `openspec status` и `openspec validate --change ...`. После реализации валидация повторяется перед sync/archive.

## Риски / Компромиссы

- [Старые задачи описывают намерение, отличающееся от кода] → Требовать evidence и состояние трассировки; не синхронизировать неподтверждённый контракт.
- [23 задачи превышают контекст одного агента] → Пакеты по capabilities и сервисам, ограниченный manifest на субагента, отдельная сверка полноты 23/23.
- [Параллельные агенты конфликтуют в specs] → Единственный владелец файла и последовательное слияние пересекающихся capabilities.
- [Дублирование AGENTS/CLAUDE расходится] → CLAUDE только указывает на AGENTS.
- [OpenSpec правила конфликтуют с профильными инструкциями] → AGENTS задаёт оркестрацию, OpenSpec — состояние change; противоречие является блокером и выносится пользователю.
- [Dirty worktree смешивается с задачей] → До каждой фазы фиксировать status и проверять path-scoped diff.
- [Один финальный QG делает обратную связь поздней] → Разрешить локальную самопроверку пакетов, но формальный вердикт и report остаются едиными после всех задач.

## План миграции

1. Обновить агентные инструкции и OpenSpec config по утверждённым артефактам.
2. Выполнить документационный Quality Gate workflow-слоя.
3. Построить и проверить manifest исторических задач.
4. Создать, валидировать и синхронизировать capability-пакеты backfill.
5. Провести единый финальный Quality Gate, устранить findings и повторить проверку.
6. Синхронизировать текущие delta specs и архивировать change после успешного verdict.

Rollback документационной миграции выполняется обратным применением только path-scoped diff задачи 023; исторические пользовательские изменения и runtime-код не затрагиваются. Уже синхронизированные specs откатываются отдельным OpenSpec change, а не ручным удалением истории.

## Открытые вопросы

Блокирующих вопросов нет. Утверждены: `docs/tasks` как input, `docs/plans` как legacy/read-only, короткий `CLAUDE.md`, evidence-based capability backfill и обязательная пауза до реализации.
