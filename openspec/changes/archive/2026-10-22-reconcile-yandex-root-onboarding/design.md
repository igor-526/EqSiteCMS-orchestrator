## Goals / Non-Goals

**Цели:** достоверный каталог и быстрый старт для двух сервисов; безопасный инвентарь root env; различение зарегистрировано / есть команда / проверено runtime / разрешён release; явные deferred gaps.

## Decisions

### 1. Только два документа при будущем apply

Единый документационный владелец меняет [SERVICES.md](<../../../SERVICES.md>) и [README.md](<../../../README.md>) последовательно. Альтернатива — исправить Make/registry одновременно — отклонена: это отдельное tooling/runtime решение без approval. В каталоге добавить строки и краткие разделы ролей/ресурсов, не детальные функциональные обещания. В README дать ссылку на каталог вместо дублирования бизнес-описания.

Точечно убрать из VK-ограничений только неверное blanket-обобщение, будто root `test/lint/format` ограничены четырьмя сервисами: явно направить к текущей матрице commands. Остальной VK-техдолг, его manifest/deployment статус и другие сервисы не аудитировать и не исправлять в этом change.

### 2. Матрица документируемых команд

| Поверхность | Yandex | Metrica | Граница утверждения |
|---|---|---|---|

| Make сборка | `make yandex-build`, `make yandex-build-nc` | `make ya-metrica-build`, `make ya-metrica-build-nc` | Индивидуальная сборка, не core release |

| Aggregate build | Не включён | Не включён | Сохраняются четыре core-сервиса |
| Core `check` | Не подтверждён этим исследованием | Не подтверждён этим исследованием | Убрать ложный alias claim; готовность gate не обещать |

Состав остальных сервисов в root quality recipes можно обозначить как «расширенный набор по Make», не превращая docs-only в их onboarding. `make infra` поднимает все infra services: это не изолированная команда для двух DB. Не рекомендовать её как безопасный узкий smoke. Сеть `eqsitecms_network` должна существовать отдельно; service Compose не содержит DB/dependencies и не гарантирует их готовность. Миграционные контейнеры one-shot; здесь не обещается барьер app-start после миграции.

### 3. Безопасный env и resource inventory

В [SERVICES.md](<../../../SERVICES.md>) поместить следующую root-only матрицу, без реальных значений. В README — короткое объяснение двух независимых контуров env и ссылка. Обобщённый приоритет `.env.local/.env.prod` из frontend не распространять на сервисы Яндекса: их Compose подключает только обязательный service `.env`.

| Переменные/файлы | Назначение | Безопасное представление |
|---|---|---|
| `EXPOSE_YANDEX_SERVICE_PORT`, `EXPOSE_YA_METRICA_SERVICE_PORT` | Host → app `8000` | `<выбранный свободный локальный порт>`; значения не обнаруживались |

| Service env | Обязательные `services/<service>/.env` в обоих service Compose и Make `--env-file` | Пути по шаблону, содержимое не читать; полный app inventory — service-backfill |
| Infra env | Make `infra` использует отдельный `.docker-compose/.env` | Локальный файл не читать; DB placeholders должны согласовываться оператором |

Пароли и app credentials не переносятся в tracked файлы. `SKIP_MIGRATIONS` читается shell контейнера через `$$`, а не является доказанным обязательным app setting. `.env.example` сервисов в этом unit не инспектировались: не обещать их полноту или генерировать новые. Не запускать `docker compose config`, который может раскрыть интерполированные secrets.

Ресурсы: app containers `eqsitecms-yandex-service`, `eqsitecms-ya-metrica-service`; migration containers с суффиксом `-migration`; DB containers `eqsitecms-db-yandex`, `eqsitecms-db-ya-metrica`, keys `db-yandex`, `db-ya-metrica`; logical volumes `eqsitecms_yandex_db_data`, `eqsitecms_ya_metrica_db_data`. Service Compose projects из Make: `eqsitecms-yandex`, `eqsitecms-ya-metrica`; infra — `eqsitecms-infra`.

### 4. Access applicability и безопасная граница

Endpoint changes отсутствуют; HTTP method/path/access/roles/status matrix — **неприменимо**, новые строки endpoints не создаются. Anonymous/authenticated HTTP tests — **неприменимо**: документация не является доказательством доступа. Нельзя объявлять маршруты сервисов Public Read или разрешёнными private исключениями по факту их существования.

Compose публикует app `8000` и DB `5432` на host через переменные без явного loopback bind. Каталог обязан предупредить об exposure и запретить трактовать dev Compose как разрешение публичного/production использования. Документирование не исправляет auth/token gaps. Решения о сетевом ограничении и access требуют отдельного service/access change с полной матрицей и anonymous/authenticated тестами.

## Execution units

Deliverable D-DOC: Backend — единый ownership двух root документов; профиль корневой технической документации, без runtime edits. Deliverable D-QG: Quality Gate — [format report](<../../../docs/reports/reconcile-yandex-root-onboarding/format.md>), evidence рядом и уже существующая isolation `/srv/eqSiteCMS-qg-format-cxkmcu2n`; root docs/specs и код не исправляет. PLAN-R4 делит продолжение blocked QG-FORMAT на bounded dependency PREP units и RUN; PLAN-R5 добавляет ровно один metadata-only PREP-SAFETY для остатка partial/BLOCKED PREP, не новую install/audit цепочку. Это один ownership с последовательными сессиями, не скрытая работа Router. Каждый unit отмечает только свои фактически выполненные IDs в [tasks](<tasks.md>); PLAN-R5 исторически передавал PREP `.3`/`.V` PREP-SAFETY, но тот завершён BLOCKED без их закрытия. Split PREP → RUN принят Router; отдельное approval для безопасной bounded установки зависимостей внутри existing isolation не требуется. Семь Python-групп заранее вынесены из первого PREP, чтобы одна агентная сессия содержала только одну install-группу одного nested проекта и <=8–12 существенных действий. PREP — шесть checklist-пунктов, PY units — по три (каждый <=8–12 действий), RUN — семь и одна root verification-группа. При дополнительном превышении бюджета — безопасный checkpoint, partial handoff и split до продолжения, не больше групп в текущей сессии. Router читает handoff перед следующим unit. Предыдущие completed review tasks не означают PASS; исторические failed/blocked/not-run не стираются. PLAN-R5 — только design/tasks process и status/strict/scoped check, без installs, QG runs, root docs/functional specs/proposal/report edits; остановка на handoff, без нового ожидания пользовательских инструкций. Один только scoped comparison exit 0 недостаточен. Не утверждать whole-checkout preservation=true, не исправлять historical preservation=false. Passed — только bounded safety disposition, не FORMAT PASS.
- `BLOCKED`, если matching source/version, порядок эффектов или существенная inherited-env/cache write-ветка не обоснованы targeted evidence, обнаружены tracked writes/security issue либо реальный риск не снят в границах unit. Назвать точную недостающую информацию/ветку/риск; отсутствие исторического baseline не заполнять вымышленным снимком, настоящий snapshot не выдавать за pre-call. Не чинить и не удалять возможные artifacts. PY1 остаётся gated, не добавляется новая audit-цепочка.

**История, checkbox и переход.** Создать только новые `format-prep-safety-*` disposition, ledger overlay и handoff в прежней report-зоне; overlay ссылается на неизменный [PREP ledger](<../../../docs/reports/reconcile-yandex-root-onboarding/format-prep-readiness-ledger.json>) и сохраняет один install, все прежние exits/incidents/blocked assertions. PREP `.3` и `.V` закрываются по отдельности лишь после фактической проверки соответствующих cache/write-destination и scoped root/nested diff/own-write обязательств на имеющемся evidence и passed disposition; недоказанный пункт остаётся открытым. ## Risks / Trade-offs

- Наблюдение ошибочно становится нормой → добавляем документальные требования, не меняем существующий core gate; R-G1 остаётся deferred.
- Список команд принимают за эксплуатационную гарантию → явно разделяем наличие рецепта, registry, запуск и release.
- Каталог становится endpoint backfill → только минимальные роли и ссылка на отдельный service-backfill, без access-исключений.
- Другие устаревшие строки root docs провоцируют аудит всего репозитория → правим только пересечение двух сервисов/команд; прочее не включаем автоматически.
