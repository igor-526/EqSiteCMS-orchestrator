# Spec Delta

## MODIFIED Requirements

### Requirement: Пункт меню SEO

Боковое меню CMS MUST содержать пункт «SEO» с иконкой `RiseOutlined` из `@ant-design/icons`, ведущий на `/seo`. Пункт MUST быть видим только пользователям с существующей ролью `SEO`; при открытом `/seo` пункт активен, а заголовок страницы — «SEO». Локальный permission adapter MUST проверять SEO без наследования ADMIN/SUPERUSER/DEVELOPER.

#### Scenario: Пользователь с ролью ADMIN
- **WHEN** в меню входит пользователь с ролью `SEO`
- **THEN** пункт «SEO» с иконкой виден, клик открывает `/seo`, пункт выделен как активный

#### Scenario: Пользователь без роли ADMIN
- **WHEN** в меню входит пользователь без роли SEO (включая SUPERUSER, DEVELOPER, USER_MANAGER и отсутствие ролей)
- **THEN** пункт «SEO» не отображается

### Requirement: Страница SEO с вкладками

`/seo` MUST быть Protected Admin UI (anonymous → `/login`) с вкладками CMS «Яндекс.Метрика» (по умолчанию), «Яндекс.Вебмастер», «Страницы» и «Запросы». Без SEO MUST отображаться доступное forbidden-состояние без запросов `/api/yandex/**` и `/api/seo/**`. Вкладки MUST сохранять доступность клавиатурой и связи tab/panel на desktop 1366×768; tablet/mobile не входят в поддержку CMS.

#### Scenario: Открытие раздела
- **WHEN** пользователь с ролью SEO открывает `/seo`
- **THEN** видны четыре вкладки в стиле остальных CMS-страниц, активна «Яндекс.Метрика», существующий сценарий Метрики сохранён

#### Scenario: Прямой заход без роли ADMIN
- **WHEN** пользователь без роли SEO (включая SUPERUSER/DEVELOPER) открывает `/seo` по URL
- **THEN** отображается forbidden-состояние, доступное для фокуса и keyboard-scroll, запросы к `/api/yandex/**` и `/api/seo/**` не отправляются

#### Scenario: Анонимный пользователь
- **WHEN** пользователь без сессии открывает `/seo`
- **THEN** выполняется переход на `/login`, защищённый интерфейс не доступен

#### Scenario: Доступные мобильные вкладки

Историческое имя сценария сохранено для delta merge; обновлённый сценарий заменяет прежнюю мобильную гарантию на desktop-контракт.

- **WHEN** SEO переключает вкладки мышью и клавиатурой на desktop 1366×768
- **THEN** четыре вкладки достижимы и читаемы без overlap и горизонтального скролла страницы; tablist содержит корректные доступные элементы, tab/panel связаны, `aria-required-children` не возникает; mobile/tablet отдельно не реализуются и не проверяются

### Requirement: Шаг выбора аккаунта Яндекса

Шаг 1 MUST загружать `GET /api/yandex/accounts` с limit/offset и «Показать ещё» при `items < total`, показывать loading/error и последним действием «Добавить аккаунт». Аккаунт MUST быть компактной строкой с именем, логином и email; основная область активируется кликом, Enter или Space, без отдельного «Выбрать». При пустом списке MUST быть только одна верхняя подсказка, без второй заглушки списка.

#### Scenario: Список аккаунтов
- **WHEN** у конюшни есть аккаунты
- **THEN** отображаются компактные строки с именем, логином, email и отдельной иконкой отвязки справа; последним действием остаётся «Добавить аккаунт»

#### Scenario: Пустой список
- **WHEN** аккаунтов нет
- **THEN** отображаются ровно одна верхняя подсказка добавить аккаунт и действие «Добавить аккаунт», вторая заглушка отсутствует

#### Scenario: Догрузка
- **WHEN** `total` больше числа загруженных аккаунтов и пользователь нажимает «Показать ещё»
- **THEN** запрашивается следующая страница с `offset` = числу загруженных, элементы добавляются в конец

#### Scenario: Доступная активация
- **WHEN** SEO кликает основную область строки аккаунта либо фокусирует её и нажимает Enter или Space
- **THEN** аккаунт выбирается один раз и сразу открывается шаг 2; доступное имя позволяет определить аккаунт, фокус видим и переносится на содержимое нового шага

#### Scenario: Длинные значения и состояния списка
- **WHEN** список загружается, загрузка не удалась либо имя/email длинные и экран узкий
- **THEN** видны соответствующие loading/error с возможностью повтора загрузки, строки не перекрывают иконку и не выходят за пределы модального окна

### Requirement: Отвязка аккаунта Яндекса через подтверждение

Каждый аккаунт MUST иметь отдельную иконку отвязки справа с доступным именем. Её активация MUST открывать только подтверждение с предупреждением об удалении привязки счётчика через этот аккаунт, не выбирать аккаунт и не менять шаг. После подтверждённого успеха MUST обновляться список и блок привязки; выбор сбрасывается, если отвязан выбранный аккаунт.

#### Scenario: Отвязка аккаунта
- **WHEN** пользователь подтверждает отвязку аккаунта
- **THEN** выполняется `DELETE /api/yandex/accounts/{id}`, аккаунт исчезает из списка, блок привязки перезагружается

#### Scenario: Аккаунт уже отсутствует
- **WHEN** backend отвечает `404`
- **THEN** показывается сообщение, список аккаунтов перезагружается

#### Scenario: Изоляция иконки
- **WHEN** SEO кликает иконку отвязки либо активирует её Enter или Space
- **THEN** открывается только подтверждение с каскадным предупреждением, выбор и шаг не меняются, DELETE до подтверждения не отправляется; отмена ничего не удаляет

#### Scenario: Ошибка и pending отвязки
- **WHEN** отвязка выполняется либо завершается ошибкой, включая `401/403`
- **THEN** повторный submit и выбор аккаунта во время pending заблокированы; при ошибке подтверждение остаётся с безопасным сообщением, ложного перехода/успеха нет

### Requirement: Шаг выбора счётчика Метрики

Цель «Яндекс.Метрика» MUST загружать `GET /api/yandex/metrica/counters` с поиском debounce 300 мс, сбросом offset и пагинацией limit/offset. Активация компактной строки счётчика кликом, Enter или Space MUST сразу вызывать `POST /api/yandex/metrica/connection`; отдельных «Выбрать счётчик», «Привязать», «Обновить счётчики» MUST NOT быть. Успех MUST закрывать визард и обновлять блок.

#### Scenario: Привязка счётчика
- **WHEN** пользователь активирует строку счётчика
- **THEN** немедленно выполняется один POST с `yandex_account_id` и `counter_id` именно активированной строки; успех закрывает визард, блок показывает привязанный счётчик

#### Scenario: Поиск сбрасывает offset
- **WHEN** пользователь на второй странице вводит строку поиска
- **THEN** после debounce запрос уходит с `offset=0` и `search`

#### Scenario: Ошибка счётчиков
- **WHEN** backend отвечает ошибкой при загрузке счётчиков или привязке
- **THEN** шаг показывает сообщение ошибки, визард остаётся открытым, выбранный аккаунт сохраняется; ошибка привязки сохраняет список/поиск/страницу и не вызывает автоматический POST

#### Scenario: Повтор после ошибки
- **WHEN** привязка завершилась ошибкой и SEO снова активирует строку
- **THEN** отправляется одна новая попытка с идентификатором этой строки, без промежуточной кнопки; до новой активации повторной mutation нет

#### Scenario: Повтор загрузки после ошибки чтения
- **WHEN** загрузить счётчики не удалось
- **THEN** доступен контекстный повтор GET из сообщения ошибки без постоянной кнопки «Обновить счётчики»; при пустом успешном ответе отображается одна подсказка

#### Scenario: Pending привязки
- **WHEN** запрос привязки ещё выполняется
- **THEN** виден pending, активация всех строк, поиск, пагинация, «Назад» и закрытие визарда заблокированы до завершения запроса, повторный POST не отправляется

### Requirement: Защита мутаций SEO на UI

Действия привязки, отвязки и добавления аккаунта MUST быть доступны только SEO; роль MUST повторно проверяться в hook непосредственно перед API, без наследования SUPERUSER/DEVELOPER. Все mutation-триггеры, включая строки и иконки, MUST иметь синхронную защиту double-submit. Отказы `401/403` MUST отображаться без ложного успеха и потери контекста шага.

#### Scenario: Локальный отказ без ADMIN
- **WHEN** пользователь без SEO, включая SUPERUSER/DEVELOPER, пытается запустить мутацию через hook
- **THEN** локальная проверка отклоняет действие, API не вызывается

#### Scenario: Двойной клик
- **WHEN** пользователь дважды быстро активирует строку счётчика (в том числе разные строки), иконку либо подтверждение мутации
- **THEN** до завершения pending отправляется не более одного mutation-запроса

#### Scenario: Отказ backend
- **WHEN** мутация получает `403`
- **THEN** пользователь видит сообщение об отсутствии прав, данные не меняются, визард/подтверждение не закрывается как при успехе

#### Scenario: Отзыв разрешения перед mutation
- **WHEN** после отображения доступного действия роль SEO отозвана и пользователь активирует его
- **THEN** hook повторно проверяет актуальные permissions и не отправляет mutation
