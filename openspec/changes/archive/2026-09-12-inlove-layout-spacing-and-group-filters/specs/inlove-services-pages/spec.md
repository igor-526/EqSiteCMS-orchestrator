## ADDED Requirements

### Requirement: Сетка карточек тарифов плотнее на desktop и компактнее на mobile
На каждой из трёх страниц услуг сетка карточек тарифов SHALL показывать три карточки в ряд на desktop (вместо двух). На mobile изображение карточки SHALL занимать меньшую долю карточки, чем на desktop (уменьшенное/менее доминирующее соотношение сторон), чтобы на экран помещалось больше карточек одновременно. Название тарифа в карточке SHALL отображаться полужирным начертанием (минимум `font-weight: 700`), визуально отличимым от остального текста карточки. На desktop клик по изображению карточки SHALL переводить на detail-страницу тарифа (`/uslugi/{zanyatiya|progulki|postoy}/[slug]`); на mobile клик по изображению MUST NOT инициировать переход (переход остаётся доступен через текстовую ссылку «Подробнее»).

#### Scenario: Desktop grid и переход по изображению
- **WHEN** страница услуги отображается на desktop viewport (≥1024px)
- **THEN** карточки тарифов расположены по три в ряд, название тарифа полужирное, а клик по изображению карточки переводит на её detail-страницу

#### Scenario: Mobile изображение занимает меньшую долю карточки
- **WHEN** страница услуги отображается на mobile viewport
- **THEN** изображение карточки заметно меньше по высоте относительно всей карточки, чем на desktop, а клик по изображению не выполняет переход

### Requirement: Страницы услуг не показывают блок предупреждения о переменности цен
Ни одна из трёх страниц услуг (список и detail) SHALL NOT отображать блок-предупреждение о переменности/источниках цен (например, «Цены и условия собраны из нескольких источников и могут измениться…») ни при каких данных API или site settings. Компонент, ранее принимавший `notice`, SHALL перестать поддерживать такой проп/рендер в контракте `PricesSection`/страничных Prices-компонентов.

#### Scenario: Notice отсутствует независимо от входных данных
- **WHEN** страница услуги отображается при любых значениях API/settings, в том числе исторически содержавших текст предупреждения
- **THEN** HTML страницы не содержит текста предупреждения о переменности цен ни в каком виде

### Requirement: Фильтрация тарифов на всех трёх страницах услуг выполняется backend через выделенные price_groups
Принцип «одна страница услуг = одна выделенная backend-группа `price_groups`» SHALL применяться ко всем трём страницам услуг; ни одна из них MUST NOT обращаться к общей catch-all группе («Основные услуги» или любая другая, объединяющая тарифы нескольких страниц) и MUST NOT применять клиентский allow-list фиксированных slug'ов или фильтр по `name` поверх ответа API.

Локальный переключатель «Разовые/Абонементы» на странице «Занятия» SHALL сохраняться в UI, но каждое его состояние SHALL выполнять **отдельный** Public Read запрос `GET /api/prices?groups=<точное имя>` («Разовые» либо «Абонементы» соответственно) — не один запрос с повторяемым `groups=`, чтобы не зависеть от его AND/OR-семантики. Страница «Прогулки» SHALL запрашивать `GET /api/prices?groups=Прогулки` вместо повторяемого `name=`. Страница «Постой» SHALL запрашивать `GET /api/prices?groups=Постой частных лошадей` вместо фильтра по `name`.

Набор карточек на каждой странице SHALL равняться фактическому ответу её backend-группы(групп) без дополнительной клиентской фильтрации. Detail-route guard (`/uslugi/{zanyatiya|progulki|postoy}/[slug]`) SHALL считать тариф принадлежащим странице, если поле `groups` в ответе `GET /api/prices/{slug_or_id}` содержит хотя бы одно из имён групп, допустимых для этой страницы, и SHALL возвращать 404 иначе — без хардкоженного массива slug'ов.

#### Scenario: Переключатель «Занятия» выполняет два отдельных запроса
- **WHEN** посетитель переключает «Разовые»/«Абонементы» на странице «Занятия»
- **THEN** сайт выполняет отдельный Public Read запрос с `groups=Разовые` либо `groups=Абонементы` (не единый repeatable-запрос) и отображает ровно те тарифы, что вернул backend для этой группы

#### Scenario: Прогулки запрашивают свою группу
- **WHEN** посетитель открывает `/uslugi/progulki`
- **THEN** сайт выполняет Public Read запрос с `groups=Прогулки`, а не повторяемый фильтр по `name`

#### Scenario: Постой запрашивает свою группу
- **WHEN** посетитель открывает `/uslugi/postoy`
- **THEN** сайт выполняет Public Read запрос с `groups=Постой частных лошадей`, а не фильтр по `name`

#### Scenario: Detail-route guard проверяет членство в группе, а не хардкод-список
- **WHEN** detail route одной из трёх страниц услуг проверяет принадлежность slug своей странице
- **THEN** решение принимается по полю `groups` тарифа из ответа `GET /api/prices/{slug_or_id}` (пересечение с допустимыми группами страницы), а не по статической константе slug'ов в коде

#### Scenario: Ни одна страница не использует catch-all группу
- **WHEN** reviewer проверяет исходящие запросы всех трёх страниц услуг
- **THEN** ни один запрос не содержит `groups=Основные услуги` и не полагается на неё как источник карточек

### Requirement: Сокращённый вертикальный разрыв между блоками страницы «Постой»
Разрыв между блоками «Постой», «Инфраструктура», «Что входит» и «Стоимость» на странице `/uslugi/postoy` SHALL использовать переиспользуемый seam-механизм `Section` (`inlove-ui-components`) и визуально не превышать примерно четверть прежнего суммарного отступа между каждой парой блоков.

#### Scenario: Компактные переходы между блоками Постоя
- **WHEN** `/uslugi/postoy` отображается на desktop и mobile viewport
- **THEN** видимый разрыв между каждой последовательной парой блоков «Постой»/«Инфраструктура»/«Что входит»/«Стоимость» заметно меньше суммы паддингов двух отдельных секций
