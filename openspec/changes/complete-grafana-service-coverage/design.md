# Design — complete-grafana-service-coverage

Дата: 2026-11-12; уточнение PLAN-2 — найден source EqCMS_Infra. Запрос: `docs/tasks/115_grafana_service_coverage.md`; история: `docs/tasks/054_observability.md`. Сервисы: девять manifest-сервисов без inlove, инфраструктура Redis/NATS/PostgreSQL.

## Context

Мотивация — proposal.md. `platform-observability` прочитан целиком: это действующий контракт Sentry и внутреннего Prometheus listener первых трёх Python-сервисов, не доказательство текущего полного покрытия. `docs/operations/observability.md` описывает Next.js Prometheus как неприменимый — это изменится. Его старые mobile/tablet QA рекомендации не переносить: CMS desktop 1366×768, UI diff здесь нет.

### Что установлено из checkout и read-only runtime

- Каждый service workflow `.github/workflows/check_and_deploy.yml` использует service-local `.helm/`, `helm upgrade --install` на release и `KUBE_CONFIG` secret. Python/Frontend releases — `cms`, site-ad — `consumer`. Наличие kubeconfig проверено без чтения значения. Выполнены только `kubectl get`, `helm list` и Grafana read-only запросы; право записи не проверялось и не предполагается.
- Во всех семи Python charts есть ServiceMonitor с path `/`; backend Service имеет `app` label, но email и другие новые Service-шаблоны не имеют требуемого `app` при таком selector. Это конкретный static gap, но не доказательство единственной причины. Нужны согласованные Service labels, namespace/discovery и `/metrics`; backend `/` сейчас scrape-able, при rollout переключить явно.
- Backend/email/notification/VK имеют Instrumentator и `utils/observability.py` с `start_http_server:9000`; SEO/Yandex/ya-metrica таких вызовов в src не найдено. Worker charts не объявляют metrics ports/Services. API и workers сейчас используют разные selectors, их нельзя объединять HTTP Service.
- Next.js 15 в frontend/site-ad запускается `next start`; Prometheus зависимость/внутренний server instrumentation отсутствуют. Не подменять это контейнерными метриками.
- В monitoring фактически Helm releases: `monitoring` (`kube-prometheus-stack-0.1.0`), `alloy` (`monitoring-alloy-0.1.0`), `loki` (`monitoring-loki-0.1.0`), `postgres-exporter` (`monitoring-postgres-exporter-0.1.0`). Prometheus `monitoring-kube-prometheus-prometheus` имеет serviceMonitorSelector={} и namespaceSelector={}. Collector — Alloy, не предположительный Promtail.
- Redis/NATS — releases `redis`/`nats` в cms. PLAN-2 по прямому указанию пользователя нашёл их source в `/srv/EqCMS_Infra/charts/{redis-helm,nats-helm}` и monitoring source в `charts/monitoring/`; прежний blocker неизвестного repository снят. Соседний source исследован только read-only, с его AGENTS.md; `secrets/`, env и kubeconfig не читались. Право изменения source/кластера текущей сессии не расширялось.
- Router передал один live прикладной backend target и контейнерную память остальных. Planner не повторял полный Prometheus аудит. Loki label values за час для cms/consumer содержат 14 имён, но без email API и отдельных cleanup/merge; `celery-worker` смешивает service identity. За 15 минут найдено семь групп, остальные не объявляются отсутствующими: короткое окно/простой не доказательство потери сбора. Сырые строки логов не извлекались.
- Read-only evidence: `.qa/complete-grafana-service-coverage/PLAN-1/{monitoring-owners.txt,monitoring-releases.json,cms-runtime.txt,scrape-selectors.txt,loki-observation.md}`.

### Конечный runtime inventory

| Service | Долгоживущие components | Дополнительная граница |
|---|---|---|
| backend | api | NATS обработчики внутри API: consumer heartbeat/outcomes, не искусственный deployment |
| notification-service | api | встроенные NATS handlers учитываются по фиксированному consumer type |
| email-service | api, celery-worker (email) | built-in consumers отдельно от Celery success |
| vk-service | api, celery-worker (vk), vk-bot | bot polling heartbeat, handler errors/retry; библиотечные retry не новая Sentry авария |
| seo-service | api, seo-scheduler, seo-maintenance | tick/dispatch/maintenance duration/outcome без tenant labels |
| yandex-service | api | external provider failures по ограниченной категории, без OAuth/token |
| ya-metrica-service | api, celery-worker (ya_metrica), celery-beat, cleanup-worker, merge-worker | встроенный NATS supervisor отдельно от четырёх процессов |
| frontend | next-server | server HTTP/runtime; browser RUM вне scope |
| site-ad | next-server | SSR/public HTTP/runtime; не только API routes |
| Redis/NATS/PostgreSQL | infrastructure/exporters | exporter + исходный workload logs, не только exporter log |

Итого 18 долгоживущих прикладных deployments в текущем inventory; каждый pod/replica также проверяется через discovery. Migration/one-shot jobs: completion/exit из kube-state-metrics и lifecycle logs, без бессмысленного вечного `up`. Финальный inventory сверяется с effective render/runtime: не включать/выключать workers и не менять их replicas/очереди/Singleton semantics ради покрытия. Текущий source расходится с некоторыми историческими multiarch описаниями — источник истины здесь текущие файлы и переданный handoff, не старый proposal.

## Goals / Non-Goals

**Цели:** воспроизводимые telemetry adapters, согласованные service/infra charts, безопасные настройки в их единственном source of truth, проектные dashboards и независимый live coverage gate.

**Не цели:** изменения схемы БД, транзакций, NATS topology/subjects/envelopes, business API/tenant semantics, новая UI CMS, browser RUM, production chaos, миграция общего monitoring стека. API/NATS contracts не меняются, поэтому AsyncAPI не редактируется.

## Decisions

### 1. Источники истины и граница двух репозиториев

**EqSiteCMS root** владеет только `deploy/observability/{runtime-inventory.yaml,telemetry-policy.yaml,README.md}`, `tests/observability/{test_contract.py,test_source_links.py,fixtures/**}`, `docs/operations/observability.md`; это контракт и runbook, не второй deployment bundle. Service templates/instrumentation остаются в `services/<service>/`. В root не создавать `deploy/observability/monitoring/` и `dashboards/`: предложение PLAN-1 о переносимом дубликате снято, ни один такой runtime файл ещё не создан.

**EqCMS_Infra** — отдельный source directory с собственным AGENTS.md и владельцем DevOps. Найдены точные paths:

| Release / namespace | Единственный deployment source | Что меняется / что сохраняется |
|---|---|---|
| monitoring / monitoring | `charts/monitoring/kube-prometheus-stack/{Chart.yaml,values.yaml,templates/,dashboards/}`; обязательный `grafana-postgresql.values.yaml` | EXT-SCRAPE: стабильный scraper pod label; EXT-VIEWS: новые project JSON/ConfigMaps. Сохранить overlay, Grafana DB/Secret refs и текущие dashboards |
| alloy / monitoring | `charts/monitoring/alloy/{Chart.yaml,values.yaml,templates/}` | один существующий Deployment, API-based pod logs; finite workload mapping/normalization, не второй collector |
| loki / monitoring | `charts/monitoring/loki/{Chart.yaml,values.yaml,templates/}` | только collector/security wiring и при необходимости новая ingress NetworkPolicy; schema/S3 Secret refs/retention168h/placement/storage не менять |
| postgres-exporter / monitoring | `charts/monitoring/postgres-exporter/{Chart.yaml,values.yaml,templates/}` | reuse exporter/Secret `postgres-exporter:datasource`, target metadata/scrape restrictions; grants не менять |
| redis / cms | `charts/redis-helm/{Chart.yaml,values.yaml,templates/redis-{deployment,service}.yml}` и новые `templates/redis-{metrics-service,monitor,networkpolicy}.yaml` | sidecar exporter, существующая identity, Secret references вместо plaintext; не менять данные/port6379/client semantics |
| nats / cms | `charts/nats-helm/{Chart.yaml,values.yaml,templates/nats-{deployment,service}.yml}` и новые `templates/nats-{monitoring-config,metrics-service,monitor,networkpolicy}.yaml` | sidecar exporter и localhost monitoring8222; сохранить 4222, JetStream flags/store/replicas |

Тесты каждого EXT slice — собственный новый `tests/test_eqcms_{scrape_contract,log_pipeline,redis_metrics,nats_metrics,postgres_metrics,dashboards}.py`; PostgreSQL source `charts/eqcms-infra/templates/workloads.yaml` и helper/config данного workload только read-only identity reference, не ownership на его БД/GlitchTip. `docs/MONITORING.md` меняет один DevOps owner последовательно по назначенным разделам. `docs/GRAFANA-POSTGRESQL.md`, namespaces manifests и vendored archives/locks read-only. Не запускать infra Makefile: db-update mutating, db-port-forward — runtime operation, monitoring target отсутствует.

В EqCMS_Infra отсутствует `.git` (`git status` — not a git repository). Не init/commit/объявлять выдуманную revision. Для воспроизводимости каждый EXT unit сохраняет immutable allowlisted non-secret source snapshot до/после, manifest file hashes, chart/dependency version и safe render summary в своём ignored evidence. Перед snapshot обязательна secret-safety проверка; legacy Redis source с literal не копировать даже в .qa — только redacted structural baseline и непубликуемый owner rollback reference. После исправления safe source можно версионировать snapshot/digest. Один hash без сохранённого safe source не объявлять воспроизводимой rollback revision. Дальнейшее размещение source в Git — отдельное решение владельца, не prerequisite offline реализации. PLAN-2 evidence — `.qa/complete-grafana-service-coverage/PLAN-2/{source-fingerprints.json,safe-source-summary.json,render-summary.json,security-observation.md}`. Hashing не включает секреты.

EXT units назначаются внешнему **DevOps владельцу EqCMS_Infra**. Router получает его handoff/разрешённый context pack, не посылает CMS Backend с правом менять чужой каталог. В этой PLAN-2 сессии разрешены только плановые файлы EqSiteCMS и ignored evidence; никакие infra configs не редактируются. После approval Router отдельно выдаёт ограниченный execution grant каждому внешнему unit; это штатная граница будущего запуска, не открытое проектное решение и не deployment permit.

### 2. Служебный доступ

Каноническая access matrix — `specs/platform-observability/spec.md`, ACCESS-01/02. Все новые/меняемые metrics — отдельный :9000/metrics на каждом pod; exporter ports 9121/7777/9187, NATS 8222 только exporter. Без business auth: доступ задаётся NetworkPolicy allowlist namespace+pod labels фактического Prometheus, не всеми pod monitoring namespace. EXT-SCRAPE задаёт Prometheus `prometheus.prometheusSpec.podMetadata.labels["eqcms.observability/scraper"]=true` под wrapper ключом kube-prometheus-stack; все metrics policies разрешают только этот label AND namespace `monitoring`. Alloy собирает logs через Kubernetes API и НЕ получает право scrape :9000. Его source pod labels из offline render: app.kubernetes.io/name=alloy, app.kubernetes.io/instance=alloy. Public ingress `/metrics` и `/api/metrics` — явный 404 deny до Next catch-all; прочие public routes и authenticated business API неизменны. Private listener 200 проверяется без cookie и с валидной CMS session, forbidden source — network deny независимо от cookie. Не возвращать fake 401 вместо сетевого отказа.

Исходная документация infra сообщает Flannel VXLAN и отсутствие NetworkPolicy, а не доказанный CNI enforcement. Новая per-workload ingress policy сохраняет прежние business ports (8000/5100/3000, Redis6379/NATS4222) с прежним client reachability, но отдельное правило metrics разрешает только scraper identity. Нельзя добавить broad all-ports rule: policies additive и оно отменит изоляцию. Для background разрешён только9000. Не вводить глобальный namespace default-deny/egress deny и не закрывать существующие shared clients. Без подтверждённого enforcer security acceptance blocked; установка/перенастройка CNI не входит в proposal. ClusterIP сам по себе недостаточен. Никакие токены scraper не добавляются в browser env.

### 3. Python API и фоновые процессы

Сохранить локальные adapters, без общей Python библиотеки на девять lockfiles. Инфраструктурная instrumentation в `src/utils/observability.py` и logging adapter, подключение в `src/main.py`/settings и process entrypoints; core entities не импортируют Prometheus. Первые сервисы сохраняют production-only enablement и default registry; listener `/metrics` использует ровно registry middleware. Каждый API adapter обновляет process heartbeat независимо от запросов; отсутствие NATS consumer у Yandex не отменяет runtime heartbeat. На shutdown гарантированно освобождать port/thread, повторный lifespan/test не создаёт duplicate series. Prometheus collectors не выполняют DB/HTTP обращения на каждом scrape. Вывод process metrics не должен описывать exporter вместо приложения.

HTTP: `http_requests_total{method,handler,status}` и `http_request_duration_seconds_bucket{method,handler,le}`; status — ограниченные значения 1xx..5xx, handler — route template либо `unmatched`. Фиксированные histogram buckets 0.005,0.01,0.025,0.05,0.1,0.25,0.5,1,2.5,5,10,+Inf. `/health`, `/metrics` исключены. Существующие backend метрики не переименовывать молча: сохранить совместимые aliases/queries там, где отличался label status; приведение через dashboard recording expressions, не двойная instrumentation. Latency у Next.js измерять до response finish (или abort с фиксированным outcome), а не временем middleware dispatch.

Workers: parent создаёт listener один раз, не каждый child. Celery prefork — отдельная `PROMETHEUS_MULTIPROC_DIR` emptyDir на pod, очищаемая только перед стартом parent, worker signals регистрируют counters/histograms; multiprocess registry использует MultiProcessCollector, dead child cleanup, aggregate process collectors документируются отдельно. Singleton parent heartbeat не выдавать за child job progress: отдельные `eqcms_runtime_heartbeat_timestamp_seconds` и `eqcms_job_last_completed_timestamp_seconds`. Один worker pod не читает registry другого. Beat — отдельный registry/heartbeat и dispatch outcomes без включения второго scheduler. Bot/SEO процессы — listener в основном lifecycle. Встроенный NATS consumer имеет ограниченный label consumer и progress/outcomes внутри API registry, не новый процесс.

Jobs: `eqcms_jobs_total{job_type,outcome}` (success,error,retry), `eqcms_job_duration_seconds`, `eqcms_runtime_heartbeat_timestamp_seconds`, `eqcms_job_last_completed_timestamp_seconds`, `eqcms_queue_depth{queue}`, `eqcms_queue_wait_seconds` по безопасной enqueue timestamp metadata. Очереди allowlist: email, vk, ya_metrica, ya_metrica_cleanup, ya_metrica_merge и согласованные JetStream consumers. Текущий oldest queue age не выдумывать из last completion: при отсутствии безопасного broker metadata явно unsupported, backlog и observed wait остаются видимыми. Никакого чтения/экспорта task body, email/tenant labels или неограниченного сканирования Redis. Test failure/retry проверяется локально, без отправки писем, VK сообщений и vendor API.

### 4. Next.js HTTP/runtime metrics

Выбрать небольшой custom Node production server `server/observability-server.mjs` в каждом Next.js проекте: тот же процесс вызывает Next request handler и содержит prom-client registry/внутренний :9000 listener. Это обеспечивает SSR/static/API request count и response finish latency, в отличие от sidecar с собственными process metrics или middleware-only тайминга. `server/route-labels.mjs` использует конечный allowlist публичных/приватных route templates, `unmatched` для произвольного path; query/body не читаются. Metrics listener отдельный HTTP server, не `src/app/api/metrics`. Dockerfile копирует server files и запускает production server вместо `next start`; dev команда не меняется. Зависимость prom-client в production dependencies и lockfile. В Node registry есть process heartbeat timer с unref и cleanup при shutdown; он не зависит от HTTP traffic. Тесты сравнивают существующие public/auth responses, cache/streaming и graceful shutdown. Next/Sentry instrumentation сохраняется. Edge/browser метрики не объявляются покрытыми server metrics.

### 5. Logging и labels

Единый JSON stdout/stderr formatter с UTC timestamp/level/service/component/environment/event/message; exception stack как escaped строка одной JSON записи. Стабильный service равен manifest имени, component из runtime inventory; инфраструктурные имена отдельны. В Loki базовые labels: cluster, namespace, service_name (canonical service), component, environment. pod/container — только технические stream labels существующего Kubernetes collector, не пользовательские IDs; не добавлять instance с URL, requestId, traceId, tenant/user/job ID, email, query/path. В Prometheus service/component/environment добавляет target relabeling; pod/instance — технические discovery labels, не прикладные dimensions. Нормализация существующего `eqcms-*`/`celery-worker` не должна терять происхождение: извлекать service/component из pod labels workload, не из одного имени контейнера. Поддержать старые stream queries через dashboard migration window, не дублировать ingestion.

Обязательный logging closure включает uvicorn/gunicorn access, Celery task logs, SQL/HTTP client и Node console/library stderr: не оставлять рядом с JSON formatter несанитизированные native handlers; не включать SQL parameters, raw URL/query или task args. Первичная sanitization в сервисе (до stdout), Alloy — defense-in-depth, не оправдание утечки в kube logs. Удалять credentials, bearer/cookies, DSN/URLs с паролем, request/response bodies, recipient/user/tenant identifiers и PII из exception messages. Allowlisted event/error_category вместо raw vendor exception. Sampling не скрывает errors/lifecycle. Стабильные periodic heartbeat logs не чаще 60 секунд там, где иначе нельзя подтвердить тихий runtime; enabled через observability config и без бизнес-side effects. Лимит policy: ≤8 Loki indexed labels с сохранением уже нужных технических labels; если effective pipeline больше — внешний owner обосновывает/сокращает до adoption. Cardinality-test: 1000 случайных IDs/query не создают новых handler/task label values; метрики не более 10k активных прикладных series на service при текущем route/replica inventory, превышение блокирует adoption, не лечится drop всех HTTP метрик.

### 6. Discovery, infra и dashboards

Для API `.helm` labels Service и ServiceMonitor совпадают; workers/bot/scheduler/beat имеют отдельные metric-only Services с named port metrics, `/metrics`, 30s interval. Предпочтение ServiceMonitor как текущему механизму; PLAN-2 подтвердил этот выбор, PodMonitor не вводится. Namespace берётся из release, сохраняются resource identity/images/commands/secret refs и business selectors. ContainerPort сам по себе не доказывает наличие listener.

Infra: reuse существующего PostgreSQL exporter (не создавать второго) и проверить все project DB instances, а не лишь exporter up. Redis exporter получает только согласованные read-only collectors, connections/memory и фиксированные queue aliases без ключей пользователя. NATS exporter читает внутренний 8222, safe varz/jsz aggregate, отключить публикацию client URLs/accounts/subjects с приватными IDs. Наблюдать ack pending/redelivery/backlog по конечному списку consumers. Доступы — secret references в infra source, без root copies/literals; изменение grants только владельцем после отдельного permit.

Dashboards только в `/srv/EqCMS_Infra/charts/monitoring/kube-prometheus-stack/dashboards/eqcms-{coverage,http,jobs,infrastructure,logs}.json` и пяти одноимённых `templates/dashboard-eqcms-*.yaml` ConfigMaps с label grafana_dashboard="1", stable UID `eqcms-*`, параметризованные datasources (Prometheus default; Loki UID P8E80F9AEF21F6940 как текущая selection, не пароль). Фильтры environment/service/component с allowlist только scope. Coverage показывает expected inventory рядом с present series/log evidence; отсутствие series не `or vector(0)`. Error rate при нуле requests — «нет трафика», p95 при отсутствии observations — N/A. Logs drilldown по canonical labels и текущему time window; infra общий dashboard не менять для чужих проектов, добавить проектный view. Rules для scrape down/stale heartbeat/delivery lag — сначала versioned примеры без включения paging/notification integrations.

### 7. Конкретные EXT решения после проверки source

**EXT-SCRAPE.** Сохранить общие `serviceMonitorSelector={}`/`serviceMonitorNamespaceSelector={}` и NilUsesHelmValues=false, не ломать общие infra targets/mcp. Project ServiceMonitors имеют label `eqcms.observability/scope=eqsitecms`, named port metrics, `/metrics`, interval30s. Сервисные owners добавляют Service labels `observability_service`, `observability_component`, `observability_environment` и явные relabelings в Prometheus service/component/environment; стабильные pod service/component labels нужны и Alloy. Фиксированные environment labels соответствуют deployment environment, не извлекаются из приватных env. Новый scraper pod label задаётся только Prometheus, не Grafana/Alloy. Render Prometheus CR проверяет podMetadata, ServiceMonitor contract tests — labels/port/path и отсутствие чужих namespace/allowlists. Existing shared targets не переименовывать/не удалять.

**EXT-LOGS.** Меняется существующий Alloy configMap.content в values, не отдельный DaemonSet. Маппинг по namespace + workload service/component labels (с fallback таблицей текущих eqcms names); новый project branch принимает только девять сервисов в cms/consumer, Redis/NATS в cms, PostgreSQL workload `postgresql` в eqcms-infra и postgres-exporter в monitoring. Для PostgreSQL allowlist опирается на StatefulSet identity/label app=postgresql из исходного workloads.yaml, не на namespace целиком. Monitoring/eqcms-infra namespace-wide keep запрещён: иначе собираются GlitchTip/чужие процессы. Требуемый RBAC pods/log уже есть в vendored Alloy; права на secrets не расширять. Формат JSON приложений сохраняется с redaction и multiline; native infra branch выпускает только timestamp/level/service/component + фиксированную event category и безопасное сообщение, raw text/SQL/connection URI не пересылаются в Loki. Это нормализация, не утверждение, что legacy native stdout уже безопасен: обнаруженный небезопасный source output фиксируется отдельным owner finding, raw historical data не удаляется автоматически. Метрики нормализации/drop/error и число входных stream rows нужны, чтобы privacy filtering не выдавать за потерю ingestion. Проверка heartbeat для тихого infra workload использует разрешённую known lifecycle запись, без production restart ради evidence.

Защитить Loki gateway и singleBinary HTTP ingress через source NetworkPolicy: разрешённый existing Alloy (write), Grafana (read) и внутренняя gateway→singleBinary связь; source port/selector взять из vendored default render, не гадать. Не менять S3/retention/schema/ARM placement/storage/credentials. Явно сохранить путь Prometheus→Loki/gateway metrics, если этот target уже существует. ## Risks / Trade-offs

- Source найден, но отдельный контур не передан текущему runtime агенту → будущие EXT invocations только после approval и явного narrow ownership grant, без live patch.
- Next custom server увеличивает packaging responsibility → независимые startup/SSR/auth/cache/shutdown tests; standalone output не включать без согласования.
- Celery prefork теряет child metrics при неверном lifecycle → parent-owned registry/multiproc tests и три scrape intervals после рестарта в изолированной проверке.
- Метрики/логи раскрывают данные или взрывают cardinality → pre-stdout sanitization и finite allowlists, seed-marker tests, runtime label audit.
- Короткое окно логов/мало трафика → lifecycle/heartbeat evidence, не искусственная production рассылка.
- Пересечение charts/workflows с активным multiarch change и app files с task-monitor/SMTP → Router обязан получить handoff и передать ownership до запуска; чужой diff не включать.
- Rollout ещё не разрешён → QG может завершить static/local lanes, но итог не APPROVED с полной live coverage до снятия blockers.

Для контролируемого traffic — отдельный разрешённый non-mutating request; для job canary — isolated target/permit. Не делать rollback Grafana на revision1/SQLite, не удалять данные/очереди/log history/Secrets. Эта безопасная rollback конфигурация должна быть подготовлена/tested заранее с synthetic Secret, её adoption также отдельно разрешается.
7. После общего QG и fixes Router по решению пользователя делает sync specs, strict validate и archive. Runtime readiness и archive не запускаются Planner.
