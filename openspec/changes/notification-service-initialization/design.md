## Context

Текущий notification-service имеет:
- Базовую структуру FastAPI с NATS клиентом
- Настройки для подключения к PostgreSQL, NATS, main backend
- HTTP-клиент для main backend (`clients/main_backend/client.py`)
- Консьюмер для callback_request с хардкодом email

**Проблемы текущей реализации:**
- Миграция пустая, таблиц не существует
- Нет моделей SQLAlchemy
- Нет репозиторного слоя
- Обработчик callback_request жёстко привязан к email-адресу "igor-526@yandex.ru"
- Нет сервисного слоя для оркестрации пайплайна

## Goals / Non-Goals

**Goals:**
1. Реализовать модели SQLAlchemy для channels, events, user_notification_settings
2. Создать миграцию Alembic с созданием таблиц
3. Реализовать сидирование данных (по аналогии с backend)
4. Реализовать репозиторный слой для CRUD операций
5. Реализовать сервис оркестрации пайплайна обработки событий
6. Обновить обработчик callback_request для работы с БД
7. Интегрировать все компоненты через DI-контейнер

**Non-Goals:**
1. Реализация других каналов доставки (VK, SMS) — только email
2. Реализация других событий — только callback
3. Логика экстрактинга email из пользовательских данных — хардкод "igor-526@yandex.ru"
4. UI для управления настройками уведомлений
5. Валидация метаданных событий — этим занимается основной backend

## Decisions

### 1. Архитектура слоёв
**Решение:** Четырёхслойная архитектура:
- **Models** (SQLAlchemy) — определение таблиц
- **Repositories** — CRUD операции с БД
- **Services** — бизнес-логика и оркестрация
- **Handlers** — обработка NATS-событий

**Обоснование:**
- Разделение ответственности
- Тестируемость каждого слоя
- Соответствие существующей архитектуре проекта

### 2. Сидирование данных
**Решение:** Сидирование через SimpleSeeder паттерн (по аналогии с backend)

**Реализация:**
- BaseSeeder — абстрактный базовый класс с методами prepare, fetch_existing, diff, create_missing
- SimpleSeeder — generic seeder для простых случаев
- init_registry — apply_migration + run_seeders_with_retry
- Seed данные в core/seeds/ с фиксированными UUID
- Seeder классы в utils/seeding/seeders/

**Обоснование:**
- Данные read-only (каналы, события)
- Гарантированная воспроизводимость
- Дедупликация при повторном запуске
- Единый подход с backend

### 3. Стратегия поиска адресатов
**Решение:** 
1. Получение пользователей от main backend по equestrian_id
2. Фильтрация по настройкам user_notification_settings
3. Хардкод email для MVP

**Обоснование:**
- Поэтапная реализация
- Интеграция с существующим main backend API
- Отложенная реализация экстрактинга email

### 4. Обработка ошибок main backend
**Решение:** Пропустить уведомление, залогировать ошибку

**Обоснование:**
- Не блокировать обработку других событий
- Логирование для диагностики
- Простота реализации

### 5. Паттерн обработки событий
**Решение:** Registry паттерн для обработчиков событий:
- Event.code → EventHandler class
- Динамический поиск обработчика по коду события

**Обоснование:**
- Расширяемость для новых событий
- Конфигурируемость через БД
- Соответствие требованиям из docs/tasks

### 6. DI-контейнер
**Решение:** Использование dependency-injector (DeclarativeContainer)

**Обоснование:**
- Уже используется в проекте
- Соответствие существующей архитектуре
- Удобство тестирования

### 7. Дедупликация событий
**Решение:** Дедупликация по event_id (UUID из payload)

**Обоснование:**
- Предотвращение повторной обработки
- NATS гарантирует at-least-once delivery
- Идемпотентность обработки

### 8. Отправка уведомлений
**Решение:** Сервис уведомлений только формирует и отправляет команды на доставку. Вся остальная логика (отправка email, SMS и т.д.) происходит в соответствующих микросервисах.

**Обоснование:**
- Разделение ответственности
- Единая точка обработки событий
- Легкая интеграция с новыми каналами

## Risks / Trade-offs

### Риски:
1. **Миграция БД:** Изменение схемы требует миграции
   - *Митигация:* Тщательное тестирование миграции, возможность отката

2. **Зависимость от main backend:** Сбой main backend блокирует обработку
   - *Митигация:* Пропуск уведомления с логированием ошибки

3. **Производительность:** Запросы к main backend + local DB
   - *Митигация:* Небольшой объем трафика, горизонтальное масштабирование

### Trade-offs:
1. **Хардкод email vs полная реализация:**
   - Выбрано: Хардкод для MVP
   - Причина: Ускорение реализации, отложенная сложность

2. **Сидирование через SimpleSeeder vs Alembic bulk_insert:**
   - Выбрано: SimpleSeeder
   - Причина: Дедупликация, идемпотентность, соответствие backend

3. **Registry паттерн vs простой switch:**
   - Выбрано: Registry
   - Причина: Расширяемость, соответствие требованиям
