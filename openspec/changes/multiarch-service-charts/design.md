# Design — multiarch-service-charts

Задание: `docs/tasks/111_charts.md` · дата: 2026-11-10 · профиль планирования: PLAN-111.
Сервисы: backend, email-service, notification-service, frontend, vk-service, site-ad, site-ksk-inlove, seo-service, yandex-service, ya-metrica-service.

## Context

Мотивация — [proposal.md](proposal.md). Инвентаризация выполнена по tracked delivery-файлам рабочего дерева, без чтения реальных `.env`, Secret, полного продуктового кода и `docs/plans`. Runtime не запускался, kubectl не понадобился.

Статическое чтение uv.lock обнаружило wheel references обеих архитектур для проверенных native-пакетов: backend asyncpg 0.30.0/bcrypt 4.0.1/pandas 2.3.2/psycopg2-binary 2.9.10; остальные Python-сервисы asyncpg 0.31.0/uvloop 0.22.1/httptools 0.8.0, Yandex/Metrica также cryptography 50.0.2. Это не доказывает совместимость конкретного Python ABI, наличие shared libraries и доступность URL; сводка — `.qa/multiarch-service-charts/PLAN-111/static-checks.json`.

Ни один Dockerfile не содержит явного `--platform=linux/amd64`, но это не доказательство multiarch: семь Actions не задают `platforms` и Buildx/QEMU. Все семь автоматически публикуют на release и выполняют helm upgrade; site-ad/Inlove также проверяют main. Ошибка упаковки — не основание незаметно сменить Python major/Node major или удалить зависимость. Доступность base manifests и locked wheels пока **unchecked**, это будущая проверка CI-04; не утверждается, что версия 3.14.6 отсутствует или работает.

Существующий `ci-workflows` описывает только uv cache по историческому пути, его requirement не переписывается; добавляются отдельные требования multiarch. `core-service-release-hardening` уже задаёт health и backend body-size: сохраняем, не дублируем их новыми изменениями поведения. Единственный активный change — `seo-metrica-task-monitor`: код истории задач и `scripts/qa/infra/**` остаются вне ownership. Сервисные packaging units могут идти после handoff соответствующего продуктового владельца; при изменении исходников после build evidence инвалидируется по fingerprint.

Источники инфраструктуры (read-only): `/srv/EqCMS_Infra/docs/CLUSTER.md` (mixed arch, cms/consumer), `NETWORK.md` (ClusterIP не изоляция, нет NetworkPolicy), `PLATFORM.md` (F5 NGINX, не community ingress-nginx). Это документационный снимок, не новая live проверка. Не расширять scope до реорганизации ingress/БД/брокеров. Существующий backend legacy body-size сохраняется; совместимость admission — ответственность отдельного инфраструктурного rollout.

## Goals / Non-Goals

Цель: воспроизводимая сборка/локальное исполнение платформенных артефактов и проверяемый Helm-контракт, не production rollout. Поддерживаются ровно `linux/amd64` и `linux/arm64`, не arm/v7, Windows или macOS.

Не входят: новый HTTP/API/access/AsyncAPI, изменения схем/миграций БД, включение maintenance, выдача секретов, настройка firewall/NetworkPolicy, перенос данных/PV, provision PG/NATS/Redis, root release/stack tooling, реализация UI. Изменение requirements/lock допустимо только как минимальный packaging fix в назначенном сервисе с доказанным architecture blocker и сохранением продуктового контракта; иначе stop и Router replan.

## Decisions

### 1. Сохранить release-путь, проверять без его запуска

Уточнение пользователя отменяет прежнее предложение отключить publish/deploy. Существующие `.github/workflows/check_and_deploy.yml`, quality jobs, branch triggers, release identity, image repositories, SHA/latest tags и credential references сохраняются. Добавить Buildx + setup-qemu перед сборкой, platforms `linux/amd64,linux/arm64` в существующем release build/push. Release `build_deploy` остаётся функциональным: `needs: test`, registry login → единый multiarch push → kubeconfig → `helm upgrade --install` своего release с `imageTag=${{ github.sha }}`, прежним namespace и `--wait`. Это описание конфигурации, **не разрешение выполнить команды**.

Сохранять **исходный event contract**, а не расширять набор событий ради acceptance. Не добавлять pull_request/workflow_dispatch, новые branch/path filters или отдельные check_image jobs. Уже добавленные backend/frontend PR/manual события и связанные проверочные jobs подлежат механической коррекции CI-EVENT-FIX. Не удалять PR/manual события, если иной исходный baseline их содержал; в семи проверенных baseline их нет. Existing site main triggers и release-only deploy guard сохраняются. Guard release-only workflow допустим, если не меняет исходные условия запуска; permissions не перепроектировать ради отсутствующих PR/manual ветвей. Не вводить if:false и не отключать публикацию/deploy. Root core release scope не расширять.

Три новых Python workflow следуют подтверждённому email/notification/VK-паттерну: **только push в release**, quality gate (`uv sync --locked`, lint/test), job с `needs: test`, `contents:read`, `packages:write`, GHCR login через `GITHUB_TOKEN`, Buildx/QEMU multiarch push SHA/latest, `KUBE_CONFIG`, setup-helm и deploy соответственно `eqcms-seo-service`, `eqcms-yandex-service`, `eqcms-ya-metrica-service` в cms. Никаких выдуманных PR/manual/main triggers. Chart opt-in defaults и private-peer isolation prerequisites сохраняются: наличие workflow не разрешает его запуск.

Локальные Docker/Helm/actionlint проверки выполняются отдельно от Actions; не нужен CI-only OCI job или новое событие. Проверять Dockerfile/context/platforms/build-arg mappings release-конфигурации, локально использовать synthetic public inputs вместо secret values. Локальный OCI archive не является опубликованным release и не доказывает production digest при иных inputs. Изменять удалённые SHA/latest tags в acceptance запрещено.

#### Минимальный diff — окончательная граница scope

Прямое уточнение пользователя: только образы amd64/arm64 и размещение на разных архитектурах; дополнительно исходный запрос о трёх новых charts/workflows. Не добавлять соседние улучшения: новые CI события, общий validator, security hardening, переименование Chart/release/resources, knobs placement без архитектурной необходимости, переработку CMD/увеличение runtime hygiene ради no-sync/offline. Имеющиеся исходные contracts/triggers/secrets сохраняются. Исторически выполненные изменения не считаются автоматически нужными и не откатываются целым файлом: correction снимает только наши лишние hunks, чужой diff не затрагивается.

Для пяти уже изменённых workflows baseline во всех случаях одинаков: `secrets.KUBE_CONFIG` → `~/.kube/config`, затем исходный setup-helm/Deploy. Новые три Python workflows используют тот же способ. Убрать введённые этим change kubeconfig env/mktemp/umask/KUBECONFIG/GITHUB_ENV/cleanup, не трогая другие независимые env/GITHUB_ENV настройки. Это сознательное возвращение исходного контракта, не задача по усилению/аудиту безопасности.

```yaml
- name: Set up kubeconfig
  run: |
    mkdir -p ~/.kube
    echo "${{ secrets.KUBE_CONFIG }}" | base64 -d > ~/.kube/config
```

Это конфигурационный образец с reference, не разрешение запускать его или читать secret values. Baseline source SHA пяти сервисов и точные blocks: `.qa/multiarch-service-charts/PLAN-111/kubeconfig-scope-before.json`. Использовать immutable SHA, а не текущий dirty workflow как baseline.

#### Ссылки и механизм secret injection

Инвентарь получен read-only из `.github/workflows/check_and_deploy.yml`, `.helm/values.yaml` и deployment/worker/migration templates семи существующих сервисов. Из инфраструктуры использованы только документация и metadata ключей несекретных templates: `/srv/EqCMS_Infra/charts/eqcms-infra/templates/workloads.yaml` (`secretKeyRef`), `backup.yaml` и `provision.yaml` (`envFrom.secretRef`/`secretKeyRef`); Secret manifests/data и реальные env не читались. `/srv/EqCMS_Infra/docs/OPERATIONS.md:112–126` требует отдельно согласовать источник секретов, `/srv/EqCMS_Infra/docs/CLUSTER.md` не подтверждает готовность production app secrets. Это evidence механизма, не подтверждение наличия/валидности секретов в GitHub или кластере. Новый ExternalSecrets/SealedSecrets/Vault механизм не вводится.

| Контур | Существующий паттерн / выбранная ссылка | Использование / граница |
|---|---|---|
| GHCR existing | backend/frontend/site-ad: согласована точечная замена `secrets.GH_TOKEN` → `secrets.GITHUB_TOKEN`; email/notification/VK/Inlove — прежний `secrets.GITHUB_TOKEN` | автоматически выдаваемый GitHub token; username/существующие contents:read/packages:write не менять; реальный GHCR package access отдельно unchecked |

| App runtime | `envFrom.secretRef.name: values.secretName` в app/worker/migration | новые defaults `eqsitecms-seo-service-secret`, `eqsitecms-yandex-service-secret`, `eqsitecms-ya-metrica-service-secret`; ссылки во всех процессах, без data/stringData/создания Secret |

Runtime secrets — namespaced: Secret для env и imagePullSecret должны существовать в namespace workload, ссылки на Secret в eqcms-infra не являются автоматическим cross-namespace доступом из cms. Оператор создаёт/заполняет их отдельно; агенты не читают data, не копируют инфраструктурные credentials, не создают production Secret и не исполняют provision Job. Для API/migration/scheduler/workers инъекция одинакова; отдельные app key names документируются по service `.env.example`/settings без значений. External secret name overrides валидируются рендером с synthetic names. HTTP/auth модель не меняется.

#### Согласованное исключение: только CI-BUILTIN-TOKEN

Пользователь явно подтвердил перевод backend/frontend/site-ad с ручного GH_TOKEN на встроенный `secrets.GITHUB_TOKEN`. Read-only сверка трёх текущих workflow: login-action password использует GH_TOKEN, username уже github.actor, build_deploy уже имеет contents:read/packages:write. Новые permissions/scopes/guards/events не нужны. Меняется **ровно один password reference на файл**, остальные YAML поля/байты сохранены; сравнивать с pre-unit working copy, не с HEAD целиком и не откатывать multiarch/чужую работу.

`GITHUB_TOKEN` автоматически создаётся/предоставляется GitHub Actions для repo/job и доступен как secrets.GITHUB_TOKEN; пользователь не должен вручную создавать одноимённый secret. Это только registry login credential выбора трёх jobs. Существующие Kubernetes imagePullSecrets (`ghcr-secret`, site-ad `ghcr-secret-ad`), KUBE_CONFIG и baseline ~/.kube/config не относятся к этой замене и не трогаются. Остальные secret references/public build mappings, triggers/guards/permissions/username/quality/build/deploy остаются прежними.

**Внешний GHCR prerequisite:** packages:write в workflow не доказывает write access к ранее созданному package. Package, опубликованный PAT и не связанный с repo/не выдающий этому Actions repo write access, может вернуть denied при GITHUB_TOKEN. Repo linkage/Manage Actions access на package стороне проверяет/настраивает оператор отдельно; агенты не читают tokens/Secret values, не запрашивают/меняют GH settings/registry и не пытаются publish для доказательства. Статический PASS — только корректность reference и неизменность конфигурации, не unconditional registry runtime PASS. Внешний доступ остаётся unchecked, без скрытого fallback на PAT.

Root doc имеет два релевантных GH_TOKEN упоминания: общая заметка backend/frontend и site-ad. Только их актуализировать и рядом кратко объяснить автоматическую выдачу token/внешний package access. Не переписывать SEO/прочие разделы и historical evidence. Один Backend unit временно владеет тремя workflow и этим узким doc фрагментом; пересекающиеся writers завершены/остановлены, после handoff вернуть ownership.

### 2. Только необходимые image portability fixes

Buildx/QEMU и `platforms: linux/amd64,linux/arm64` — целевые изменения. Обе платформы должны использовать подходящий base image и native-зависимости своего target, без ABI/exec-format ошибок. Если исходный Dockerfile уже работает на обеих, его не переписывать ради стиля. Нужные native fixes допустимы после конкретного reproducer; сохранение прежней логики и entrypoints — предпочтительный путь.

Не требовать no-sync/offline env, замены uv run на абсолютные CLI, multistage/slim/CMD/WORKDIR переработки, отключения reload/telemetry, новых cache/cleanup флагов или массового dockerignore как самостоятельного результата. Для уже изменённых пяти сервисов эти категории оцениваются в их существующих packaging units только по необходимости для target ABI/build, не автоматически откатываются. Например, исправление host node_modules/.venv contamination допустимо, если оно реально мешает target build; дополнительная hygiene сверх этого — нет. Смена Python/Node major или продуктового кода не следует из multiarch запроса.

### 3. Минимальные Helm changes

**Существующие charts:** если исходные PodSpec архитектурно нейтральны, их изменение не требуется. Снять только мешающие amd64/arm64 pin/hostname/affinity ограничения, если такие реально есть. Не навязывать новые placement values/пробросы nodeSelector/affinity/tolerations, namespace/Chart.name/selector/replica/strategy/probe/hook переработки и смену default tag. Исходные service identity, команды workers/migration, probes и defaults остаются, если необходимый image fix не требует строго связанной корректировки. Pre-existing дефект без отношения к архитектуре — отдельный вопрос, не этот change.

**Новые charts:** отдельные eqcms-seo-service/eqcms-yandex-service/eqcms-ya-metrica-service, namespace cms; image ghcr.io/igor-526/eqsitecms-<service> с SHA override, исходный Python image/tag/secretName/imagePullSecertName паттерн достаточен. API ClusterIP 8000, отдельный migration hook по существующему паттерну; Secrets/БД/брокеры/Ingress/NodePort/LoadBalancer не создавать. Peer DNS сохраняют eqsitecms-seo-service / eqsitecms-yandex-service / eqsitecms-ya-metrica-service. Внешние envFrom/pull references по решению 1, без literal secrets. `values.schema.json`, универсальные helpers и placement API не обязательны.

Процессы берутся из существующего runtime-контракта, не выдумываются: SEO API + один scheduler и opt-in maintenance OFF; Yandex API с его собственным lifecycle; Metrica API + opt-in parse worker/beat, cleanup/merge OFF, очереди ya_metrica/ya_metrica_cleanup/ya_metrica_merge. Singleton semantics и безопасные opt-in defaults сохраняются, запуска фоновых процессов в acceptance нет. Migration cwd/command/env должны соответствовать реальному образу; probes только существующих маршрутов/команд. Не требуется дополнительное security/lifecycle hardening, чтобы считать chart написанным.

### 3.3. Явно согласованный scheduler в том же workers template

Прочитаны только актуальные SEO values/workers/scheduler и SEO root-doc section. ## Risks / Trade-offs

- QEMU медленнее native → бюджеты и blocked вместо бесконечных retries; native arm runner — допустимая замена с явной записью environment.
- Lock/uv/Python 3.14 wheels могут оказаться несовместимы → минимальный packaging reproducer/fix либо stop; major upgrade требует нового согласования.
- Release CI сохраняет возможность публикации/deploy → агенты не пушат изменения и не запускают workflow; исходные triggers сохранены, acceptance статическая/локальная без новых событий. Фактический release выполняется только пользователем отдельно.
- Chart успешен статически, но secret/DNS/DB extension отсутствует → не обещать cluster-ready, описать operator prerequisites без чтения credentials.
- SERVICES.md частично устарел о VK/Inlove → использовать актуальные файлы и наблюдения выше; исправление общего сервисного каталога — отдельная согласуемая документационная работа, не расширять назначенный новый chart ownership.
- Parallel active change меняет build context → после handoff fingerprint freeze или scoped повтор, не менять чужие product files.
