# horse-service-relations-ui Specification

## Purpose
Зафиксировать требования к CMS-интерфейсу управления связями лошадь-услуга: кнопка в таблице лошадей, Drawer с таблицей, модальное окно добавления/редактирования.

## ADDED Requirements

### Requirement: Кнопка управления услугами в таблице лошадей
CMS SHALL отображать третью кнопку в колонке «Действия» таблицы лошадей для управления услугами лошади. Кнопка SHALL использовать иконку, связанную с финансами (например, `DollarOutlined` или `TransactionOutlined`). На кнопке SHALL отображаться количество связанных услуг (badge).

#### Scenario: Отображение кнопки с количеством услуг
- **WHEN**_authenticated CMS-пользователь открывает вкладку «Лошади» и у лошади 3 привязанные услуги
- **THEN** кнопка отображается с badge «3»

#### Scenario: Отображение кнопки без услуг
- **WHEN** authenticated CMS-пользователь открывает вкладку «Лошади» и у лошади нет привязанных услуг
- **THEN** кнопка отображается с badge «0» или без badge

#### Scenario: Кнопка не мешает другим действиям
- **WHEN** пользователь нажимает на кнопку «Фото» или «Родословная»
- **THEN** кнопка «Услуги» не перехватывает событие, другие кнопки работают корректно

### Requirement: Drawer с таблицей связанных услуг
При нажатии на кнопку «Услуги» CMS SHALL открывать `<Drawer>` справа на полэкрана с таблицей связанных услуг лошади. Drawer SHALL содержать заголовок с именем лошади и кнопку «Добавить».

#### Scenario: Drawer с привязанными услугами
- **WHEN** пользователь нажимает на кнопку «Услуги» лошади с 3 привязанными услугами
- **THEN** открывается Drawer справа, в котором отображается таблица с 3 строками (колонки: «Наименование», «Цена»)

#### Scenario: Drawer без привязанных услуг
- **WHEN** пользователь нажимает на кнопку «Услуги» лошади без привязанных услуг
- **THEN** открывается Drawer с NoData-заглушкой и направлением нажать кнопку «Добавить»

#### Scenario: Закрытие Drawer
- **WHEN** пользователь нажимает крестик или кнопку закрытия Drawer
- **THEN** Drawer закрывается, таблица лошадей остаётся в прежнем состоянии

### Requirement: Таблица связанных услуг в Drawer
Таблица в Drawer SHALL содержать 2 колонки: «Наименование» (название услуги) и «Цена» (цена с учётом override и форматтера). При нажатии на строку таблицы SHALL открываться модальное окно редактирования связи.

#### Scenario: Отображение цены с override
- **WHEN** связь имеет `price_override=600000` и `price_formatter_override=equal`
- **THEN** колонка «Цена» отображает «6 000 ₽» (override-значение)

#### Scenario: Отображение дефолтной цены
- **WHEN** связь не имеет override (все override-поля null)
- **THEN** колонка «Цена» отображает дефолтную цену услуги с дефолтным форматтером

#### Scenario: Клик по строке таблицы
- **WHEN** пользователь нажимает на строку таблицы связанных услуг
- **THEN** открывается модальное окно редактирования связи с заполненными полями

### Requirement: Модальное окно добавления связи
При нажатии на кнопку «Добавить» в Drawer CMS SHALL открывать модальное окно с Select для выбора услуги и полями override (description, price, price_formatter). Select SHALL показывать только услуги, ещё не привязанные к данной лошади.

#### Scenario: Открытие модального окна создания
- **WHEN** пользователь нажимает «Добавить» в Drawer
- **THEN** открывается модальное окно с Select (доступные услуги), полем «Описание» (override), Radio.Group для форматтера цены и полем «Цена» (override)

#### Scenario: Выбор услуги из Select
- **WHEN** пользователь выбирает услугу из Select
- **THEN** поля формы заполняются дефолтными значениями выбранной услуги (для reference)

#### Scenario: Успешное создание связи
- **WHEN** пользователь выбирает услугу, задаёт override-поля и нажимает «Добавить»
- **THEN** модальное окно закрывается, таблица в Drawer обновляется, badge на кнопке «Услуги» увеличивается

#### Scenario: Валидация — услуга не выбрана
- **WHEN** пользователь нажимает «Добавить» без выбора услуги
- **THEN** отображается ошибка валидации «Выберите услугу»

### Requirement: Модальное окно редактирования/удаления связи
При нажатии на строку таблицы CMS SHALL открывать модальное окно в режиме редактирования с полями override и кнопками «Изменить» и «Удалить». Выбор услуги readonly.

#### Scenario: Открытие модального окна редактирования
- **WHEN** пользователь нажимает на строку таблицы связанных услуг
- **THEN** открывается модальное окно с readonly Select (выбранная услуга), заполненными override-полями, кнопками «Изменить» и «Удалить»

#### Scenario: Успешное обновление связи
- **WHEN** пользователь изменяет override-поля и нажимает «Изменить»
- **THEN** модальное окно закрывается, таблица в Drawer обновляется с новыми значениями

#### Scenario: Удаление связи
- **WHEN** пользователь нажимает «Удалить» и подтверждает в Popconfirm
- **THEN** модальное окно закрывается, строка удаляется из таблицы, badge на кнопке «Услуги» уменьшается

#### Scenario: Ошибка backend при создании/обновлении
- **WHEN** backend возвращает ошибку валидации (например, дублирование связи)
- **THEN** модальное окно отображает ошибку, не закрывается, данные формы сохраняются

### Requirement: Scope-aware UX для управления связями
CMS SHALL скрывать или отключать кнопку «Добавить» и кнопки редактирования/удаления, если пользователь не имеет horse write scope. Проверка scope MUST NOT заменять backend-авторизацию.

#### Scenario: Пользователь без horse write scope
- **WHEN** authenticated пользователь без horse write scope открывает Drawer
- **THEN** кнопка «Добавить» скрыта или disabled, строки таблицы не открывают модальное окно редактирования

#### Scenario: Пользователь с horse write scope
- **WHEN** authenticated пользователь с horse write scope открывает Drawer
- **THEN** кнопка «Добавить» активна, клик по строке открывает модальное окно редактирования

### Requirement: Изолированная frontend test boundary для связей
Frontend tests для управления связями лошадь-услуга SHALL выполняться в jsdom с MSW server, SHALL считать любой необработанный сетевой запрос ошибкой и SHALL проверять API serialization, `401/403`, scopes и UI states без live backend.

#### Scenario: Тест вызывает API flow связей
- **WHEN** тест обращается к CMS API boundary для связей с зарегистрированным MSW handler
- **THEN** ответ формируется handler-ом и тест проверяет query/body/status behavior без внешней сети

#### Scenario: Тест пытается обратиться к live backend
- **WHEN** код теста выполняет запрос без MSW handler
- **THEN** `onUnhandledRequest: "error"` завершает тест ошибкой

### Requirement: Frontend test matrix для связей
Изменение SHALL иметь unit/component/API-boundary coverage через Vitest, React Testing Library и MSW без live backend calls, а Manual QA MUST покрывать desktop/tablet/mobile, auth, permissions, ошибки и успешное обновление.

#### Scenario: Автоматизированное frontend evidence
- **WHEN** исполнитель завершает frontend deliverable
- **THEN** тесты покрывают data/loading/empty/error, search backend Select, modal create/update/delete/validation/error/refresh, anonymous/authenticated и применимые scope/`401/403` cases

#### Scenario: Backend denial и состояние формы
- **WHEN** Protected Write для связи возвращает validation error, generic error, `401` или `403`
- **THEN** modal не показывает ложный успех, сохраняет значения полей и отображает доступную ошибку для исправления либо повторной попытки

#### Scenario: Double submit protection
- **WHEN** разрешённый пользователь дважды нажимает submit в модальном окне связи
- **THEN** отправляется не более одного запроса

#### Scenario: Protected Admin route для управления связями
- **WHEN** anonymous или authenticated пользователь открывает `/horses`
- **THEN** anonymous перенаправлен/заблокирован, а authenticated пользователь видит кнопку «Услуги» согласно scopes

#### Scenario: Изоляция consumer-контура для связей
- **WHEN** reviewer проверяет frontend diff для horse service relations UI
- **THEN** `services/site-ad` не изменён, CMS не импортирует `site-*`/Public Read consumer runtime и существующая `limit/offset` pagination не регрессирует

### Requirement: Безопасная валидация модального окна связи
CMS horse UI SHALL отображать ошибки каждого поля связи только из массива соответствующего ключа и SHALL сохранять введённое состояние после backend validation, generic, `401` или `403` error.

#### Scenario: Ошибка backend при создании связи
- **WHEN** backend возвращает ошибку валидации (например, `409` дублирование связи)
- **THEN** modal отображает ошибку, не закрывается, данные формы сохраняются

#### Scenario: Ошибка backend при обновлении связи
- **WHEN** backend возвращает ошибку при обновлении override-полей
- **THEN** modal отображает ошибку, не закрывается, данные формы сохраняются

#### Scenario: Пустые override-поля
- **WHEN** пользователь создаёт или обновляет связь, оставив override-поля пустыми
- **THEN** CMS отправляет Protected Write один раз, не показывает клиентскую ошибку обязательности этих полей и после успеха обновляет таблицу с дефолтными значениями услуг
