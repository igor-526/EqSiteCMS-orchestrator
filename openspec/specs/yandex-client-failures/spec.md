# Purpose

Единый контракт клиентских ошибок интеграции Яндекс и Метрики: безопасная диагностика, преобразование ошибок сервисами и сохранение допустимого частичного результата.

## Requirements

### Requirement: Единственный тип ошибки на границе клиента

`YandexOAuthClient` и `YaMetricaServiceClient` в yandex-service, а также `YandexMetricaClient` в ya-metrica-service SHALL при любой обычной неудаче выполнения запроса или обработки его ответа выбрасывать локальный `core.exceptions.yandex.YandexClientException`, а не HTTP/framework/domain исключение. Контракт распространяется на `make_request` и высокоуровневые методы, включая DTO validation. Клиент SHALL сохранять исходную причину через chaining и закрывать HTTP client. Повторный `YandexClientException` MUST NOT оборачиваться повторно. Отмена задачи и системные `BaseException` SHALL распространяться без превращения в интеграционную ошибку; клиент MUST NOT перехватывать `BaseException`.

#### Scenario: Успешный запрос
- **WHEN** upstream возвращает 2xx с корректными JSON и схемой ожидаемого метода
- **THEN** клиент возвращает прежний успешный результат, сохраняя параметры запросов, пагинацию, auth headers и timeout по умолчанию 10 секунд

#### Scenario: Timeout и transport
- **WHEN** connect/read/write/pool timeout, DNS/connect/TLS/protocol/transport ошибка возникает при входе, запросе или закрытии HTTP client
- **THEN** наружу выходит ровно локальный `YandexClientException` с безопасной категорией и исходной причиной, без сырого httpx исключения

#### Scenario: Неуспешный HTTP upstream
- **WHEN** upstream возвращает статус вне 200..299, включая 3xx, 401, 403, 429 или 5xx, с JSON, HTML либо пустым телом
- **THEN** клиент выбрасывает `YandexClientException`, сохраняет доступный upstream status для диагностики и не выпускает JSON decoding error

#### Scenario: Непригодный успешный ответ
- **WHEN** upstream возвращает 2xx с пустым телом, malformed JSON, JSON не-object, отсутствующими полями либо неверными типами top-level структуры/DTO, делающими ответ непригодным целиком (не отдельным пропускаемым счётчиком)
- **THEN** клиент выбрасывает `YandexClientException`, а не JSON/Pydantic/TypeError и не успешный частичный результат; существующий пропуск отдельного некорректного счётчика регулируется отдельным требованием и не является этим отказом

#### Scenario: Отмена и повторное исключение
- **WHEN** во время вызова приходит отмена задачи или уже возник `YandexClientException`
- **THEN** отмена распространяется как отмена, а существующий `YandexClientException` не получает повторной обёртки

### Requirement: Локальные исключения и безопасная диагностика

Оба сервиса SHALL использовать собственный уже существующий класс `YandexClientException`; cross-service Python import и новая общая runtime-библиотека MUST NOT вводиться. Поле `status` конструктора SHALL допускать отсутствие HTTP-ответа (`None`), сохраняя совместимость существующих вызовов с числом и `.message`. Никакой фиктивный upstream HTTP status для timeout SHALL не создаваться. Тексты исключения, HTTP payload, stdout и контролируемые приложением логи MUST NOT содержать code, client_secret, access/refresh token, Authorization, полный URL с токеном, полный upstream body или персональные данные.

#### Scenario: Ответ не получен
- **WHEN** возникает timeout до получения HTTP-ответа
- **THEN** локальное исключение содержит `status=None` и безопасную категорию, а `ClientError` не включает исходный URL или текст transport исключения

#### Scenario: Upstream прислал секрет в ошибке
- **WHEN** upstream body либо текст исходного исключения содержит секрет-маркер
- **THEN** маркер отсутствует в `.message`, ответе HTTP и контролируемых логах/stdout; причина доступна только через внутренний chaining без её сырого вывода

### Requirement: Преобразование клиентской ошибки сервисом

OAuth service SHALL ловить `YandexClientException` отдельно при обмене кода и получении профиля; оба Metrica service SHALL ловить его при своём вызове клиента. Сервисы MUST преобразовывать его в `ClientError` с безопасным русским сообщением и chaining; роутеры SHALL не выполнять это преобразование. При отказе OAuth до завершения получения валидного профиля сервис MUST NOT записывать аккаунт.

#### Scenario: Ошибка обмена кода или профиля
- **WHEN** любой из двух OAuth-вызовов выбрасывает `YandexClientException`, включая timeout
- **THEN** сервис выбрасывает `ClientError`, HTTP-ответ равен `400` с `detail`, а запись аккаунта не выполняется

#### Scenario: Сквозной отказ Метрики
- **WHEN** клиент Метрики или клиент ya-metrica-service выбрасывает `YandexClientException`
- **THEN** соответствующий сервис преобразует его в `ClientError`, и прямой либо проксированный endpoint Метрики возвращает `400`, а не 500/502/504

### Requirement: Валидация ответа Метрики с сохранением частичного списка

`YandexMetricaClient.get_counters` SHALL проверять top-level структуру upstream `rows/counters`, сохраняя wire-compatible dict-контракт Protocol и успешное преобразование числовых строк. Отсутствующий/null/нечисловой `rows`, отсутствующий или не-list `counters` SHALL считаться неудачей всего вызова с `YandexClientException`. Некорректный отдельный счётчик (не-object элемент, некорректные `id/site`) MUST NOT превращать весь клиентский вызов в отказ: существующее пропускание таких элементов и частичный список корректных элементов SHALL сохраняться. Обработка элементов MUST NOT выпускать наружу raw TypeError/ValueError. Конвертация в прежний API DTO `total/items` остаётся в сервисе; существующая семантика `total` и пустого результата, в том числе после пропуска элементов, SHALL сохраняться без новых правил пересчёта или отказа. Общее требование об ошибках схемы относится к непригодному целиком ответу/DTO, а не к допускаемому пропуску отдельного счётчика.

#### Scenario: Некорректный отдельный счётчик
- **WHEN** top-level ответ валиден, но среди корректных счётчиков есть повреждённый элемент
- **THEN** элемент пропускается по существующему поведению, корректные элементы возвращаются частичным списком с `200`; весь вызов не становится `YandexClientException`

#### Scenario: Непригодный целиком ответ Метрики
- **WHEN** происходят timeout/transport/HTTP failure, JSON целиком невалиден либо top-level ответ непригоден (`rows=null`, `counters` отсутствует или имеет неверный тип)
- **THEN** весь вызов завершается `YandexClientException → ClientError → 400`; частичный `200` не скрывает эти отказы

#### Scenario: Пустой валидный список
- **WHEN** upstream возвращает валидный пустой список либо после существующего пропуска элементов не остаётся корректных счётчиков
- **THEN** сохраняется существующее поведение пустого результата и `total/items`, без введения новых правил этим change
