# seo-parse-scheduling Specification

## Purpose
Ежедневное автоматическое управление парсингом в seo-service: время и часовой пояс из `.env`, выбор конюшен с настроенной интеграцией через реестр провайдеров, гарантия «один раз в сутки на конюшню и провайдера» и расширяемость под будущих клиентов парсинга.

## Requirements

### Requirement: Настройки расписания в .env seo-service
seo-service SHALL читать из собственного `.env`: `PARSE_SCHEDULE_ENABLED` (по умолчанию `true`), `PARSE_SCHEDULE_TIME` (`HH:MM`, по умолчанию `03:00`), `PARSE_SCHEDULER_TICK_SECONDS` (по умолчанию `30`), `PARSE_PROVIDERS_ENABLED` (список кодов, по умолчанию `ya_metrica`), `PARSE_TARGETS_PAGE_SIZE`, `PARSE_DISPATCH_MAX_ATTEMPTS`. Часовой пояс конюшен — существующий `SEO_UTC_OFFSET_HOURS`. Невалидное значение MUST отклонять загрузку конфигурации.

#### Scenario: Значения по умолчанию
- **WHEN** в `.env` нет параметров расписания
- **THEN** расписание включено, время `03:00` по поясу `SEO_UTC_OFFSET_HOURS`, активен провайдер `ya_metrica`

#### Scenario: Некорректное время
- **WHEN** `PARSE_SCHEDULE_TIME` равен `25:00`, `3:7` или пустой строке
- **THEN** загрузка конфигурации отклоняется до старта процесса

#### Scenario: Неизвестный провайдер в списке
- **WHEN** `PARSE_PROVIDERS_ENABLED` содержит код, которого нет в реестре
- **THEN** загрузка конфигурации или сборка контейнера завершается ошибкой с понятным сообщением

### Requirement: Ежедневный слот по локальному времени конюшни
Scheduler SHALL считать слот наступившим, когда локальное время (UTC + `SEO_UTC_OFFSET_HOURS`) не раньше `PARSE_SCHEDULE_TIME`, и закреплять слот за локальной датой. Пропущенный слот SHALL догоняться в пределах той же локальной даты (например, после рестарта); на следующую дату пропущенный слот не переносится.

#### Scenario: До времени запуска
- **WHEN** локальное время `02:59`, расписание `03:00`
- **THEN** ни одна команда не публикуется

#### Scenario: Наступление слота
- **WHEN** локальное время становится `03:00` или позже и слот локальной даты ещё не выполнен
- **THEN** для каждой цели каждого активного провайдера публикуется команда `trigger=schedule`

#### Scenario: Смена суток на границах пояса
- **WHEN** смещение `-12` либо `14`, а UTC-момент пересекает полночь
- **THEN** локальная дата и признак наступления слота вычисляются по локальному времени

#### Scenario: Расписание выключено
- **WHEN** `PARSE_SCHEDULE_ENABLED=false`
- **THEN** scheduler ничего не публикует, ручной endpoint остаётся доступным

### Requirement: Цели — конюшни с привязанным счётчиком
Список целей `ya_metrica` SHALL браться у yandex-service постранично (`GET /api/connections/metrica`) и содержать только конюшни с привязанным счётчиком. Конюшня без привязки MUST NOT получать команду. Недоступность источника целей MUST NOT приводить к публикации и к записи слота как выполненного; следующий tick SHALL повторить попытку.

#### Scenario: Только привязанные конюшни
- **WHEN** yandex-service возвращает три привязки
- **THEN** публикуются ровно три команды с `equestrian_id` этих привязок

#### Scenario: Источник целей недоступен
- **WHEN** запрос списка привязок завершается таймаутом или не-2xx
- **THEN** warning без секретов, команды не публикуются, слот не отмечается, следующий tick повторяет попытку

### Requirement: Один раз в сутки на конюшню и провайдера
Ledger `parse_dispatches` в PostgreSQL seo-service SHALL гарантировать уникальность `(provider, equestrian_id, schedule_date)` для `trigger=schedule`. Публикация SHALL выполняться только после захвата записи слота; параллельные scheduler-процессы MUST NOT публиковать один слот дважды. Неуспешная публикация SHALL позволять повтор в тот же день до `PARSE_DISPATCH_MAX_ATTEMPTS`; зависший захват SHALL становиться доступным для повторного захвата по тайм-ауту.

#### Scenario: Рестарт после выполнения
- **WHEN** scheduler перезапущен в тот же день после успешной публикации всех целей
- **THEN** новые команды не публикуются

#### Scenario: Два scheduler-процесса
- **WHEN** два процесса одновременно захватывают слот одной конюшни
- **THEN** ровно один публикует команду, второй пропускает цель

#### Scenario: Сбой NATS при публикации
- **WHEN** публикация цели завершилась ошибкой
- **THEN** запись получает статус `failed`, остальные цели обрабатываются, повтор в следующем tick, после исчерпания попыток — error в лог и слот остаётся `failed`

#### Scenario: Ручной запуск не занимает слот
- **WHEN** выполнен ручной запуск `trigger=manual`
- **THEN** он не занимает слот расписания и не мешает ежедневному запуску

### Requirement: Окно дат — автоматическое
Команда расписания SHALL содержать `window={"mode":"auto"}`. Потребитель определяет диапазон по последней сохранённой статистике и своей текущей дате; seo-service MUST NOT вычислять даты парсинга. При ежедневной работе после успешного вчерашнего запуска окно — вчера и сегодня (2 дня): вчерашние данные обновляются, сегодняшние добавляются.

#### Scenario: Штатный ежедневный запуск
- **WHEN** последняя статистика конюшни датирована вчера, команда с `mode=auto` обработана
- **THEN** потребитель ставит окно «вчера..сегодня»

#### Scenario: Пропуск нескольких дней
- **WHEN** последняя статистика датирована пятью днями ранее
- **THEN** окно покрывает период от последней даты до сегодня без пробелов

### Requirement: Расширяемый реестр провайдеров парсинга
seo-service SHALL работать с провайдерами через единый протокол и реестр: код, subject, источник целей, проверка применимости к конюшне, сборка `params`. Scheduler, ручной endpoint, ledger и публикация MUST NOT содержать провайдер-специфичной логики; тестовый провайдер, зарегистрированный в тесте, SHALL проходить весь путь без правок этих компонентов.

#### Scenario: Фейковый провайдер
- **WHEN** в тесте регистрируется провайдер `demo` с одной целью
- **THEN** scheduler публикует команду в `commands.parse.demo.run`, ledger хранит запись `provider=demo`, код scheduler и API не менялся

#### Scenario: Отключённый провайдер
- **WHEN** провайдер зарегистрирован, но отсутствует в `PARSE_PROVIDERS_ENABLED`
- **THEN** scheduler и ручной endpoint не публикуют для него команды

### Requirement: Процесс scheduler и устойчивость
Scheduler SHALL работать отдельным контейнером `seo-scheduler` (один экземпляр, тот же образ seo-service), подключаться к NATS и PostgreSQL, корректно завершаться по сигналу и не падать из-за единичной ошибки цели или провайдера. Недоступность NATS при старте MUST приводить к повторным попыткам подключения, а не к немедленному завершению.

#### Scenario: Ошибка одной цели
- **WHEN** обработка одной конюшни завершилась исключением
- **THEN** остальные цели и провайдеры текущего tick обрабатываются

#### Scenario: NATS недоступен при старте
- **WHEN** scheduler стартует при остановленном брокере
- **THEN** подключение повторяется с backoff, ошибка эскалируется один раз за инцидент, после появления брокера расписание работает

### Requirement: Доступ scheduler к peer-сервисам
Scheduler SHALL быть внутренним процессом без пользовательских прав и HTTP-endpoint'ов; к yandex-service он обращается только по Private Peer Read `GET /api/connections/metrica` (`yandex-metrica-binding-list`), а команды публикует в NATS (`parse-job-messaging`). Ручной endpoint описан в `seo-parse-trigger-api`.

#### Scenario: Нет публичной поверхности
- **WHEN** QG проверяет контейнер `seo-scheduler`
- **THEN** он не публикует портов и не обслуживает HTTP
