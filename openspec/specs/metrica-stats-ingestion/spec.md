# metrica-stats-ingestion Specification

## Purpose
Выполнение задания парсинга Яндекс.Метрики: подготовка кредов сервисным слоем, постраничная выгрузка Reporting API, ELT-фиксация каждой страницы с checkpoint, резолв страниц и фраз в UUID через seo-service и безопасное логирование.

## Requirements

### Requirement: Креды резолвит сервисный слой

Перед выгрузкой сервисный слой SHALL получить привязку счётчика конюшни из yandex-service, сверить её с заданием, получить зашифрованный токен аккаунта и расшифровать его общим ключом `ENCRYPTION_SERVICE_KEY`. Клиент Метрики SHALL получать уже готовые счётчик, открытый токен, вид и окно; открытый токен MUST NOT сохраняться в БД или логах.

#### Scenario: Готовое задание для клиента
- **WHEN** привязка конюшни совпадает с `counter_id` и `yandex_account_id` задания и ciphertext расшифровывается
- **THEN** клиент вызывается со счётчиком задания и открытым токеном только в памяти процесса

#### Scenario: Привязка изменилась или удалена
- **WHEN** yandex-service возвращает `counter=null` или другой счётчик/аккаунт для конюшни
- **THEN** задание становится `failed` с `error_code=binding_changed` без запросов к Метрике

#### Scenario: Токен не расшифровывается
- **WHEN** ciphertext повреждён или зашифрован другим ключом
- **THEN** задание становится `failed` с `error_code=credentials_invalid`, Метрика не вызывается

### Requirement: Запрос к Reporting API

Клиент SHALL вызывать `GET https://api-metrika.yandex.net/stat/v1/data` с header `Authorization: OAuth <token>`, `ids=<counter_id>`, metrics `ym:s:visits,ym:s:users,ym:s:pageviews,ym:s:bounceRate,ym:s:pageDepth,ym:s:avgVisitDurationSeconds`, dimensions набора, `date1/date2` окна, `accuracy=full`, стабильной сортировкой `sort=ym:s:date,<dimension набора>`, `limit` и 1-based `offset`. Токен MUST NOT передаваться в query.

#### Scenario: Параметры набора «запросы»
- **WHEN** выполняется задание `search_queries` за `2026-10-21..2026-10-25` с лимитом страницы 100000
- **THEN** первый запрос содержит `dimensions=ym:s:date,ym:s:lastSearchPhrase`, `sort=ym:s:date,ym:s:lastSearchPhrase`, `limit=100000`, `offset=1`, `accuracy=full`, токен только в header

### Requirement: Постраничная выгрузка до конца

Задание SHALL запрашивать страницы последовательно максимальным размером (по умолчанию 100000 — максимум API), продвигая `offset` на число полученных строк, пока `offset` не превысит `total_rows` или страница не вернётся пустой. Запросы одного задания MUST NOT выполняться параллельно.

#### Scenario: Несколько страниц
- **WHEN** `total_rows=35`, а лимит страницы равен 10
- **THEN** выполняются ровно 4 последовательных запроса с `offset` 1, 11, 21, 31

#### Scenario: Пустой результат
- **WHEN** за окно `total_rows=0`
- **THEN** выполняется один запрос, задание завершается `succeeded` с нулевыми счётчиками строк

### Requirement: ELT-фиксация каждой страницы с checkpoint

Строки каждой страницы API SHALL записываться в БД в отдельной транзакции сразу после получения, вместе с обновлением checkpoint следующего `offset` задания. Результаты MUST NOT накапливаться в памяти между страницами. Повтор задания SHALL продолжать выгрузку с сохранённого checkpoint.

#### Scenario: Сбой после первой страницы
- **WHEN** первая страница зафиксирована, а запрос второй страницы завершился временной ошибкой
- **THEN** строки первой страницы и `next_offset` второй страницы сохранены, повтор начинается со второй страницы и не дублирует значения первой

#### Scenario: Сбой записи страницы
- **WHEN** запись строк страницы в БД завершилась ошибкой
- **THEN** транзакция откатывается целиком: ни строки этой страницы, ни checkpoint не сохраняются

### Requirement: Разбор строк ответа

Ответ SHALL проверяться по оболочке (`data` — список, `total_rows` — целое); непригодная оболочка SHALL завершать попытку ошибкой `provider_response_invalid`. Отдельная строка с некорректной датой, неверным числом метрик, нецелым значением счётчиковых метрик либо датой вне окна SHALL пропускаться и учитываться в счётчике пропущенных.

#### Scenario: Непригодная строка
- **WHEN** в странице из 10 строк одна содержит 5 метрик вместо 6
- **THEN** сохраняются 9 строк, `rows_skipped` увеличивается на 1, задание не падает

#### Scenario: Сэмплирование
- **WHEN** ответ содержит `sampled=true` или `total_rows_rounded=true`
- **THEN** данные сохраняются, задание помечается флагом сэмплирования и пишется warning-лог

### Requirement: Пустые измерения не сохраняются

Строки, у которых значение измерения страницы или фразы равно `null` или пусто после trim (в Метрике это «не определено»), SHALL пропускаться без обращения к seo-service и учитываться в счётчике пропущенных.

#### Scenario: Фраза не определена
- **WHEN** строка набора «запросы» содержит `{"name": null}` во втором измерении
- **THEN** строка не сохраняется, `rows_skipped` увеличивается

### Requirement: Резолв сущностей через seo-service

Уникальные значения измерения страницы API SHALL резолвиться в UUID вызовами `POST /api/pages/resolve` или `POST /api/search-queries/resolve` seo-service с header `X-Equestrian-Id` конюшни задания, пакетами не более 1000 значений. Строки SHALL сопоставляться UUID по исходному значению.

#### Scenario: Пакетирование
- **WHEN** страница API содержит 2500 уникальных URL
- **THEN** выполняются 3 resolve-запроса (1000, 1000, 500) с `X-Equestrian-Id` конюшни, и каждая строка получает UUID своего URL

#### Scenario: Отказ seo-service для части пакета
- **WHEN** seo-service отвечает 400 на пакет из-за одного невалидного значения
- **THEN** пакет делится, невалидные значения пропускаются и учитываются в `rows_skipped`, остальные строки сохраняются

#### Scenario: seo-service недоступен
- **WHEN** resolve завершается таймаутом, транспортной ошибкой или 5xx
- **THEN** транзакция страницы не выполняется, попытка завершается временной ошибкой `seo_unavailable`

### Requirement: Логирование выполнения

Сервис SHALL логировать старт задания (ID задания и запуска, конюшня, вид, окно, попытка), завершение (статус, число страниц API, полученных, вставленных, обновлённых, пропущенных и удалённых сверкой строк, длительность) и каждую ошибку с безопасной категорией. Логи MUST NOT содержать открытый токен, ciphertext, тело ответа API или тексты фраз.

#### Scenario: Счётчик вставок
- **WHEN** задание записало 30 новых строк и обновило 5 существующих
- **THEN** лог завершения содержит `inserted=30` и `updated=5`

#### Scenario: Секреты отсутствуют в логах
- **WHEN** задание завершается ошибкой Метрики 403
- **THEN** лог содержит категорию `credentials_invalid` и HTTP-статус, но не содержит токен, ciphertext и тело ответа

### Requirement: Общий базовый HTTP-клиент

Клиенты Метрики (счётчики и статистика) и peer-клиенты SHALL использовать общий базовый клиент с единым безопасным преобразованием HTTP/таймаут/транспорт/ответ-ошибок в исключение с HTTP-статусом и категорией. Существующий контракт `GET /api/metrica/counters` MUST NOT меняться.

#### Scenario: Регрессия списка счётчиков
- **WHEN** после рефакторинга вызывается `GET /api/metrica/counters` с пригодным ciphertext
- **THEN** исходящий запрос, ответ и ошибки совпадают с действующей capability `ya-metrica-adapter`

#### Scenario: Классификация статуса
- **WHEN** Метрика отвечает 429 на запрос статистики
- **THEN** клиент выбрасывает исключение с `status=429` и категорией `http`, по которому сервисный слой планирует повтор
