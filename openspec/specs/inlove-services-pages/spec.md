# Purpose

Зафиксировать SSR-композицию трёх публичных страниц услуг INLOVE (`/uslugi/zanyatiya`, `/uslugi/progulki`, `/uslugi/postoy`) и их detail routes по slug тарифа, включая scoping тарифов к своей странице (allow-list), fallback цен, SEO/canonical, responsive-таблицы и 404-поведение для чужих/несуществующих slug.

## Requirements

### Requirement: Три страницы услуг рендерят SSR-контент из профильного API
`/uslugi/zanyatiya`, `/uslugi/progulki`, `/uslugi/postoy` SHALL быть SSR-композициями, в которых соответствующая группа находится по точному неизменяемому имени из consumer config (`Занятия`, `Прогулки`, `Постой` соответственно), а описание, фотографии, карточки и цены поступают из существующих профильных Public Read API. Site settings `services.*`, `services.notice`, `home.program_benefits`, `about.setting`, `about.features` и service-specific `seo.*` MUST NOT управлять страницами. Дополнительные presentation-блоки MAY быть статическими в consumer-коде и MUST NOT возвращаться в CMS catalog.

Видимость и состояние карточек тарифов (успех/пусто/ошибка) SHALL определяться исключительно ответом собственного price-group Public Read запроса страницы (`GET /api/prices?groups=...`). Отдельный дескриптор описания страницы (точное совпадение имени в каталоге `horse_services`) MUST NOT подменять или скрывать уже успешно загруженные карточки тарифов: его отсутствие, переименование или дублирование MAY приводить только к отсутствию description-текста и SEO description (с существующим статическим fallback), но MUST NOT приводить к странице «услуга временно недоступна» при доступных тарифах.

#### Scenario: Страница услуг использует точное имя группы
- **WHEN** anonymous visitor открывает одну из трёх страниц и API содержит группу с настроенным точным именем
- **THEN** SSR HTML содержит данные только этой группы и её сущностей, без чтения service site settings

#### Scenario: Группа отсутствует или переименована
- **WHEN** API не возвращает exact-match группу для страницы
- **THEN** страница показывает локальный error/empty state и CTA, не использует fuzzy matching и не подмешивает другую группу

#### Scenario: Ошибка API не блокирует оболочку
- **WHEN** профильный API завершается сетевой ошибкой или 5xx
- **THEN** header/footer и статическая часть страницы остаются доступными, а динамический блок показывает error state

#### Scenario: Карточки тарифов не зависят от отдельной группы-описания
- **WHEN** price-group Public Read запрос страницы возвращает тарифы успешно, а отдельный дескриптор описания (`horse_services`, точное имя «Занятия»/«Прогулки»/«Постой») пуст, переименован или дублирован
- **THEN** страница отображает карточки тарифов как обычно, без сообщения о недоступности услуги; отсутствует только текстовое описание/SEO description группы, для которых уже используется статический fallback

#### Scenario: Реально отсутствующие тарифы показывают пустое состояние независимо от группы-описания
- **WHEN** price-group Public Read запрос страницы возвращает пустой список или завершается ошибкой
- **THEN** страница показывает соответствующий `EmptyState` с CTA либо `ErrorBlock` с retry для блока цен, независимо от состояния отдельного дескриптора описания

### Requirement: Detail route тарифа по slug, ограниченный своей страницей
Каждая из трёх страниц услуг SHALL обслуживать `/uslugi/zanyatiya/[slug]`, `/uslugi/progulki/[slug]`, `/uslugi/postoy/[slug]` соответственно, используя `GET /api/prices/{slug_or_id}`. Detail route MUST принимать только slug тарифа, принадлежащего набору тарифов родительской страницы (тот же allow-list, что определяет список карточек). Slug, не входящий в allow-list своей страницы (включая валидный slug тарифа другой группы/страницы того же tenant), MUST возвращать `404` через `notFound()`.

#### Scenario: Валидный slug своей страницы рендерится
- **WHEN** anonymous visitor открывает `/uslugi/progulki/horse-rides-official`
- **THEN** HTML содержит серверно отрендеренные name, description, photos и price_tables тарифа

#### Scenario: Slug чужой страницы недоступен
- **WHEN** anonymous visitor открывает `/uslugi/zanyatiya/<slug-тарифа-постоя>`
- **THEN** Next.js возвращает `404`, даже если `GET /api/prices/{slug_or_id}` для этого slug у backend вернул бы `200`

#### Scenario: Несуществующий или чужой tenant slug
- **WHEN** `GET /api/prices/{slug_or_id}` возвращает `404` для несуществующего или принадлежащего другому tenant slug
- **THEN** Next.js возвращает `404`

### Requirement: SEO и доступ по карте услуг
Три list-страницы SHALL иметь серверные title/description из consumer config и/или описания exact-match группы API, canonical на собственный путь. Detail routes SHALL формировать title/description из полей сущности API. Удалённые `seo.lessons.*`, `seo.rides.*`, `seo.boarding.*` и `site.short_name` MUST NOT влиять на metadata. Используемые GET SHALL оставаться Public Read с tenant selector.

| Method | Path | Access class | Роли | Без/с неверным selector | С корректным selector |
|---|---|---|---|---|---|
| `GET` | используемые `/api/horse_services*` | Public Read | нет | `401` | `200/404` tenant-scoped |
| `GET` | `/api/prices`, `/api/prices/{slug_or_id}` | Public Read | нет | `401` | `200` своего tenant; `404` чужого tenant/несуществующий |

#### Scenario: Metadata доступна без hydration
- **WHEN** crawler получает HTML list либо detail страницы без клиентского JavaScript
- **THEN** HTML содержит route-specific title, description и canonical без зависимости от удалённых SEO settings

#### Scenario: Анонимный доступ без tenant selector
- **WHEN** запрос к используемому GET выполнен без selector или с неверным значением
- **THEN** API возвращает `401`

### Requirement: Адаптивная вёрстка страниц услуг
Список и detail каждой из трёх страниц SHALL быть адаптивными: desktop — две колонки и полноценные таблицы price_tables; mobile — одна колонка, таблица преобразуется в пары «параметр — значение» либо получает управляемый горизонтальный скролл. Detail route наследует тот же адаптивный паттерн таблиц, что и список.

#### Scenario: Мобильная раскладка таблицы тарифа
- **WHEN** страница услуги или её detail route открыта на viewport мобильной ширины
- **THEN** `price_tables` отображается как пары «параметр — значение» либо в контейнере с управляемым горизонтальным скроллом, без горизонтального скролла всей страницы

### Requirement: Сетка карточек тарифов плотнее на desktop и компактнее на mobile
На каждой из трёх страниц услуг сетка карточек тарифов SHALL показывать три карточки в ряд на desktop (вместо двух). На mobile изображение карточки SHALL занимать меньшую долю карточки, чем на desktop (уменьшенное/менее доминирующее соотношение сторон), чтобы на экран помещалось больше карточек одновременно. Название тарифа в карточке SHALL отображаться полужирным начертанием (минимум `font-weight: 700`), визуально отличимым от остального текста карточки. На desktop клик по изображению карточки SHALL переводить на detail-страницу тарифа (`/uslugi/{zanyatiya|progulki|postoy}/[slug]`); на mobile клик по изображению MUST NOT инициировать переход (переход остаётся доступен через текстовую ссылку «Подробнее»).

#### Scenario: Desktop grid и переход по изображению
- **WHEN** страница услуги отображается на desktop viewport (≥1024px)
- **THEN** карточки тарифов расположены по три в ряд, название тарифа полужирное, а клик по изображению карточки переводит на её detail-страницу

#### Scenario: Mobile изображение занимает меньшую долю карточки
- **WHEN** страница услуги отображается на mobile viewport
- **THEN** изображение карточки заметно меньше по высоте относительно всей карточки, чем на desktop, а клик по изображению не выполняет переход

### Requirement: Страницы услуг не показывают блок предупреждения о переменности цен
Ни одна из трёх страниц услуг (список и detail) SHALL NOT отображать блок-предупреждение о переменности/источниках цен (например, «Цены и условия собраны из нескольких источников и могут измениться…») ни при каких данных API или site settings. Компонент, ранее принимавший `notice`, SHALL перестать поддерживать такой проп/рендер в контракте `PricesSection`/страничных Prices-компонентов.

#### Scenario: Notice отсутствует независимо от входных данных
- **WHEN** страница услуги отображается при любых значениях API/settings, в том числе исторически содержавших текст предупреждения
- **THEN** HTML страницы не содержит текста предупреждения о переменности цен ни в каком виде

### Requirement: Фильтрация тарифов на всех трёх страницах услуг выполняется backend через выделенные price_groups
Принцип «одна страница услуг = одна выделенная backend-группа `price_groups`» SHALL применяться ко всем трём страницам услуг; ни одна из них MUST NOT обращаться к общей catch-all группе («Основные услуги» или любая другая, объединяющая тарифы нескольких страниц) и MUST NOT применять клиентский allow-list фиксированных slug'ов или фильтр по `name` поверх ответа API.

Локальный переключатель «Разовые/Абонементы» на странице «Занятия» SHALL сохраняться в UI, но каждое его состояние SHALL выполнять **отдельный** Public Read запрос `GET /api/prices?groups=<точное имя>` («Разовые» либо «Абонементы» соответственно) — не один запрос с повторяемым `groups=`, чтобы не зависеть от его AND/OR-семантики. Страница «Прогулки» SHALL запрашивать `GET /api/prices?groups=Прогулки` вместо повторяемого `name=`. Страница «Постой» SHALL запрашивать `GET /api/prices?groups=Постой частных лошадей` вместо фильтра по `name`.

Набор карточек на каждой странице SHALL равняться фактическому ответу её backend-группы(групп) без дополнительной клиентской фильтрации. Detail-route guard (`/uslugi/{zanyatiya|progulki|postoy}/[slug]`) SHALL считать тариф принадлежащим странице, если поле `groups` в ответе `GET /api/prices/{slug_or_id}` содержит хотя бы одно из имён групп, допустимых для этой страницы, и SHALL возвращать 404 иначе — без хардкоженного массива slug'ов.

#### Scenario: Переключатель «Занятия» выполняет два отдельных запроса
- **WHEN** посетитель переключает «Разовые»/«Абонементы» на странице «Занятия»
- **THEN** сайт выполняет отдельный Public Read запрос с `groups=Разовые` либо `groups=Абонементы` (не единый repeatable-запрос) и отображает ровно те тарифы, что вернул backend для этой группы

#### Scenario: Прогулки запрашивают свою группу
- **WHEN** посетитель открывает `/uslugi/progulki`
- **THEN** сайт выполняет Public Read запрос с `groups=Прогулки`, а не повторяемый фильтр по `name`

#### Scenario: Постой запрашивает свою группу
- **WHEN** посетитель открывает `/uslugi/postoy`
- **THEN** сайт выполняет Public Read запрос с `groups=Постой частных лошадей`, а не фильтр по `name`

#### Scenario: Detail-route guard проверяет членство в группе, а не хардкод-список
- **WHEN** detail route одной из трёх страниц услуг проверяет принадлежность slug своей странице
- **THEN** решение принимается по полю `groups` тарифа из ответа `GET /api/prices/{slug_or_id}` (пересечение с допустимыми группами страницы), а не по статической константе slug'ов в коде

#### Scenario: Ни одна страница не использует catch-all группу
- **WHEN** reviewer проверяет исходящие запросы всех трёх страниц услуг
- **THEN** ни один запрос не содержит `groups=Основные услуги` и не полагается на неё как источник карточек

### Requirement: Сокращённый вертикальный разрыв между блоками страницы «Постой»
Разрыв между блоками «Постой», «Инфраструктура», «Что входит» и «Стоимость» на странице `/uslugi/postoy` SHALL использовать переиспользуемый seam-механизм `Section` (`inlove-ui-components`) и визуально не превышать примерно четверть прежнего суммарного отступа между каждой парой блоков.

#### Scenario: Компактные переходы между блоками Постоя
- **WHEN** `/uslugi/postoy` отображается на desktop и mobile viewport
- **THEN** видимый разрыв между каждой последовательной парой блоков «Постой»/«Инфраструктура»/«Что входит»/«Стоимость» заметно меньше суммы паддингов двух отдельных секций
