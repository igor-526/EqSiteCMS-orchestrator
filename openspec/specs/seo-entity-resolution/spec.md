# seo-entity-resolution

## Purpose

Хранение поисковых запросов и страниц сайта конюшни и batch API «найти или создать», через который сервисы-парсеры получают стабильные UUID этих сущностей.

## Requirements

### Requirement: Уникальность в рамках конюшни
seo-service SHALL хранить поисковые запросы и страницы с идентификатором конюшни и нормализованным значением без ограничения длины. Пара (конюшня, нормализованное значение) MUST быть уникальной на уровне БД; одинаковые значения разных конюшень MUST храниться отдельными записями с разными UUID, без связей многие-ко-многим.

#### Scenario: Одинаковый запрос в двух конюшнях
- **WHEN** конюшни A и B разрешают `"купить лошадь"`
- **THEN** создаются две записи `"Купить лошадь"` с разными UUID, каждая принадлежит своей конюшне

#### Scenario: Ограничение БД
- **WHEN** в БД напрямую вставляется вторая запись с той же конюшней и тем же нормализованным значением
- **THEN** БД отклоняет вставку нарушением уникальности

#### Scenario: Очень длинное значение
- **WHEN** разрешается страница или запрос длиной 100 000 символов
- **THEN** значение сохраняется полностью и повторное разрешение возвращает тот же UUID

### Requirement: Batch resolve поисковых запросов
`POST /api/search-queries/resolve` SHALL принимать `{"items": [string, …]}`, нормализовать каждый элемент, найти или создать запрос в конюшне из `X-Equestrian-Id` и вернуть `200` с `{"items": [{"source", "normalized", "id"}, …]}` в порядке и количестве входа.

#### Scenario: Новые и существующие запросы
- **WHEN** в конюшне уже есть `"Купить лошадь"`, разрешаются `["КУПИТЬ лошадь", "аренда денника"]`
- **THEN** первый элемент получает существующий UUID, для второго создаётся `"Аренда денника"`; ответ содержит два элемента в порядке входа

#### Scenario: Повторное разрешение идемпотентно
- **WHEN** тот же batch разрешается повторно
- **THEN** возвращаются те же UUID, новые записи не создаются

#### Scenario: Дубли внутри batch
- **WHEN** разрешается `["лошадь", "ЛОШАДЬ", " лошадь "]`
- **THEN** все три элемента получают один UUID, создаётся одна запись

### Requirement: Batch resolve страниц
`POST /api/pages/resolve` SHALL принимать `{"items": [string, …]}`, нормализовать каждый элемент по черным спискам конюшни из `X-Equestrian-Id`, найти или создать страницу и вернуть `200` с `{"items": [{"source", "normalized", "id"}, …]}` в порядке и количестве входа.

#### Scenario: URL с UTM и путь сводятся к одной странице
- **WHEN** в черном списке конюшни `utm_source`, разрешаются `["https://site.ru/a?utm_source=ya", "/a"]`
- **THEN** оба элемента получают UUID одной страницы `"/a"`

#### Scenario: Ответ сохраняет исходное значение
- **WHEN** разрешается `"https://site.ru/a?b=2&a=1"`
- **THEN** элемент ответа содержит `source` равный входной строке и `normalized` равный `"/a?a=1&b=2"`

### Requirement: Ограничения batch
Resolve-запрос SHALL содержать от 1 до 1000 строковых элементов. Пустой список, более 1000 элементов, не-строковый элемент или элемент, невалидный после нормализации, MUST отклонять весь batch с `400` без создания записей; `detail` MAY содержать индекс элемента, но MUST NOT содержать его значение.

#### Scenario: Пустой batch
- **WHEN** отправляется `{"items": []}`
- **THEN** ответ `400`

#### Scenario: Превышение размера
- **WHEN** отправляется 1001 элемент
- **THEN** ответ `400`, записи не созданы

#### Scenario: Граница размера
- **WHEN** отправляется ровно 1000 уникальных элементов
- **THEN** ответ `200` с 1000 элементами

#### Scenario: Невалидный элемент в середине
- **WHEN** batch содержит `["лошадь", "   ", "денник"]`
- **THEN** ответ `400`, ни `"Лошадь"`, ни `"Денник"` не созданы

### Requirement: Конкурентная безопасность find-or-create
Параллельные resolve-запросы одной конюшни с пересекающимися значениями SHALL завершаться успешно и возвращать один и тот же UUID для одинакового нормализованного значения; дубликаты, ошибки уникальности и deadlock MUST NOT возникать.

#### Scenario: Параллельные пересекающиеся batch
- **WHEN** два одновременных запроса одной конюшни разрешают `["а", "б", "в"]` и `["в", "б", "г"]`
- **THEN** оба получают `200`, для `"Б"` и `"В"` оба ответа содержат одинаковые UUID, в БД ровно четыре записи

### Requirement: Отсутствие изменения и удаления сущностей
seo-service MUST NOT предоставлять API изменения или удаления поисковых запросов и страниц; созданная запись сохраняет UUID и нормализованное значение.

#### Scenario: Попытка удаления
- **WHEN** caller вызывает `DELETE /api/search-queries/{id}` или `PATCH /api/pages/{id}`
- **THEN** маршрут не существует, запись не меняется
