## Purpose
Определить защищённый CMS-интерфейс управления пользователями и его permission-aware поведение.

## Requirements

### Requirement: Страница управления пользователями в CMS
Система SHALL предоставлять страницу управления пользователями в CMS, доступную только пользователям с ролью `USER_MANAGER` или `SUPERUSER`. Страница MUST содержать таблицу пользователей с фильтрацией, пагинацией, сортировкой и действиями.

#### Scenario: Доступ к странице для USER_MANAGER
- **WHEN** авторизованный пользователь с ролью USER_MANAGER переходит на `/users`
- **THEN** система отображает страницу управления пользователями

#### Scenario: Доступ к странице для SUPERUSER
- **WHEN** авторизованный пользователь с ролью SUPERUSER переходит на `/users`
- **THEN** система отображает страницу управления пользователями

#### Scenario: Отсутствие доступа для других ролей
- **WHEN** авторизованный пользователь с ролью ADMIN (без USER_MANAGER/SUPERUSER) переходит на `/users`
- **THEN** система отображает страницу 403 Forbidden или перенаправляет на dashboard

### Requirement: Кнопка в боковом меню
Система SHALL отображать кнопку "Пользователи" в боковом меню CMS для пользователей с ролью `USER_MANAGER` или `SUPERUSER`. Кнопка MUST быть расположена после всех остальных кнопок в меню.

#### Scenario: Отображение кнопки для USER_MANAGER
- **WHEN** авторизованный пользователь с ролью USER_MANAGER открывает CMS
- **THEN** боковое меню содержит кнопку "Пользователи" с иконкой пользователей

#### Scenario: Скрытие кнопки для других ролей
- **WHEN** авторизованный пользователь с ролью ADMIN (без USER_MANAGER/SUPERUSER) открывает CMS
- **THEN** боковое меню НЕ содержит кнопку "Пользователи"

### Requirement: Header страницы управления пользователями
Страница управления пользователями MUST содержать верхнюю область, визуально согласованную с разделом «Услуги и цены»: первой строкой MUST идти навигация по вкладкам, второй — фильтры и действия с пагинацией, выровненной справа, а перед таблицей MUST быть явный вертикальный отступ. Вкладки MUST предоставлять основной список, пользовательское описание и техническое описание. Responsive layout MUST сохранять этот смысловой порядок без перекрытия элементов.

#### Scenario: Порядок элементов верхней области
- **WHEN** авторизованный пользователь с разрешённой ролью открывает `/users`
- **THEN** система показывает сначала вкладки, затем фильтры и действия с пагинацией справа, затем отделённую от них таблицу

#### Scenario: Поиск через верхнюю область
- **WHEN** пользователь вводит текст в строку поиска
- **THEN** таблица обновляется с результатами поиска по first_name, last_name, middle_name, а offset сбрасывается в 0

#### Scenario: Responsive layout
- **WHEN** пользователь открывает страницу на desktop, tablet или mobile viewport
- **THEN** tabs, filters, paginator, actions и table не перекрываются, а при переносе сохраняют нормативный порядок

#### Scenario: Переключение документационных вкладок
- **WHEN** пользователь выбирает пользовательское или техническое описание
- **THEN** система отображает соответствующую документацию без mutation пользовательских данных

### Requirement: Таблица пользователей
Страница управления пользователями MUST содержать таблицу с колонками: Username, Фамилия, Имя, Отчество, Роль, Забл., Действия. Каждая колонка (кроме Действий) MUST поддерживать фильтр и сортировку.

#### Scenario: Отображение таблицы
- **WHEN** страница управления пользователями загружена
- **THEN** таблица отображает пользователей с колонками Username, Фамилия, Имя, Отчество, Роль, Забл., Действия

#### Scenario: Сортировка по колонке
- **WHEN** пользователь нажимает на заголовок колонки "Username"
- **THEN** таблица сортируется по username (ASC/DESC при повторном нажатии)

#### Scenario: Фильтрация по колонке
- **WHEN** пользователь вводит значение в фильтр колонки "Фамилия"
- **THEN** таблица фильтруется по last_name с регистронезависимым regex

### Requirement: Отображение ролей в виде тегов
Колонка "Роль" MUST отображать роли пользователя в виде разноцветных тегов в спектре от красного до зелёного по значимости. MUST быть fallback на серый цвет для незнакомых ролей.

#### Scenario: Отображение ролей SUPERUSER
- **WHEN** пользователь имеет роль SUPERUSER
- **THEN** отображается красный тег "SUPERUSER"

#### Scenario: Отображение ролей USER_MANAGER
- **WHEN** пользователь имеет роль USER_MANAGER
- **THEN** отображается оранжевый тег "USER_MANAGER"

#### Scenario: Отображение ролей ADMIN
- **WHEN** пользователь имеет роль ADMIN
- **THEN** отображается жёлтый тег "ADMIN"

#### Scenario: Отображение ролей DEVELOPER
- **WHEN** пользователь имеет роль DEVELOPER
- **THEN** отображается зелёный тег "DEVELOPER"

#### Scenario: Fallback для незнакомой роли
- **WHEN** пользователь имеет роль, не входящую в предопределённый список
- **THEN** отображается серый тег с названием роли

### Requirement: Отображение статуса блокировки
Колонка "Забл." MUST отображать статус блокировки пользователя в виде красного и зелёного тега.

#### Scenario: Пользователь заблокирован
- **WHEN** пользователь имеет `is_blocked=true`
- **THEN** отображается красный тег "Заблокирован"

#### Scenario: Пользователь не заблокирован
- **WHEN** пользователь имеет `is_blocked=false`
- **THEN** отображается зелёный тег "Активен"

### Requirement: Кнопки действий в таблице
Колонка "Действия" MUST отображать кнопки управления пользователями в соответствии с правами доступа. Кнопки MUST иметь подходящие иконки.

#### Scenario: Отображение кнопок для USER_MANAGER
- **WHEN** текущий пользователь имеет роль USER_MANAGER и просматривает таблицу
- **THEN** для каждого пользователя (кроме SUPERUSER) отображаются кнопки: "Сменить пароль", "Заблокировать/Разблокировать", "Удалить"

#### Scenario: Скрытие кнопок для SUPERUSER-строк (для UM)
- **WHEN** текущий пользователь имеет роль USER_MANAGER и просматривает строку пользователя с ролью SUPERUSER
- **THEN** кнопки действий скрыты

#### Scenario: Отображение кнопок для SUPERUSER
- **WHEN** текущий пользователь имеет роль SUPERUSER и просматривает таблицу
- **THEN** для каждого пользователя отображаются кнопки: "Сменить пароль", "Заблокировать/Разблокировать", "Удалить"

#### Scenario: Кнопка "Заблокировать" для активного пользователя
- **WHEN** текущий пользователь просматривает активного пользователя
- **THEN** отображается кнопка "Заблокировать" с иконкой замка

#### Scenario: Кнопка "Разблокировать" для заблокированного пользователя
- **WHEN** текущий пользователь просматривает заблокированного пользователя
- **THEN** отображается кнопка "Разблокировать" с иконкой открытого замка

### Requirement: Модальное окно смены пароля
При нажатии кнопки "Сменить пароль" MUST открываться модальное окно с полями для ввода нового пароля и подтверждения.

#### Scenario: Открытие модального окна
- **WHEN** пользователь нажимает кнопку "Сменить пароль"
- **THEN** открывается модальное окно с полями "Новый пароль" и "Подтвердить пароль"

#### Scenario: Валидация совпадения паролей
- **WHEN** пользователь вводит разные пароли в поля
- **THEN** отображается ошибка "Пароли не совпадают"

#### Scenario: Валидация сложности пароля
- **WHEN** пользователь вводит пароль, не соответствующий требованиям сложности
- **THEN** отображается ошибка с описанием требований

#### Scenario: Успешная смена пароля
- **WHEN** пользователь вводит валидные совпадающие пароли и нажимает "Сменить пароль"
- **THEN** пароль изменяется, модальное окно закрывается, отображается уведомление об успехе

### Requirement: Модальное окно подтверждения блокировки/разблокировки
При нажатии кнопки "Заблокировать" или "Разблокировать" MUST открываться модальное окно подтверждения.

#### Scenario: Подтверждение блокировки
- **WHEN** пользователь нажимает кнопку "Заблокировать" и подтверждает действие в модальном окне
- **THEN** пользователь блокируется, модальное окно закрывается, строка обновляется

#### Scenario: Подтверждение разблокировки
- **WHEN** пользователь нажимает кнопку "Разблокировать" и подтверждает действие в модальном окне
- **THEN** пользователь разблокируется, модальное окно закрывается, строка обновляется

#### Scenario: Отмена действия
- **WHEN** пользователь нажимает "Отмена" в модальном окне подтверждения
- **THEN** модальное окно закрывается, действие не выполняется

### Requirement: Модальное окно подтверждения удаления
При нажатии кнопки "Удалить" MUST открываться модальное окно с предупреждением о необратимости действия.

#### Scenario: Подтверждение удаления
- **WHEN** пользователь нажимает кнопку "Удалить" и подтверждает действие в модальном окне
- **THEN** пользователь удаляется (soft-delete), модальное окно закрывается, строка удаляется из таблицы

#### Scenario: Предупреждение о необратимости
- **WHEN** открывается модальное окно удаления
- **THEN** отображается предупреждение "Действие необратимо без участия разработчика"

### Requirement: Модальное окно создания/редактирования пользователя
Система MUST предоставлять единое модальное окно для создания нового пользователя и редактирования существующего. В обоих режимах MUST присутствовать selector ролей, который отображает локализованные человекочитаемые названия, использует UUID как внутренние значения и отправляет выбранные UUID в `scope_ids`. UUID роли MUST NOT отображаться пользователю вместо названия.

#### Scenario: Открытие для создания
- **WHEN** пользователь нажимает кнопку «Добавить пользователя»
- **THEN** открывается модальное окно с пустыми полями Фамилия, Имя, Отчество, Username, Пароль и selector ролей

#### Scenario: Выбор ролей при создании
- **WHEN** пользователь открывает selector ролей и выбирает одну или несколько ролей
- **THEN** options и выбранные tags показывают названия ролей, а create payload содержит их UUID в `scope_ids`

#### Scenario: Открытие для редактирования
- **WHEN** пользователь нажимает на строку пользователя в таблице
- **THEN** открывается модальное окно с заполненными данными и текущими ролями, показанными названиями, при скрытом поле пароля

#### Scenario: Изменение ролей существующего пользователя
- **WHEN** пользователь изменяет выбранные роли и сохраняет форму
- **THEN** update payload содержит актуальный массив UUID в `scope_ids`, модальное окно закрывается после успеха и строка обновляется

#### Scenario: Загрузка и пустой список ролей
- **WHEN** список ролей загружается или backend возвращает пустой список
- **THEN** selector показывает соответственно loading или доступное empty state и не отображает UUID как подписи

#### Scenario: Ошибка получения ролей
- **WHEN** backend возвращает generic error, `401` или `403` при загрузке ролей
- **THEN** CMS показывает понятное состояние ошибки и применяет существующий auth/permission flow без live retry из component test

#### Scenario: Ошибка сохранения сохраняет форму
- **WHEN** create/update возвращает validation error, generic error, `401` или `403`
- **THEN** система показывает ошибку, сохраняет введённые значения и не выполняет повторную mutation при double-submit

#### Scenario: Валидация username
- **WHEN** пользователь вводит username, который уже существует
- **THEN** отображается ошибка "Пользователь с таким username уже существует"

#### Scenario: Успешное создание
- **WHEN** пользователь заполняет обязательные поля, выбирает допустимые роли и нажимает «Создать»
- **THEN** пользователь создаётся, модальное окно закрывается, таблица обновляется

#### Scenario: Успешное редактирование
- **WHEN** пользователь изменяет данные и нажимает "Сохранить"
- **THEN** данные обновляются, модальное окно закрывается, строка обновляется
