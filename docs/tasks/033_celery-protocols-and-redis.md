# Контекст
Есть email сервис. Он по NATS принимает только то, что и куда отправить. После должен ставить это в очередь и отправлять
# Задачи
## env
Я сделал в файле `.env` настройки для NATS и Celery
Перенести их в `.env.example` и при доработке переменных окружения обязательно дополняй эти настройки
## Celery
Мы делали задачу по инструкциям агентов по работе с разными технологиями. Посмотри протокол разработки и использования NATS в `agents/howto`. Нам необходимо продумать архитектуру для работы с Celery
Конкретно в этой задаче Celery будет использоваться для отправки email. В других задачах у Celery может быть несколько очередей. Продумай корректно архитектуру, протоколы и принципы использования Celery в микросервисах. Критично в соответствии с SOLID
# Redis
Celery будет использовать как брокер Redis. Подними его в инфраструктурном docker compose. Используй парольный доступ. Переменные окружения от инфраструктурного Redis положи в .env папки .docker-compose. Не используй этот файл для проектов. В каждом проекте, который использует Celery, Redis нужны свои переменные окружения. В docker compose зафиксируй последнюю актуальную версию
### Использование БД
Для любого приложения, использующего celery необходимо выделять 2 БД. Под очередь и под результаты. Нумерацию начинаем с "1", а "0" резервируем под кэш основного backend (пока не используйется)

Файл README.md каждого микросервиса, использующего Celery должен содержать информацию об очередях и использовании Celery
# БД Redis
Чтобы нам не запутаться в БД, нам необходимо хранить, какие БД для чего используются
Для этого в папке agents создай файл yaml, в котором будем вести учёт, какой номер БД Redis для чего использован или зарезервирован. Номер, сервис, краткое описание. Ориентируй в протоколе на этот файл backend агента и quality_gate. При необходимости его дополнять или изменять
