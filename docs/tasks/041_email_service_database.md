# Контекст
Мы в `email-service` реализовали возможность отправлять email письма пользователям. Но на данный момент сами email пользователей нигде не хранятся и никак не подтверждаются
Давай реализуем
# Хранение
Реализуй в БД сервиса таблицу, которая будет хранить привязку email к пользователю. 1 к 1. По умолчанию email пользователя не подтверждён. Нужна защита от дубликатов email в рамках одного Equestrian ID. Для проверки сервис может сходить на сервисный эндпоинт основного backend, который вернёт информацию обо всех пользователях в рамках одного Equestrian. Также нам нужно реализовать тут soft-delete, поэтому дубликаты ещё необходимо проверять только в non-deleted записях
# Подтверждение
Подтверждение email пользователя будет происходить методом отправки на указанный электронный адрес письма со ссылкой на подтверждение. Разработай систему такого подтверждения. Микросервис будет принимать PATCH запрос с кодом из этой ссылки и по коду искать email для подтверждения и подтвержать его.
## Механика подтверждения
### Получение запроса
Сервис принимает запрос на подтверждение email и отправляет email с ссылкой, по которой пользователю нужно перейти в браузере. Ссылка содержит параметр с контрольной строкой, на основе которой потом будет происходить запрос на подтверждение. Эта строка должна быть длиной не менее 20 символов. У этой строки должен быть срок действия
### Автоотправка запроса
Frontend выполняет запрос к основному backend на подтверждение email
### Запрос от основного backend
Так как микросервис не виден снаружи, управлять им может только основной backend. Он проксирует запрос к этому сервису
### Поиск email для подтверждения по контрольной строке
Сервис выполняет в БД поиск по контрольной строке и ищет email, который нужно подтвердить и в случае успеха подтверждает его, возвращая основному backend успех или ошибку. Основной backend возвращает этот ответ на frontend, а тот показывает сообщение пользователю об успехе или ошибке
# Frontend
Нам будет нужна страница. При переходе пользователя на эту страницу frontend считывает параметр запроса и делает запрос к основному backend на подтверждение. Эта страница должна быть доступа для неавторизованных пользователей. Давай сделаем это по пути `/callback/email`, чтобы мы потом могли расширять эту архитектуру
# Frontend CMS
Изменений не потребуется
# Non Goals
Микросервис не отвечает за валидацию подтверждения email перед отправкой. За это будет отвечать только notification-service перед тем, как давать команду на отправку письма
# API
Нам нужно реализовать 2 эндпоинта в микросервисе
### Получение email пользователей
Это должен быть GET эндпоинт, на который будет ходить notification-service за тем, чтобы по UUID пользователей получить их email. В пути должен быть обязательный параметр `user_ids`, который будет принимать список UUID пользователей. Давай добавим туда ещё фильтр (необязательный параметр) `approved`, который будет принимать None, True или False и фильтровать email пользователей
По итогу этот эндпоинт должен возвращать что-то типа:
```json
[
	{
		"id": "UUID записи",
		"user_id": "UUID пользователя",
		"email": "igor-526@yandex.ru",
		"approved": true
	},
	{
		"id": "UUID записи",
		"user_id": "UUID пользователя",
		"email": "igor-527@yandex.ru",
		"approved": true
	},
	{
		"id": "UUID записи",
		"user_id": "UUID пользователя",
		"email": "igor-528@yandex.ru",
		"approved": false
	},
]
```
### Запись email пользователя
POST запрос, который принимает
```json
{
	"user_id": "UUID пользователя",
	"email": "igor-526@yandex.ru"
}
```
и возвращает
```json 
{
	"id": "UUID записи",
	"user_id": "UUID пользователя",
	"email": "igor-526@yandex.ru",
	"approved": false
}
```
### Смена email пользователя
PATCH запрос, который принимает
```json
{
	"user_id": "UUID пользователя",
	"email": "igor-527@yandex.ru"
}
```
и возвращает
```json 
{
	"id": "UUID записи",
	"user_id": "UUID4",
	"email": "igor-527@yandex.ru",
	"approved": false
}
```
Запрос должен быть идемпотентным. Если новый email ничем не отличается от сменяемого email, то статус approved не должен пропадать. В противном случае статус автоматически становится false
### Удаление email пользователя
Запрос DELETE, в пути которого присутствует UUID пользователя. Выполняется мягкое удаление и возврат статуса 204. Запрос должен быть также идемпотентным. При удалении несуществующего email просто возвращаем 204
### Подтверждение email
PATCH запрос, который принимает
```json
{
	"code": "контрольная строка из email"
}
```
### Запрос на отправку письма подтверждения
POST запрос, который будет принимать
```json
{
	"user_id": "UUID пользователя"
}
```
после чего будет искать в БД email этого пользователя и отправлять пользователю письмо с просьбой подтвердить email с помощью перехода по ссылке
# Проксирование
Мы уже описывали, что взаимодействие между микросервисами происходит исключительно в отдельном архитектурном слое в пакете clients. Запрашиваемый сервис обязательно должен содержать схемы ответов сервиса, которые он проксирует и валидировать их
Основной backend будет обращаться по эндпоинтам:
- запись email пользователя
- смена email пользователя
- удаление email пользователя
- подтверждение email
- запрос на отправку письма подтверждения
C эндпоинтом массового получения email пользвоателей взаимодействовать будет notification_service
# ENV
В этом сервисе необходимо добавить сервисный ключ основного backend и его адрес
В основном backend необходимо добавить адрес этого сервиса
В сервисе уведомлений необходимо добавить адрес этого сервиса

В этом сервисе в переменные окружения необходимо вынести всё параметризуемое, включая, но не ограничиваясь
- срок действия контрольной ссылки в часах
- адрес frontend, к которому необходимо добавить параметр запроса для подтверждения
