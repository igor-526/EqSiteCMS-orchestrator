# Завершение пайплайна задачи: готовность к ручной проверке, слияние в main и релиз

## Контекст

Сейчас реализован пайплайн работы с задачами: агент-роутер выполняет маршрутизацию между Planner, исполнителями и Quality Gate. После `QG-SYNTH` / архивирования change пайплайн заканчивается простым отчётом о том, что всё выполнено. Механизм нужно довести до конца.

## Требования пользователя

1. **Готовность к ручной проверке.** После выполнения задачи она должна быть готова к ручной проверке: все контейнеры изменённых сервисов уже пересобраны и перезапущены (с учётом правок, сделанных после `QG-ENV`, например по findings `REWORK`).
2. **Слияние в main.** После завершения задачи Router спрашивает пользователя, сливать ли изменения в `main`. После подтверждения на **каждом изменённом репозитории**:
   - создаётся ветка по маске `feature/<change_name>` или `bug/<change_name>`;
   - делается коммит изменений;
   - ветка вливается в `main`;
   - изменения пушатся.
   Перед слиянием в `main` обязательно выполняется `make sync` (pull всех репозиториев).
3. **Релиз.** Затем Router спрашивает, нужно ли релизить. Если да:
   - в ветку `release` вливается `main` и пушится;
   - через GitHub CLI (`gh`) проверяется, что CI/CD пайплайн дошёл до конца;
   - если пайплайн не дошёл до конца — **никаких автоматических исправлений**, только отчёт пользователю для принятия решения.

## Вспомогательные команды в корне

- `make sync` — pull всех репозиториев (`scripts/sync.sh`, пулит текущую ветку каждого клона из `services.manifest`).
- `make services-branches` — ветка и число изменённых файлов в каждом репозитории (корень + `services/*`).

## Наблюдения Router (факты окружения)

- Корень монорепы — отдельный git-репозиторий (`origin = git@github.com:igor-526/EqSiteCMS-orchestrator.git`), в нём живут OpenSpec artifacts, `docs/`, `AGENTS.md`, `agents/**`. Подсервисы `services/<name>` — отдельные клоны из `services.manifest`.
- Во всех сервисах (`backend`, `frontend`, `notification-service`, `email-service`, `vk-service`, `site-ad`, `site-ksk-inlove`) есть ветки `main` и `release` и `.github/workflows/check_and_deploy.yml`, запускаемый на `push` в `release` (lint/test → build image в GHCR → helm deploy). В корне CI нет.
- `gh` установлен и авторизован (`igor-526`, scopes `repo`).
- `scripts/stackctl` (skill `stack-control`) умеет `rebuild/restart/migrate/status/doctor` для backend, frontend, notification, email, vk; сайты `site-*` в stackctl не представлены.
- Рабочие деревья часто содержат «посторонние» dirty-файлы, не относящиеся к текущему change (сейчас корень — 56 файлов, backend — 16). Нужно защититься от коммита чужих изменений.
- Существуют legacy-ветки `agent/<uuid>` и коммиты «Automated commit: task pipeline completion» от удалённого orchestrator — это не целевой механизм.
- Текущий `AGENTS.md` запрещает Router писать код; операционные git/release шаги нужно явно вписать в модель ролей (Router сам по skill/скрипту или отдельный профиль/lane).
