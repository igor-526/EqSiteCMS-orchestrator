# Вывод текущих метрик на страницах

## Контекст

В задаче 101 мы реализовали парсинг данных с Яндекс.Метрика

В задаче 099 и 100 мы реализовали SEO сервис и frontend для него

Теперь нам нужно реализовать вывод и агрегацию этих метрик

Для начала начнём со страниц

## Задачи

### Вёрстка

В разделе "SEO" есть вкладка "Страницы". Мне не нравится вёрстка кнопки "Нормализация". Посмотри эталонную страницу "Услуги и цены". Там вкладки находятся слева, а пагинация и остальные действия находятся справа

Давай немного отступим от правил и сделаем следующим образом:

1.  Вкладки слева, справа только пагинация таблицы и кнопка "Нормализация". Также нужно реализовать кнопку сброса фильтров, как она сделана на всех остальных страницах CMS
2.  Чуть ниже расположим блок фильтров, так как в одну ширину он не влезет. Этот блок фильтров при прокрутке должен также оставаться наверху страницы. Прокручивается только содержимое страницы

### Фильтры

Я хочу видеть на страницах следующие фильтры. Все обязательны и имеют значения по умполчанию:

1.  Режим - по сути enum из значений, по которым мы можем вывести значения. Может принимать следующие значения: по дням / по неделям / по месяцам / по годам. По умолчанию "по дням". Является
2.  Показатель - выбор метрики. Все доступные метрики представлены в таблице `metrica_page_stats`. По умолчанию визиты
3.  Диапазон дат. Выбираются 2 даты, за которые нужно показать метрики. В зависимости от выбранного режима нужно установить лимит и значения по умолчанию

| Режим | Лимит | По умолчанию |
| --- | --- | --- |
| По дням | 31 день | 7 дней |
| По неделям | 16 недель | 4 недели |
| По месяцам | 12 меясцев | 6 месяцев |
| По годам | 5 лет | 2 года |

Значение по умолчанию высчитывается от сегодняшнего дня. По часовому поясу пользуемся уже реализованной в прошлой задаче настройкой

Если пользователь вводит даты, диапазон которых больше лимита, то давай просто обрезать под максимум со стороны второй даты. Я предлагаю это делать со стороны backend. В ответе будет присылаться итоговый диапазон дат, а frontend будет сравнивать. Если даты были обрезаны, то они меняются в фильтре, а пользователю выводится уведомление об этом

### Таблица

На данный момент в таблице есть колонка со страницей и с датой создания. Давай расширим эту таблицу вправо в зависимости от выбранных фильтров. В качестве заголовков нужно вывести дату или диапазон дат. В днях год не выводим. В диапазонах выводим год только если он в диапазоне разный или отличен от текущего. Месяца давай выводить кратко буквами, а года двумя последними цифрами

В ячейках будем выводить сами метрики и форматировать их. Проценты добавлять в конце "%", время с единицей измерения (сокращенно). Десятичные округлять до второго знака

### Сортировка

В колонках, которые генерируются правее двух основных нужно по аналогии со страницей реализовать сортировку прямую и обратную

Ограничение по сортировке - отсортирован может быть только один столбец

### Колонка "Создано"

Давай уберём там время создания и оставим только дату. Ну и поддержим там сортировку

### Фильтрация

Фильтрацию поддерживать в колонке "Создано" и в колонках с датами не нужно

### Агрегация

При выборе диапазона, отличного от дня нам необходимо агрегировать статистики

Для этого давай использовать те же агрегации, что происходят при парсинге и слиянии

### Архитектура

Сейчас для вывода страниц испольузется эндпоинт к сервису SEO. Давай расширим DTO этого эндпоинта атрибутом "metrics\_table" и создадим универсальное DTO для вывода таблиц метрик. Это DTO будет формировать backend. В DTO будем указывать колонки и ячейки. Что то по типу:

```
{
    "metrics_table": {
            "columns": {
                    "25.10": {
                        "sortable": true, # указываем, что колонка сортируемая
                        "hint": "25.10.2026", # подсказка при наведении,
                        "values": {
                            "UUID сущности": {
                                "text": "<МЕТРИКА СУЩНОСТИ>" # мапим колонку и UUID страницы
                            }
                        }
                    }
                }
        }
}
```

В общем, нужно продумать универсальный движок выдачи таблиц с backend и их рендеринга на frontend так, чтобы и столбам и ячейкам можно было придать хороший потенциал к расширению

Сервис SEO для получения данных для формирования этой таблицы должен будет обратиться к сервису яндекс метрики. Сервис метрики должен отдавать уже агрегированные статистики

Всю агрегацию и фильтрацию нужно реализовать исключительно в SQL запросах ответственных сервисов. SEO сервис отвечает только за преобразование. А к SEO сервису обращение идёт уже с основного Backend

### N+1
