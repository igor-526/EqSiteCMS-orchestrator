# Контекст
Общение между основным бэкэндом и микросервисами может происходить не только посредством NATS Jetstream, но и с помощью API
# Защита
Все микросервисы будут работать исключительно в локальной сети и не будут выставлены наружу. Но так как микросервисы могут делать запросы к основному backend, нам необходимо его защитить. Для этого мы добавим ещё один способ авторизации для микросервиса. В Headers микросервисы будут передавать специальный сервисный ключ для обращения к основному backend. Пусть это будет X-Service-Key. Доступ по этому ключу будет только к сервисным эндпоинтам. На основные эндпоинты это не должно никак повлиять, по ним авторизация с сервисным ключом должна быть невозможной
# Сервисные эндпоинты
Все сервисные эндпоинты должны начинаться с префикса `service/` в пути
Для сервисных эндпоинтов не должно быть доступа по другим методам авторизации (cookies, equestrian key)
Все сервисные эндпоинты должны иметь потенциал к расширению. Не делай эндпоинты только для одной цели
# Первый сервисный эндпоинт
Нам нужно получать пользователей платформы по конюшне и по роли для отправки уведомления о том, что появилась заявка на обратный звонок
Для этого давай сделаем эндпоинт GET `api/service/users`, который будет возвращать пагинированный список полного DTO пользователя
Так как нужно заложить потенциал к расширению, давай добавлять необязательные фильтры, чтобы добиться того результата, который нам нужен
### Фильтр по id конюшни
Параметр `equestrian_ids` должен принимать список UUID конюшен и отвечать списком пользователей с этих конюшен по логике "ИЛИ"
Давай сделаем аналогичный фильтр сразу по сервисному ключу `equestrian_service_keys`, который будет делать тоже самое, только с сервисным наименованием конюшни, а не с UUID
### Фильтр по роли пользователя
Будет принимать список строк из таблицы `user_scopes.scope_name` и фильтровать пользователей дополнительно по ролям. Аналогично с логикой "ИЛИ"
### Комбинации фильтров
Комбинации фильтров встают в логику "И"
# Пагинация
Давай стандартизируем правила пагинации для сервисных эндпоинтов. DTO остаётся таким же, как и для cms и consumer. Поле  total будет говорить о необходимости следующего запроса
Пагинация будет производиться с помощью limit и offset параметров
Стандартный limit=100
Максимальный 5000
# ENV
В основном backend в .env и в .env.example добавь переменную `SERVICE_KEY` и сгенерируй рандомную строку
Для всех микросервисов, которые обращаются к основному backend нужно  добавить переменные:
- `MAIN_BACKEND_URL` - URL для обращения к основному backend
- `MAIN_BACKEND_SERVICE_KEY` - сервисный ключ для обращения к основному backend
Если основной backend будет обращатся к микросервисам или микросервис будет обращаться к другим микросервисам, нам необходимо добавлять переменные для адреса этих микросервисов, например, "NOTIFICATION_SERVICE_URL" или "EMAIL_SERVICE_URL"
Никакого хардкода ключей или адресов
# Обращение к другим сервисам
Для обращения к другим сервисам по API необходимо использовать библиотеку aiohttp и реализовывать клиенты к другим сервисам в соответствующем инфраструктурном слое. Это папка `clients`. Она уже реализована в notification_service и email_service. По аналогии
Не допускается использование клиента к другому микросервису в core обращающегося сервиса
Обрабатывай все возможные ошибки. Никогда не возвращай с основного backend на frontend 502. В случае, если микросервис недоступен, возвращаем 500 с описанием проблемы
# Протоколы
После реализации нам нужно запротоколировать работу с сервисными эндпоинтами. Для этого доработай агента `backend`, добавь в него все вышеописанные правила
