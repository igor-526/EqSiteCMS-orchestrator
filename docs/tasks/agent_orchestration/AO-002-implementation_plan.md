# AO-002 — План реализации: Agent Orchestration Web

Детальный план реализации фичи, описанной в [`AO-001-agent_orchestration_architecture.md`](AO-001-agent_orchestration_architecture.md): веб-интерфейс, переносящий текущий CLI-управляемый пайплайн разработки (Planner → OpenSpec → Apply → QG → Завершение) в браузер, с сохранением работы агентов через подписки (Claude Code, в перспективе Codex и MiMo), а не через API-биллинг.

---

## 1. Цель и границы MVP

### Цель
Дать возможность вести весь цикл задачи — от текстового описания до прохождения Quality Gate — из браузера, наблюдая за работой агента(ов) вживую, без необходимости держать открытым терминал.

### В скоуп MVP входит
- Стадии 1–5 из AO-001: Формирование задачи → OpenSpec → Решение по артефактам → Разработка → QG.
- Только один агент-адаптер: **Claude** (Claude Code CLI, headless/print-режим, авторизация через подписку).
- Один целевой репозиторий — сам `eqSiteCMS` (монорепо).
- Однопользовательский режим (владелец репозитория — единственный оператор), без multi-tenant.

### Явно вне скоупа MVP (зафиксировано в AO-001, стр. 15, 26)
- Стадии 6–7 (Завершение через Git, Релиз через k8s) — реализуются позже отдельным скиллом. В MVP это **ручной стаб**: кнопка «Отметить завершённым» без автоматизации git/k8s.
- Адаптеры **Codex** и **MiMo** — в MVP только архитектурный интерфейс под них (см. §5), без рабочей реализации.
- Параллельная работа нескольких операторов, права доступа, аудит.
- Автоматический retry после исчерпания лимитов агента (см. §7) — в MVP только ручной resume.

## 2. Ключевое архитектурное решение

Оркестратор **не переизобретает** Router/Planner/QG-логику из `AGENTS.md` — эта логика уже реализована внутри самого Claude Code CLI, когда он запускается в директории `eqSiteCMS` (т.к. `CLAUDE.md` репозитория указывает на `AGENTS.md` как обязательный контекст). Задача веб-интерфейса — **вызывать headless-сессии CLI-агента на нужной стадии пайплайна и показывать их вывод**, а не самому делать маршрутизацию или декомпозицию на execution units.

Стадии AO-001 мапятся на уже существующие скиллы репозитория:

| Стадия AO-001 | Что вызывает оркестратор | Существующий механизм |
|---|---|---|
| 1. Формирование задачи | ничего (чистый UI) | редактор `docs/tasks/*.md` |
| 2. Подготовка OpenSpec | headless-сессия агента с промптом на основе `openspec-propose` | скилл `openspec-propose` |
| 3. Принятие решения | ничего (UI-гейт) + опционально follow-up сессия с комментарием пользователя | — |
| 4. Разработка | headless-сессия агента, запускающая Router/AGENTS.md-пайплайн до готовности к QG | скилл `openspec-apply-change` (внутри агент сам следует `AGENTS.md`: делит на execution units, делегирует профильным подагентам) |
| 5. QG | headless-сессия(и) агента по lane-модели | `code-review` / QG lanes из `AGENTS.md` |
| 6–7 | стаб-кнопка, без вызова агента | — (будущий скилл) |

Из этого следует главный технический риск, который нужно провалидировать **первым** (Phase 2, §9): ведёт ли себя headless (`-p`/print) режим Claude Code так же, как интерактивная сессия — то есть выполняет ли он весь Router-цикл (включая внутренние вызовы субагентов) в рамках одного вызова CLI, пока не упрётся в approval-gate или не завершится. Если нет — потребуется другой механизм (например, серия отдельных вызовов с явным продолжением сессии через `--resume`).

## 3. Высокоуровневая архитектура

```
┌─────────────────────┐      REST + WebSocket      ┌──────────────────────┐
│  orchestrator-ui     │ ─────────────────────────▶ │  orchestrator-api     │
│  (браузер)            │ ◀───────────────────────── │  (FastAPI, Postgres)  │
└─────────────────────┘                              └──────────┬───────────┘
                                                                   │ ставит job
                                                                   ▼
                                                       ┌──────────────────────┐
                                                       │  orchestrator-worker  │
                                                       │  (спавнит CLI-процесс)│
                                                       └──────────┬───────────┘
                                                                   │ git worktree
                                                                   ▼
                                                       ┌──────────────────────┐
                                                       │  eqSiteCMS worktree   │
                                                       │  ветка agent/<task>   │
                                                       └──────────────────────┘

Redis (pub/sub) — доставка событий стрима от worker к api (WebSocket relay)
```

**Оркестратор — полностью отдельный проект, не часть eqSiteCMS-продукта** (решение зафиксировано в комментарии к Phase 0, §9, и в открытых вопросах §10): отдельный git-репозиторий, без записи в `services.manifest`/`SERVICES.md` этого монорепо, со своим `openspec/` (собственный OpenSpec-инстанс, не связанный с change'ами eqSiteCMS). Пересечение с eqSiteCMS — только то, что worktree одной из задач-целей физически указывает на чекаут eqSiteCMS (см. §8): оркестратор оперирует этим репозиторием как целевым, но не является его частью.

Вся инфраструктура — **один `docker-compose.yml`** в корне репозитория оркестратора, поднимающий одной командой все компоненты как отдельные контейнеры: `postgres`, `redis`, `api`, `worker`, `frontend`. Свой Makefile с целями `make up`/`make down`/`make check`/`make fix`, независимый от Makefile eqSiteCMS.

### Компоненты
- **orchestrator-api** — Python/FastAPI, Clean Architecture (тот же архитектурный принцип, что `services/backend` в eqSiteCMS, но независимый кодбейс), PostgreSQL + Alembic. Хранит метаданные задач/стадий/ранов/сообщений — не файлы (файлы остаются в файловой системе worktree).
- **orchestrator-worker** — тот же кодбейс, отдельный контейнер/процесс. Забирает job из очереди, поднимает/переиспользует git worktree, спавнит CLI-агента, стримит его вывод в БД + Redis pub/sub.
- **orchestrator-ui** — Next.js, с применением тех же архитектурных правил, что использует CMS frontend-агент (`agents/frontend.md` eqSiteCMS: структура `src/app`/`src/features`, паттерны UI-kit) — решение зафиксировано в §10, вопрос 1.

### Очередь заданий
Простая очередь — таблица `runs` в PostgreSQL, worker забирает записи `status = queued` (решение §10, вопрос 3: без порога/условия на переход к Celery, сразу простая очередь). Redis используется только для pub/sub стрима (см. §6), не как брокер задач.

## 4. Модель данных

```
tasks
  id, task_md_path, title, status, openspec_change_id (nullable),
  created_at, updated_at

stages            -- фиксированный список из 7 стадий AO-001, состояние на конкретной task
  id, task_id, stage_type (enum: forming, openspec, decision, developing, qg, completion, release),
  status (enum: pending, active, waiting_decision, blocked_quota, done, skipped),
  started_at, finished_at

runs              -- один headless-вызов CLI-агента (может быть несколько на стадию: QG lanes, retries)
  id, stage_id, agent (enum: claude, codex, mimo), status (enum: queued, running,
  waiting_input, blocked_quota, succeeded, failed, stopped),
  cli_session_id, worktree_path, branch_name, exit_code,
  started_at, finished_at

run_events        -- живой "чат": лог одного run'а
  id, run_id, seq, ts, type (enum: stdout, tool_call, tool_result, system, error), content

artifacts         -- обнаруженные по diff файлы-артефакты (proposal, specs, tasks.md, reports)
  id, task_id, run_id (nullable), path, kind, discovered_at

decisions         -- зафиксированные решения на approval-гейте (стадия 3)
  id, task_id, stage_id, comment_text, action (enum: rework, proceed), created_at
```

`stages` создаются заранее (все 7) при создании задачи со статусом `pending` — это даёт дашборду единый источник правды для прогресс-бара задачи без вычисления на лету.

## 5. Адаптер агентов (расширяемость под Codex/MiMo)

Абстракция, единая для всех агентов:

```
AgentAdapter:
  start(stage_context) -> RunHandle       # спавнит headless-процесс в worktree
  stream(run_id) -> AsyncIterator[Event]  # построчный разбор вывода в run_events
  is_quota_exceeded(event) -> bool        # адаптер-специфичный детектор лимита
  resume(run_id) -> RunHandle             # продолжение прерванной сессии, если CLI это поддерживает
  stop(run_id)
```

- **ClaudeAdapter** (MVP, единственная рабочая реализация) — headless/print-режим Claude Code CLI со стриминговым JSON-выводом, авторизация — сохранённая сессия подписки (`claude login` на машине воркера, не API-ключ). Точные флаги вызова (формат стрима, продолжение сессии, уровень авто-разрешений на инструменты) требуют прототипирования в Phase 2 (§9) — сейчас не фиксируются как финальные.
- **CodexAdapter**, **MimoAdapter** — присутствуют как классы с `NotImplementedError`, чтобы контракт (БД-схема, UI, событийная модель) не зависел от конкретного агента и не потребовал миграций при добавлении второго/третьего адаптера. MiMo дополнительно не имеет понятия «подписки» — потребует собственного self-hosted инференса; это отдельная задача вне MVP.

Выбор агента для стадии — поле на UI (в MVP всегда предзаполнено `claude`, диздейбл, т.к. это единственный вариант); задел на будущее — dropdown, когда появится второй адаптер.

## 6. Стриминг и «живой чат»

- Worker пишет каждое событие вывода агента как строку в `run_events` **и** публикует его в Redis pub/sub канал `run:<run_id>`.
- orchestrator-api отдаёт `GET /runs/{id}/events` (история, для первой загрузки/reconnect) и `WS /runs/{id}/stream` (relay из Redis в браузер).
- Экран «Работа над задачей» показывает список активных `runs` под задачей (агент, стадия, статус, счётчик — по требованию AO-001 «видеть каждого агента, их количество»), клик по run открывает его чат-ленту.
- Если под одной стадией одновременно идёт несколько ранов (например, параллельные QG lanes — `QG-BE`/`QG-FE`/`QG-CONTRACTS` из `AGENTS.md`), UI показывает их как отдельные вкладки/карточки внутри стадии, а не единым потоком — иначе логи разных агентов будут перемешиваться и терять читаемость.

## 7. Обработка исчерпания лимитов агента

Явное требование AO-001 (стр. 26): в любой момент у агента может кончиться лимит подписки.

- Каждый `ClaudeAdapter.is_quota_exceeded` проверяет вывод/exit code на известные сигнатуры лимита (конкретные строки/коды — зафиксировать в Phase 4 по факту наблюдения реального поведения CLI, не гадать заранее).
- При обнаружении: `run.status = blocked_quota`, `stage.status = blocked_quota`. Стадия **не** переводится в `failed` — это не ошибка реализации, а внешнее ограничение.
- UI показывает баннер на задаче: Лимит агента исчерпан на стадии X с действиями
- **Повторить** — создать новый `run` для той же стадии тем же агентом (ручной клик, без авто-ретраев в MVP — чтобы не расходовать лимит молча).
  - **Сменить агента** — доступно, когда появится второй рабочий адаптер (вне MVP, но поле в UI/схеме закладывается сразу).
- Никакого автоматического опроса «сбросился ли лимит» в MVP — избыточная сложность при одном операторе, который и так открывает браузер вручную.

## 8. Изоляция через git worktree

- При «Взятии в работу» создаётся ветка `agent/<task_id>` и worktree в отдельной директории (вне пути, который видит пользователь как «основной» чекаут), например `~/.orchestrator/worktrees/<task_id>`.
- Все `runs` задачи работают в этом worktree — параллельные задачи не конфликтуют друг с другом и не мешают ручной работе пользователя в основном репозитории.
- Артефакты (OpenSpec-файлы, отчёты) обнаруживаются как diff worktree относительно базовой ветки после каждого run'а и индексируются в таблицу `artifacts`.
- Стадии 6–7 (Git/k8s), когда будут реализованы, должны будут смёржить эту ветку — уже сейчас стоит закладывать `branch_name` в схему `runs`, чтобы не делать миграцию позже.

## 9. Фазы реализации (roadmap)

Порядок выбран так, чтобы самый неопределённый технический риск (headless-поведение CLI-агента, §2) проверялся раньше, чем будет построен весь остальной UI вокруг него.

**Phase 0 — Каркас отдельного проекта**
Новый git-репозиторий оркестратора (вне eqSiteCMS), скелет backend (FastAPI + миграции БД) и frontend (Next.js), один `docker-compose.yml` (postgres/redis/api/worker/frontend), свой Makefile. По возможности — собственный `openspec/` для дальнейшей разработки самого оркестратора. Без бизнес-логики пайплайна.
**Комментарий к Phase 0:**
Давай отделять оркестратор от работы сервиса. У оркестратора в Makefile должна быть своя инфраструктура. Я бы для него делал исключительно 1 dockerfile, который поднимает и воркеров, и redis, и БД, и бэк, и фронт. Это должно быть отдельно от разрабатываемого продукта. По возможности я бы постарался вести отдельный OpenSpec для этого

**Phase 1 — Управление задачами (без агентов)**
Файловый браузер + md-редактор `docs/tasks/**`, дашборд со списком задач и статусами стадий (пока статусы выставляются вручную/статично). Даёт рабочий UI для стадии 1 без зависимости от агентской части.

**Phase 2 — Спайк: headless-вызов Claude на одной стадии**
Только `ClaudeAdapter.start/stream` для стадии «OpenSpec». Цель — подтвердить или опровергнуть гипотезу из §2 (следует ли headless-режим полному Router-циклу AGENTS.md) и зафиксировать реальный формат вывода/событий/детектор лимита. Это самая рискованная часть плана — от результата зависит форма `run_events` и адаптера.

**Phase 3 — Полный пайплайн стадий 2–5**
OpenSpec → approval-гейт (текстовое поле + 2 кнопки, «Доработать» задизейблена при пустом поле) → Разработка → QG, всё на `ClaudeAdapter`. Живой чат-стрим (§6) подключается здесь.

**Phase 4 — Обработка лимитов и resume (§7)**
Детекторы лимита по реальным наблюдениям Phase 2–3, UI-баннер, ручной повтор.

**Phase 5 — Завершение (стаб)**
Кнопка «Отметить завершённым» после успешного QG, без git/k8s-автоматизации — финальный статус задачи и ссылка на артефакты/отчёты для ручного мёржа пользователем.

**Phase 6 — Вне MVP, отдельные задачи в будущем**
- `CodexAdapter`, `MimoAdapter` — рабочие реализации.
- Скилл автоматизации git (коммит/PR/merge) и k8s-релиза — стадии 6–7 AO-001.
- Параллельный запуск нескольких execution units с разбивкой прямо в UI (сейчас декомпозиция целиком внутри одной headless-сессии агента).
- Уведомления (Telegram/etc.) о смене статуса задачи.
- Мульти-репозиторность (оркестрация не только `eqSiteCMS`).

## 10. Открытые вопросы

1. **Стек фронтенда** — Next.js (консистентность с `services/frontend`, переиспользование UI-kit) vs лёгкий Vite+React (меньше накладных расходов для внутреннего инструмента без SSR/SEO). Нужно решение перед Phase 0.
   **A:** Давай использовать Next.js с применением всех правил архитектуры CMS агента
2. **Формат headless-вывода Claude Code** и наличие/поведение continuation-сессий (`--resume` или аналог) для многошаговых стадий — закрывается спайком Phase 2, влияет на схему `run_events`.
   **A:** Я не понял вопроса. Мы можем хранить UUID сессии, чтобы в случае падения вернуться к ней
3. **Порог для перехода с polling-очереди на Celery/Redis-брокер** — сейчас сознательно не берём Celery, но стоит зафиксировать критерий (например, >3 параллельных задач регулярно), при котором пересмотреть.
   **A:** Давай ставить эти задачи просто в очередь
4. **Где живут секреты/сессии CLI при выходе за пределы однопользовательского локального режима** — не блокирует MVP (воркер = машина оператора, `claude login` уже локально авторизован), но явный технический долг, если инструмент когда-нибудь станет многопользовательским или переедет в контейнер CI.
   **A:** Нет, пока что не задумываемся об этом
5. **Точные сигнатуры «исчерпан лимит» у Claude CLI** — не фиксируются заранее в этом плане, чтобы не закладывать угадывание вместо наблюдения; собираются в Phase 2–4.
