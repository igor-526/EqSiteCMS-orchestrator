# AO-008 — ТЗ Phase 5: Завершение (стаб)

Часть плана [`AO-002-implementation_plan.md`](AO-002-implementation_plan.md), «Phase 5» из §9. Реализует терминальную ручную стадию из AO-001 («Завершение») **без** автоматизации git/k8s — она явно отложена на будущий отдельный скилл (AO-001, стр. 15; AO-002 §9 Phase 6).

Предыдущая фаза: [`AO-007`](AO-007-phase4-tz-quota-handling.md).
Следующая фаза: нет в текущем плане — Phase 6 из AO-002 §9 не имеет отдельного ТЗ (это бэклог будущих несвязанных задач: Codex/MiMo адаптеры, git/k8s-скилл, уведомления, мульти-репозиторность — каждая оформляется как отдельная задача, когда до неё дойдёт очередь).

Репозиторий оркестратора (по итогам AO-003): `orchestrator/` рядом с `eqSiteCMS`, отдельный git-репозиторий; backend-код — `api/src/{core,api,repositories}`.

## Факт по итогам AO-004 (Phase 1)

- `StageStatus.done`/`.skipped` и `TaskStatus.done` (`api/src/core/models.py`) уже определены с Phase 1 — переход `completion`/`release`/`task` в §1–§2 использует существующие значения enum'ов, схему менять не нужно.
- Ни один эндпоинт Phase 1 не пишет в `stage.status`/`task.status` — кнопка «Отметить завершённым» (§2) должна дергать новый эндпоинт поверх `TaskRepository`/`StageRepository` (`api/src/repositories/tasks.py`), которого пока нет; там же, по аналогии, стоит добавить метод точечного обновления статуса вместо правки `create_with_stages`.
- Дашборд (`frontend/src/app/page.tsx`) сейчас рендерит все задачи одной плоской таблицей и использует компонент `StageBadges` (`frontend/src/components/StageBadges.tsx`) для значков стадий. Отдельная секция/фильтр «Готово» из §3 естественно ложится поверх той же таблицы и того же компонента — переписывать вёрстку дашборда заново не требуется.
- `runs`/`worktree_path`/`branch_name`, которые сводка на экране должна показывать (§2), появляются только начиная с Phase 3 (AO-006) — в Phase 1 этих полей и таблицы `runs` ещё нет.

## Факт по итогам AO-005 (Phase 2, спайк)

- Модель `Run` (`orchestrator/api/src/core/models.py`, добавлена в Phase 2) уже содержит поля `worktree_path` (заполняется всегда, обязательное) и `branch_name` (nullable — в Phase 2 не заполнялось, worktree готовился вручную вне `ClaudeAdapter`). Сводка на экране (§2 ниже) может читать `worktree_path` уже из существующей колонки; `branch_name` станет реально заполненным только начиная с Phase 3 (AO-006 §1, git worktree lifecycle) — до этого поле будет `null` у всех `runs`, и это ожидаемо, а не баг.
- Разница между `cli_session_id` (UUID для `--session-id`/`--resume` конкретного CLI-процесса) и `branch_name`/`worktree_path` (git-уровень) подтверждена на практике — это разные оси, задача §2 показывает именно git-уровень (ветка/путь), не `cli_session_id`.

## Факт по итогам AO-006 (Phase 3)

Полный отчёт — `docs/reports/phase3-full-pipeline-quality-gate.md`; реализация/специфика — `orchestrator/openspec/changes/archive/2026-09-14-phase3-full-pipeline/`.

- **`stage(qg).status = done` реально реализовано и покрыто тестами** (`api/src/core/worker_loop.py::_transition_qg_finished`, `BE-6`) — предпосылка §1 этого файла подтверждена буквально: успешное завершение `run` стадии `qg` действительно переводит `stage(qg).status = done`. Провал `qg` возвращает `stage(developing).status = active` + новый `run`.
- **Но переход `qg → completion` НЕ реализован Phase 3** — `worker_loop.py` на успехе `qg` только ставит `stage(qg).status=done`, дальше ничего не делает. `stage(completion)` остаётся `pending`, как и было с Phase 1 — это открытая работа именно этой фазы (AO-008 §1), не побочный эффект Phase 3.
- **`Run.branch_name` реально заполняется начиная с Phase 3**, как и предполагал факт по итогам AO-005: `WorktreeService.ensure()`/`BE-3` заполняет его при первом `run` стадии `openspec` (`branch_name = "agent/<task_id>"`), и каждый последующий `run` той же задачи (rework, `developing`, `qg`, retry) копирует `branch_name`/`worktree_path` от предыдущего `run`'а той же цепочки (см. `_last_run_for_stage` в `api/src/api/stages.py`, `_transition_developing_success`/`_transition_qg_finished` в `worker_loop.py`) — значит на момент, когда задача дойдёт до `completion` (эта фаза), branch/worktree path гарантированно одни и те же на всех `runs` задачи, сводка §2 может взять их с любого `run`'а задачи, не только с последнего.
- **`artifacts` — реальная таблица с готовым read-эндпоинтом**: `GET /tasks/{id}/artifacts` (`api/src/api/tasks.py`, `BE-6`) уже отдаёт полный список артефактов задачи (`path`, `kind`, `discovered_at`), отсортированный `discovered_at desc`. Сводка §2 может напрямую переиспользовать этот эндпоинт и существующий frontend-паттерн вкладки «Артефакты» (`frontend/src/app/tasks/[id]/page.tsx`, `FE-3`), а не проектировать новый способ показа артефактов.
- **`StageType.decision`, как и `completion`/`release`, создаётся Phase 1 (`pending`) и не активируется ни одной фазой по сей день** (найдено и явно задокументировано в Phase 3, `BE-9`/`QG-CONTRACTS`: гейт принятия решения реализован через `StageStatus.waiting_decision` на стадии `openspec`, не через отдельную активацию строки `decision`). Для этой фазы это означает: `stage(decision)` **тоже** остаётся вечно `pending`, как и `release` — по аналогии с уже запланированным в §1 этого файла подходом к `release` («остаётся pending/переводится в skipped»), решить для `decision` то же самое (скорее всего тоже `skipped` или молчаливо игнорировать в UI), а не оставлять как необъяснённый «вечно pending» пункт на дашборде.
- **Фронтенд-логика выбора «активной стадии» уже общая, не хардкожена под конкретные типы** (`frontend/src/lib/stages.ts`, проверено `QG-FE` на живом стеке) — она выбирает первую стадию по `STAGE_ORDER` со статусом `active`/`waiting_decision`. Практическое следствие: как только эта фаза реализует переход `completion` в `active`, существующий UI-пикер сам корректно покажет эту стадию активной без переписывания логики выбора — новой работы там только сама кнопка «Отметить завершённым» и её обработчик.
- **Паттерн нового write-эндпоинта уже устоялся** (`take_into_work` в `BE-3`, `decisions` в `BE-5`) — новый эндпоинт «Отметить завершённым» стоит делать по тому же шаблону: получить стадию через `StageRepository`, проверить состояние ДО побочных эффектов (аналог `409` из `pipeline-stage-runs` spec), одна транзакция/`commit()` на все изменения статусов, без отдельного репозиторного метода на каждое поле.
- **Операционные правила, актуальные и для этой фазы** (стоили Phase 3 нескольких ложных диагнозов): (а) `docker compose cp` без `restart`/`build` не долетает до живого процесса — не доверяй поведению живого стека, пока не перезапустил после синхронизации кода; (б) любой live/manual-QA прогон должен использовать committed-стаб `worker/fixtures/fake_claude_cli.py`, не тратить реальный лимit подписки; (в) `git config --global --add safe.directory` обязателен в любом новом образе, который трогает worktree.

## Факт по итогам AO-007 (Phase 4)

Полный отчёт — `docs/reports/phase4-quota-handling-quality-gate.md`; реализация/специфика — `orchestrator/openspec/changes/archive/2026-09-15-phase4-quota-handling/` (после архивации; до архивации — `orchestrator/openspec/changes/phase4-quota-handling/`). Вердикт Quality Gate — **APPROVED** с одним явно зафиксированным открытым техдолгом (см. ниже).

- **`RunStatus` пополнился значением `stopped`** (существовало в enum'е с Phase 1, но фактически начало использоваться только в Phase 4): «честный fallback», когда resume по `cli_session_id` не удался на спавне процесса. Это означает, что к моменту, когда задача доходит до `completion` (эта фаза), в истории `runs` задачи вполне может встретиться `blocked_quota`/`stopped` наряду с `succeeded` — сводка §2 этого файла (branch/worktree/artifacts), если будет показывать список runs, не должна трактовать такие промежуточные статусы как признак незавершённости задачи: решает только `task.status`/`stage(qg).status`, а не наличие `blocked_quota`/`stopped` где-то в истории runs.
- **Логика выбора «активной стадии» на детальном экране задачи оказалась не полностью там, где ожидалось.** Факт по итогам AO-006 утверждал, что она полностью инкапсулирована в `frontend/src/lib/stages.ts`. Phase 4 (`FE-1`) обнаружила и расширила отдельный, дублирующий цикл прямо в `frontend/src/app/tasks/[id]/page.tsx` (условие `active || waiting_decision`, пришлось добавить `blocked_quota`) — именно он, а не (только) `stages.ts`, определяет `currentStage` на этой странице. **Перед реализацией §1/§2 этого файла (переход `completion → active`) явно проверь актуальное состояние обоих мест**, а не полагайся на устаревшее описание из факта AO-006 — велика вероятность, что `completion`/`active` тоже нужно будет добавить именно в этот локальный цикл `page.tsx`, а не только в `stages.ts`.
- **Дашборд не потребовал нового кода для визуального индикатора блокировки** — `StageBadges`/`STAGE_STATUS_COLORS` (Phase 1) уже рендерят `blocked_quota` корректно из коробки. Хороший прецедент для §3 этого файла: секция/фильтр «Готово» на дашборде, скорее всего, тоже ложится на существующую инфраструктуру без переписывания таблицы — но, в отличие от бейджей, для `done`-фильтра практическое поведение ещё не проверялось живьём, проверить перед тем, как считать это данностью.
- **Паттерн нового write-эндпоинта подтверждён третий раз подряд** (`take_into_work` → `decisions` → `retry`): получить сущность через repository, проверить состояние ДО побочных эффектов, `409` без побочных эффектов при неподходящем состоянии, одна транзакция на все изменения статусов. Эндпоинт «Отметить завершённым» из §2 этого файла стоит делать по этому же устоявшемуся шаблону.
- **Операционное правило про `docker compose build`/`restart` перед выводами (впервые зафиксировано в Phase 3) подтвердилось повторно и болезненно в Phase 4**: и `worker`-образ (`SMOKE-1`), и отдельно `frontend`-образ (`QA-1`) оказывались устаревшими на момент начала live/manual-QA сессии соответствующего исполнителя, потому что деплой-шаг из Migration Plan предыдущего unit'а не выполнялся автоматически. Для Phase 5: любой unit, добавляющий кнопку/эндпоинт «Отметить завершённым», обязан явно пересобрать и передеплоить оба образа (`api`/`worker` если бэкенд, `frontend` если фронт) непосредственно перед своей live/QA-проверкой, а не полагаться на состояние стенда, оставшееся от предыдущего unit'а.
- **`CLAUDE_CODE_OAUTH_TOKEN` в контейнере `worker` подтверждён пустым повторно** (`BE-1`, Phase 4) — тот же техдолг, что и с Phase 3, к текущей фазе не относится напрямую, но если Phase 5 добавит что-то, что реально спавнит `claude` CLI (маловероятно — это чисто UI/статусный переход), учесть.
- **Открытый техдолг, вынесенный из Phase 4, не влияющий на Phase 5**: текстовая/exit-code сигнатура исчерпания лимита (`ClaudeAdapter.is_quota_exceeded`) так и не была пронаблюдена вживую за всю фазу — детектор работает только на структурном канале `rate_limit_info.status`. Это независимо от `completion`/`release` стадий, упомянуто для полноты картины состояния проекта.

## Контекст

После успешного прохождения QG (`stage(qg).status = done`) нужен явный, видимый пользователю финальный шаг — «эта задача готова, я беру мёрж/деплой на себя вручную». Стадии 6 (`completion`) и 7 (`release`) существуют в схеме `stages` с Phase 1, но до этой фазы никогда не покидали `pending`.

## 1. Переход стадий

- Когда `stage(qg).status` становится `done` (уже реализовано в Phase 3) — `stage(completion).status` переходит из `pending` в `active` (доступно для ручного действия), а не остаётся висеть в `pending`.
- `stage(release)` остаётся `pending`/переводится в `skipped` — release-автоматизации нет и не планируется в этом плане; явно показать в UI, что это осознанно отложено, а не забыто (например, подпись «релиз — вручную, авто-стадия появится позже»).

## 2. UI

- На детальном экране задачи, когда `completion.status = active`: кнопка **«Отметить завершённым»**.
- Клик → `stage(completion).status = done`, `task.status = done`.
- Экран показывает сводку для ручного завершения пользователем:
  - имя ветки/путь worktree (`branch_name`/`worktree_path`, сохранённые в `runs` начиная с Phase 3);
  - список всех `artifacts`, накопленных за задачу (OpenSpec-файлы, отчёты QG);
  - явная подпись, что ветка/worktree **не удаляются автоматически** — пользователь сам решает, когда мёржить и когда чистить (`git worktree remove` и т.п.) — не давать оркестратору самому трогать git history задачи без явной команды пользователя, этого функционала здесь нет.

## 3. Дашборд

- Задачи со `task.status = done` визуально отделяются от активных (например, отдельная секция или фильтр «Готово»), чтобы не мешать в общем списке активных задач.

## Definition of Done

- [ ] Задача, реально прошедшая QG (через Phase 3-цикл), показывает активную кнопку «Отметить завершённым» на стадии `completion`.
- [ ] Клик переводит `completion` и `task` в `done`, кнопка возврата назад не предусмотрена (перезапуск — через создание нового цикла/run, не через откат этого статуса).
- [ ] Сводка на экране содержит реальные branch/worktree path и список артефактов, а не заглушку.
- [ ] Явно показано (текстом в UI), что git-мёрдж и k8s-релиз — ответственность пользователя, не оркестратора.
- [ ] Дашборд визуально отделяет завершённые задачи от активных.

## Явно вне скоупа Phase 5

- Любая git-операция, выполняемая самим оркестратором (commit/push/merge/PR).
- Любое взаимодействие с k8s.
- Автоматическая очистка worktree/веток.
