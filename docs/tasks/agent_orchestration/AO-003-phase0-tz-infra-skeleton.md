## Контекст (коротко, без необходимости читать остальные файлы)

Строим внутренний инструмент — веб-интерфейс, который вызывает Claude Code CLI (headless) для прохождения пайплайна разработки над репозиторием `eqSiteCMS`. Инструмент **полностью отделён от продукта eqSiteCMS**: отдельный git-репозиторий, не часть `services/*`, не упоминается в `services.manifest`/`SERVICES.md` eqSiteCMS. Единственная связь с eqSiteCMS — целевой репозиторий, в котором агент будет физически работать (см. §3).

Phase 0 — это **только инфраструктурный каркас**, без бизнес-логики пайплайна (нет задач, нет вызовов агента, нет живого чата). Критерий успеха — пустой, но полностью рабочий стек, поднимаемый одной командой.

## 1. Новый репозиторий

- Создать новый git-репозиторий (название на усмотрение исполнителя, например `eqsitecms-orchestrator`; далее в тексте — «репозиторий оркестратора»). Физически отдельный от `eqSiteCMS`.
- Базовые файлы: `README.md` (кратко — что это и `make up` для старта), `.gitignore` (Python + Node + Docker), `LICENSE` не требуется (внутренний инструмент).

## 2. Структура директорий

```
.
├── api/                  # FastAPI backend, Clean Architecture по аналогии с eqSiteCMS/services/backend
│   ├── src/
│   │   ├── core/         # доменная логика (пока пусто/заглушка)
│   │   ├── api/           # HTTP-роуты (пока только /health)
│   │   └── repositories/  # доступ к БД (пока пусто)
│   ├── alembic/           # миграции, инициализированы, но без доменных таблиц
│   ├── Dockerfile
│   └── pyproject.toml (или requirements.txt — на усмотрение исполнителя)
├── worker/                # процесс воркера; может переиспользовать пакет из api/src как зависимость
│   ├── src/main.py        # на Phase 0 — бесконечный idle-цикл с логом "worker started, idle"
│   └── Dockerfile
├── frontend/              # Next.js, структура app/features по аналогии с eqSiteCMS/services/frontend
│   ├── src/app/            # одна заглушка-страница
│   └── Dockerfile
├── docker-compose.yml     # единственный compose-файл всего стека
├── Makefile
├── .env.example
└── README.md
```

## 3. Конфигурация целевого репозитория

MVP работает ровно с одним целевым репозиторием — чекаутом `eqSiteCMS` на диске оператора. Путь передаётся через переменную окружения, например `TARGET_REPO_PATH`, и монтируется volume'ом в контейнеры `api` и `worker` (в Phase 0 — просто зарезервировать переменную и volume-маппинг в `docker-compose.yml`, реального использования пути ещё нет).

## 4. `docker-compose.yml`

Один файл, поднимающий все компоненты как отдельные контейнеры:

| Сервис | Образ/сборка | Назначение |
|---|---|---|
| `postgres` | `postgres:16` (или актуальная LTS) | БД оркестратора |
| `redis` | `redis:7` | pub/sub для стрима (используется с Phase 2+, но контейнер поднимается уже сейчас) |
| `api` | build `./api` | FastAPI backend |
| `worker` | build `./worker` | воркер (idle на Phase 0) |
| `frontend` | build `./frontend` | Next.js |

Требования:
- Все сервисы поднимаются `docker compose up -d` без ручных доп. шагов (кроме `make migrate` для первой миграции).
- `api` и `worker` ждут готовности `postgres`/`redis` (`depends_on` + healthcheck, не просто порядок запуска).
- Порты `api`/`frontend` публикуются на host (конкретные номера — на усмотрение исполнителя, зафиксировать в `.env.example`).
- Volume для `postgres` данных (не терять БД при `docker compose down` без `-v`).

## 5. Makefile

Минимум целей:
- `make up` — `docker compose up --build -d`
- `make down` — `docker compose down`
- `make logs` — `docker compose logs -f`
- `make migrate` — прогон Alembic-миграций внутри контейнера `api`
- `make check` — заглушка (может пока просто вызывать `docker compose config` для валидации) — реальные lint/test появятся, когда появится код в Phase 1+

## 6. Health-эндпоинты и заглушки

- `api`: `GET /health` → `200 {"status": "ok"}`.
- `frontend`: любая страница на `/`, статически рендерящая «Orchestrator — Phase 0», без реального функционала.
- `worker`: при старте пишет в stdout `worker started, idle` и держит процесс живым (например, `sleep`-цикл с периодическим логом), не падает.

## 7. OpenSpec для самого оркестратора (по возможности)

Если исполнитель имеет доступ к `openspec` CLI/скиллам — инициализировать `openspec/` в новом репозитории (`openspec init` или аналог) с минимальным `project.md`, описывающим конвенции нового репозитория (стек, структура директорий из §2). Это даёт возможность вести Phase 1 и далее через собственный OpenSpec-workflow оркестратора, если пользователь решит так делать. Если инструментарий недоступен в среде исполнителя — пропустить этот пункт без блокировки остального Phase 0, явно отметить в handoff/отчёте, что пункт пропущен и почему.

- [x] `make up` поднимает весь стек без ошибок (проверено на месте; свежий `git clone` не проверялся отдельно, т.к. репозиторий ещё не запушен).
- [x] `curl localhost:<api_port>/health` → `200`.
- [x] Frontend открывается в браузере, отдаёт заглушку (`curl localhost:3000` → title/body «Orchestrator — Phase 0»).
- [x] Лог `worker` показывает `worker started, idle`.
- [x] `make down` корректно останавливает стек, `make up` после этого поднимает его заново без потери данных `postgres` (проверено: таблица `alembic_version`, созданная `make migrate` до `down`, сохранилась после повторного `up`; volume не пересоздавался).
- [x] `TARGET_REPO_PATH` зарезервирован в `.env.example` и смонтирован volume'ом в `api`/`worker` (bind-mount в `/target_repo`, не используется в коде).
- [x] Пункт §7 выполнен: `openspec init --tools claude .` в новом репозитории, конвенции (стек, структура директорий) описаны в `openspec/config.yaml` → `context`.

### Заметки по реализации

- `api/pyproject.toml` подключает и `asyncpg` (рантайм), и `psycopg2-binary` (нужен Alembic, который использует синхронный движок SQLAlchemy).
- `alembic/versions/` пуст (нет доменных таблиц на Phase 0), `make migrate` создаёт только служебную таблицу `alembic_version`.
- Frontend собирается как Next.js `output: "standalone"` для лёгкого runtime-образа.
- Порты по умолчанию: `API_PORT=8000`, `FRONTEND_PORT=3000` (зафиксированы в `.env.example`, при конфликте на машине оператора — переопределяются через `.env`).
- Репозиторий пока не запушен на удалённый git-хостинг и не закоммичен (первый коммит — на усмотрение пользователя).

## Явно вне скоупа Phase 0

- Любая доменная модель данных (`tasks`, `stages`, `runs` и т.д. — это Phase 1+).
- Любой вызов CLI-агента.
- UI дальше одной заглушки.
- Реальное использование `TARGET_REPO_PATH` (чтение файлов, git-операции).
