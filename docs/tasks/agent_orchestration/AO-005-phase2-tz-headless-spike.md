# AO-005 — ТЗ Phase 2: Спайк — headless-вызов Claude

Часть плана [`AO-002-implementation_plan.md`](AO-002-implementation_plan.md), «Phase 2» из §9. Это **спайк** (исследовательская задача с таймбоксом), а не финальная production-реализация — результат допускает форму «не сработало так, как предполагалось, вот что делать вместо этого».

Предыдущая фаза: [`AO-004`](AO-004-phase1-tz-task-management.md).
Следующая фаза: [`AO-006`](AO-006-phase3-tz-full-pipeline.md) — и её объём зависит от результата этого спайка.

## Факт по итогам AO-003 (Phase 0), важный для этого спайка

Репозиторий оркестратора живёт в `orchestrator/` рядом с `eqSiteCMS` (отдельный git-репозиторий). `TARGET_REPO_PATH` (host-чекаут `eqSiteCMS`) смонтирован bind-volume'ом **только по пути `/target_repo` внутри контейнеров `api`/`worker`** — больше никакие host-пути внутрь этих контейнеров не проброшены. Практическое следствие для п.1 и п.2 ниже: если эксперимент с `ClaudeAdapter.start` запускается из контейнера `worker` (а не «прямо в терминале» на хосте), то и сам CLI-вызов, и создаваемый для него git worktree должны находиться внутри `/target_repo` (или в отдельном пути, который тоже явно смонтирован volume'ом) — иначе worktree, созданный по host-пути вида `~/.orchestrator/worktrees/...`, будет просто невидим внутри контейнера. Зафиксировать по факту эксперимента, какой вариант выбран (worktree внутри `/target_repo` vs. отдельный смонтированный volume для worktree'ев) — это входные данные для §1 AO-006.

## Факт по итогам AO-004 (Phase 1), важный для этого спайка

- Миграция `tasks`/`stages` уже существует как `api/alembic/versions/0001_create_tasks_stages.py` (`revision = "0001"`, `down_revision = None`). Миграция `runs`/`run_events` из §2 ниже должна цепляться от неё (`down_revision = "0001"`), а не начинать отдельную ветку ревизий.
- В Phase 1 закреплён паттерн бэкенда, которому стоит следовать и здесь: async SQLAlchemy (`api/src/core/db.py` — `async_database_url()` + `get_session()` как FastAPI-зависимость), декларативные модели с нативными Postgres-enum'ами в `api/src/core/models.py`, репозитории вида `<Domain>Repository(session: AsyncSession)` в `api/src/repositories/`. Модели `Run`/`RunEvent` и `RunRepository` для этого спайка стоит класть туда же по той же схеме, а не заводить отдельный слой.
- `resolve_task_path()` в `api/src/core/files.py` намеренно отклоняет любой путь вне `docs/tasks/**` — для путей worktree (вне `docs/tasks`) он не подходит и переиспользовать его для эксперимента с `ClaudeAdapter.start` нельзя; нужен отдельный резолвер путей (или доверенный абсолютный путь из конфига), без завязки на `docs/tasks`-ограничение.
- Frontend обращается к API прямо из браузера через `NEXT_PUBLIC_API_URL`, зашитый на этапе сборки Docker-образа (`frontend/Dockerfile` ARG + `docker-compose.yml` build.args, по умолчанию `http://localhost:${API_PORT}`) — реверс-прокси нет, все страницы `"use client"` без серверных Next.js data-fetch'ей. Страница поллинга `run_events` из §2 должна следовать этому же паттерну (прямой fetch/поллинг из браузера на тот же `NEXT_PUBLIC_API_URL`).
- Кнопка «Взять в работу» на детальном экране задачи (`frontend/src/app/tasks/[id]/page.tsx`) в Phase 1 — чисто фронтенд-стаб: не вызывает backend и ничего не пишет в БД (максимум локальный React-state). Для целей спайка запуск `ClaudeAdapter.start` можно триггерить отдельным временным способом (скрипт/ручной вызов эндпоинта) — переиспелить эту кнопку буквально не получится без доработки.
- Вкладка «Артефакты» на том же детальном экране — сейчас статичная строка-заглушка («появится в Phase 3»); это ровно то место, где в Phase 3 появится реальный список, в этом спайке трогать не обязательно.

## Контекст и почему это отдельная фаза

Ключевая гипотеза всего проекта (AO-002 §2): headless/print-режим Claude Code CLI, запущенный внутри чекаута `eqSiteCMS`, самостоятельно проходит весь Router-цикл из `AGENTS.md` (маршрутизация → Planner → делегирование профильным подагентам) в рамках одного вызова CLI, вплоть до approval-гейта или завершения — без необходимости оркестратору самому реализовывать эту логику. Если гипотеза не подтвердится, форма адаптера и модель `run_events` могут измениться до того, как на них будет построен весь Phase 3.

## Задачи спайка

### 1. Найти рабочую форму headless-вызова

Экспериментально (можно прямо в терминале, вне кода оркестратора, на тестовой ветке/worktree `eqSiteCMS`) определить:

- Точную команду и флаги запуска Claude Code CLI в полностью автономном headless-режиме против md-файла задачи из `docs/tasks/`, так чтобы CLI выполнил цепочку `openspec-propose` до готовности apply-ready артефактов **без interactive-подтверждений на каждый шаг** (нужен подходящий уровень авто-разрешений на инструменты — конкретный флаг зафиксировать по факту, не предполагать заранее).
- Формат доступного вывода (обычный текст vs. структурированный/стриминговый JSON) — что реально можно распарсить построчно: текстовые чанки ассистента, tool_use/tool_result события, признак ухода во вложенного субагента, финальный сигнал «остановился на approval-гейте, жду пользователя».
- Механизм продолжения/резюмирования сессии (эквивалент `--resume` с session id) — подтвердить, что после получения этого id можно позже продолжить именно эту сессию (а не начать новую с нуля). Это напрямую отвечает на ответ пользователя в AO-002 §10 (вопрос 2): «храним UUID сессии, чтобы в случае падения вернуться к ней» — здесь нужно подтвердить, что такой UUID существует и способ резюма реально работает.
- Если представится случай (упереться в реальный лимит подписки во время экспериментов) — зафиксировать точный текст/exit code сигнала «лимит исчерпан». Если за время спайка лимит не встретится — явно отметить это как открытый пункт для Phase 4, не выдумывать сигнатуру заранее.

### 2. Минимальная сквозная реализация

В кодовой базе оркестратора (поверх каркаса Phase 0):

- Миграция, добавляющая таблицы `runs` и `run_events` (схема — AO-002 §4).
- `ClaudeAdapter.start(stage_context)` — спавнит найденную в п.1 команду в git worktree тестовой задачи `eqSiteCMS` (можно создать worktree вручную/скриптом для целей спайка — полноценный lifecycle worktree'ев из AO-002 §8 реализуется в Phase 3, здесь достаточно рабочего прототипа).
- `ClaudeAdapter.stream(run_id)` — построчно парсит вывод в найденном формате, пишет строки в `run_events`.
- Простейшая страница фронтенда (можно без дизайна) — открывает `run_id` и показывает `run_events` живым списком (polling REST допустим на этом этапе, WebSocket — не обязателен в спайке, полноценный стрим через Redis pub/sub — предмет Phase 3, AO-002 §6).

### 3. Итоговый отчёт спайка

Короткий раздел ниже в этом же файле (дописать по факту прогона) фиксирует:
- Финальную команду/флаги вызова.
- Схему событий, которую реально отдаёт CLI (с примером сырого фрагмента вывода).
- Подтверждён или не подтверждён механизм резюмирования по session id.
- Наблюдалась ли сигнатура исчерпания лимита; если да — точный текст/код.
- **Главный вывод**: подтвердилась ли гипотеза «headless проходит весь Router-цикл автономно» — да / нет / частично, и если нет — какой альтернативный механизм предлагается для Phase 3 (например, серия отдельных вызовов с явными промежуточными шагами вместо одного непрерывного автономного прогона).

## Отчёт по результатам спайка (заполняется исполнителем)

Эксперимент проведён на хосте (не из контейнера `worker`) в изолированном git worktree тестовой ветки `eqSiteCMS` (`spike/ao005-headless-test`, вне рабочего дерева оператора — в scratchpad-директории агентной сессии). Три реальных прогона + один резюм:
1. `docs/tasks/_spike_test_task.md` (тривиальная однострочная правка `SERVICES.md`) с `--permission-mode acceptEdits --permission-prompts none`.
2. Тот же файл с `--permission-mode bypassPermissions`.
3. `docs/tasks/_spike_test_task2.md` (архитектурная задача — новый эндпоинт) с `--permission-mode bypassPermissions`.
4. `--resume` того же session id из прогона 3.

- **Команда и флаги:**
  ```
  claude -p "<промпт>" --output-format stream-json --verbose --permission-mode bypassPermissions --session-id <uuid>
  ```
  Резюмирование — та же команда с `--resume <uuid>` вместо `--session-id <uuid>`.

  `--session-id` генерируется **оркестратором до старта процесса** (не парсится из вывода постфактум) — подтверждено, что переданный UUID проходит сквозь весь `stream-json`-вывод (`system/init.session_id` и `result.session_id`) неизменным.

  Критично: `--permission-mode acceptEdits --permission-prompts none` **недостаточно**. В прогоне 1 первый же `Bash`-вызов скилла `openspec-propose` (`openspec new change ...`) был автоматически отклонён (`system/permission_denied`, `decision_reason: "no approval surface in this session"`) — и это относится к **любому** `Bash`, включая read-only `openspec status`. Агент сам корректно остановился (не стал обходить ограничение, как и требует `AGENTS.md`) и явно спросил, как продолжать. Нужен именно `--permission-mode bypassPermissions` — тогда весь пайплайн проходит без единого отказа.

- **Формат событий (stream-json, построчный JSON).** Наблюдённые `type`/`subtype`:
  - `system` / `init` — конфигурация сессии (`session_id`, `model`, `permissionMode`, список `tools`/`skills`/`agents`).
  - `rate_limit_event` — квота: `rate_limit_info.unifiedWindows.{five_hour,seven_day}.{utilization,resetsAt}` — готовый структурированный сигнал, без парсинга текста.
  - `assistant` — content-блоки `thinking` / `tool_use` / `text` (каждое событие обычно несёт один тип блока).
  - `user` — `tool_result` (включая тексты денаев permission).
  - `system` / `thinking_tokens` — счётчик токенов рассуждений.
  - `system` / `permission_denied` — явный отказ инструмента с текстом причины.
  - `result` (финальное событие) — `subtype: "success"`, `total_cost_usd`, `usage`, `permission_denials`, `stop_reason`, `terminal_reason: "completed"`, `num_turns`.

  Пример сырого фрагмента (событие `rate_limit_event`):
  ```json
  {"type":"rate_limit_event","rate_limit_info":{"status":"allowed","resetsAt":1789153200,"rateLimitType":"five_hour","overageStatus":"rejected","isUsingOverage":false,"unifiedWindows":{"five_hour":{"utilization":0.41,"resetsAt":1789153200},"seven_day":{"utilization":0.13,"resetsAt":1789639200}}},"session_id":"3c7f4da8-..."}
  ```
  Пример финального `result`:
  ```json
  {"stop_reason":"end_turn","total_cost_usd":0.4888,"num_turns":25,"subtype":"success","terminal_reason":"completed","result":"Артефакты готовы (openspec validate --strict — успешно, 4/4 apply-ready) ... Согласно AGENTS.md, дальше требуется твоё подтверждение..."}
  ```

- **Резюмирование по session id — подтверждено.** Прогон 4 (`--resume <session_id из прогона 3>`) вернул тот же `session_id` в `system/init` и в `result`, за 1 turn и $0.018 корректно процитировал детали `design.md`, принятые в прогоне 3 (конкретную capability и access-класс), не перечитывая ни одного файла — то есть это реальное продолжение той же сессии, а не новая сессия с нуля. Отвечает на вопрос пользователя из AO-002 §10 (п.2): UUID сессии, сохранённый оркестратором, действительно работает как ключ резюма.

- **Сигнатура исчерпания лимита — не наблюдалась.** За все прогоны `rate_limit_info.status` был `"allowed"`, утилизация 5-часового окна доходила максимум до ~0.41. Остаётся открытым пунктом для Phase 4 (AO-007), как и предполагалось. Полезная находка: `rate_limit_event` в принципе даёт структурированный сигнал утилизации на каждом шаге — это более надёжная основа для будущего `is_quota_exceeded`, чем ожидание текстовой сигнатуры отказа.

- **Главный вывод: гипотеза Router-цикла ПОДТВЕРЖДЕНА, с двумя уточнениями.**
  1. **Headless-режим действительно проходит весь Router-цикл `AGENTS.md` автономно в рамках одного вызова CLI**, без внешнего управления оркестратором на каждом шаге. Подтверждено на двух разных сценариях: (а) тривиальная задача — CLI сам прочитал `AGENTS.md`, распознал паттерн «Example 2» (маленький однозначный фикс) и делегировал через встроенный `Agent` tool_use **вложенному субагенту внутри того же процесса** (`subagent_type: "claude"`, видно по `parent_tool_use_id`) — без единого дополнительного внешнего CLI-вызова; (б) архитектурная задача — CLI сам прочитал `AGENTS.md`, распознал паттерн «Example 1» (нужен Planner), прогнал скилл `openspec-propose` (создание change, чтение per-artifact инструкций, запись `proposal.md`/`design.md`/`specs/**/*.md`/`tasks.md`, `openspec validate --strict`) до apply-ready артефактов (4/4) и **сам корректно остановился**, дословно запросив подтверждение пользователя — то есть approval-гейт стадии 3 AO-001 не требует отдельного механизма на стороне оркестратора для *обнаружения* точки остановки: CLI сам заканчивает `result.subtype=success` с текстом, ожидающим решения.
  2. **Уточнение для архитектуры адаптера**: делегирование субагентам (Router→Backend) происходит через встроенный `Agent` tool **внутри одного процесса/одной stream-json сессии**, а не через отдельные внешние CLI-вызовы с `--resume` между шагами. Значит `ClaudeAdapter` для одной стадии пайплайна не должен спавнить несколько процессов или управлять цепочкой резюмирований сам — достаточно **одного** headless-вызова на стадию; `--resume` нужен только для явного продолжения *уже завершённого* рана (например, follow-up после approval-решения пользователя на стадии 3), а не для внутренней механики Router→Planner→Backend.

  **Рекомендация для Phase 3 (AO-006):** не вводить дополнительный уровень оркестрации Router-цикла на стороне `orchestrator` — по одному `ClaudeAdapter.start` на стадию/запуск, с обязательным `--permission-mode bypassPermissions` (см. риск ниже) и последующим `--resume` только для явных continuation-сценариев (approval-гейт → комментарий пользователя → продолжение той же CLI-сессии). Отдельно зафиксировать как технический долг: контейнеры `api`/`worker` пока не содержат бинарник Claude Code CLI и не имеют доступа к авторизованной сессии подписки — вариант с монтированием `~/.claude` хоста внутрь контейнера признан рискованным (конфликтует с параллельно работающей интерактивной сессией на той же машине) и требует отдельного решения в Phase 3 (например, выделенный `claude login` именно для процесса-воркера, а не шаринг сессии оператора).
