# AO-006 — ТЗ Phase 3: Полный пайплайн стадий 2–5

Часть плана [`AO-002-implementation_plan.md`](AO-002-implementation_plan.md), «Phase 3» из §9.

Предыдущая фаза: [`AO-005`](AO-005-phase2-tz-headless-spike.md) — **обязательно прочитать итоговый отчёт спайка** (раздел в конце файла AO-005) перед началом: он фиксирует реальный формат вызова/событий и подтверждает или опровергает гипотезу автономного Router-цикла. Если гипотеза не подтвердилась, реализовывать нужно предложенную в отчёте альтернативу, а не схему из этого ТЗ буквально.
Следующая фаза: [`AO-007`](AO-007-phase4-tz-quota-handling.md).

## Контекст

Это самая крупная фаза — здесь пайплайн становится реально сквозным: от клика «Взять в работу» до отчёта Quality Gate, с живым чатом по каждому агенту. Строится на:
- `tasks`/`stages` из Phase 1,
- `runs`/`run_events` и рабочем `ClaudeAdapter` из Phase 2,
- реальной команде/формате событий, зафиксированных в отчёте Phase 2.

## Факт по итогам AO-003 (Phase 0)

`TARGET_REPO_PATH` смонтирован bind-volume'ом только по фиксированному пути `/target_repo` внутри контейнеров `api`/`worker` (никакие другие host-пути внутрь них не проброшены). Путь worktree из §1 ниже должен быть выбран с учётом этого — либо подпуть внутри `/target_repo`, либо отдельный, явно добавленный в `docker-compose.yml` volume, смонтированный в оба контейнера (`api` и `worker`). Какой вариант реально рабочий — должно быть зафиксировано в отчёте спайка AO-005; если там это не проверено, проверить перед реализацией этого пункта, а не полагаться на пример `~/.orchestrator/worktrees/<task_id>` буквально.

## Факт по итогам AO-004 (Phase 1)

- Enum'ы `StageStatus` и `TaskStatus` (`api/src/core/models.py`) уже содержат все значения, нужные этой фазе: `StageStatus.waiting_decision`/`blocked_quota`/`done` и `TaskStatus.in_pipeline` определены с Phase 1, хоть и не использовались до сих пор — переходов схемы менять не нужно, только реализовать код, который реально проставляет эти статусы.
- В Phase 1 нет ни одного эндпоинта, который меняет `task.status`/`stage.status` — кнопка «Взять в работу» (`frontend/src/app/tasks/[id]/page.tsx`) чисто фронтенд-стаб без вызова backend. Все переходы статусов из §2–§6 этого файла (`stage.status = waiting_decision`, `= active`, `= done` и т.д.) нужно реализовать с нуля как новые эндпоинты/сервисы поверх `TaskRepository`/`StageRepository` (`api/src/repositories/tasks.py`) — расширить репозиторий методами точечного обновления статуса, не переписывать `create_with_stages`.
- Миграция `tasks`/`stages` — `api/alembic/versions/0001_create_tasks_stages.py` (`revision = "0001"`). Миграции `runs`/`run_events` (Phase 2) и `artifacts`/`decisions` (эта фаза, AO-002 §4) должны образовывать одну цепочку `down_revision`, а не параллельные ветки.
- `resolve_task_path()` (`api/src/core/files.py`) жёстко ограничен `docs/tasks/**` — для worktree-путей (§1) и для обнаружения артефактов (§7, `openspec/changes/**`, `docs/reports/**` внутри worktree, а не внутри `docs/tasks`) нужен отдельный path-хелпер, этот переиспользовать нельзя.
- CORS в `api/src/main.py` открыт (`allow_origins=["*"]`) — осознанное решение Phase 1 для single-operator инструмента (см. `orchestrator/openspec/changes/phase1-task-management/design.md`). `WS /runs/{id}/stream` из §5 будет обслуживаться с той же политикой, если её не пересматривать отдельно.
- Вкладка «Артефакты» на детальном экране задачи (`frontend/src/app/tasks/[id]/page.tsx`) сейчас статичная заглушка-строка — ровно то место, где §7 должен подключить реальные данные вместо неё.
- Backend/frontend уже используют устойчивый паттерн: async SQLAlchemy + репозитории (`api/src/repositories/`) на бэкенде, клиентские `"use client"` компоненты с прямым fetch на `NEXT_PUBLIC_API_URL` на фронтенде (без серверных Next.js data-fetch'ей). Новый код этой фазы стоит класть в ту же структуру, а не вводить параллельный слой.

## Факт по итогам AO-005 (Phase 2, спайк)

Полный отчёт — в конце `AO-005-phase2-tz-headless-spike.md`. Главное для реализации этой фазы:

- **Гипотеза автономного Router-цикла подтвердилась.** Один headless-вызов `claude -p ...` реально проходит `AGENTS.md`-цикл целиком (маршрутизация → делегирование через встроенный `Agent` tool **внутри того же процесса**, без внешних дополнительных CLI-вызовов) и сам корректно останавливается на approval-гейте (`result.subtype="success"`, текст с явным вопросом к пользователю). Практическое следствие для §2 и §4 ниже: **не нужно** вводить свой уровень оркестрации Router→Planner→Backend — один `ClaudeAdapter.start` на стадию/run достаточен, если гипотеза не опровергнута повторно на более сложных реальных задачах. §4 («если отчёт Phase 2 показал, что автономный прогон не проходит цикл — реализуется альтернатива») можно читать как закрытый пункт: альтернатива не нужна, реализовывать «один run на стадию».
- **Обязательный флаг — `--permission-mode bypassPermissions`.** `acceptEdits` + `--permission-prompts none` недостаточно: блокирует любой `Bash`-вызов (включая read-only), а `openspec-propose`/`openspec-apply-change` целиком построены на `Bash`-вызовах CLI `openspec`. Полная команда: `claude -p "<prompt>" --output-format stream-json --verbose --permission-mode bypassPermissions --session-id <uuid>`. Из этого следует, что worktree-изоляция (§1 ниже) — не гигиена, а обязательное условие безопасности: `bypassPermissions` даёт CLI полное доверие внутри `cwd`.
- **`--session-id` генерируется оркестратором до старта процесса** (не парсится из вывода) и проходит сквозь весь `stream-json`-вывод неизменным — `runs.cli_session_id` можно и нужно заполнять до спавна.
- **Резюмирование подтверждено**: `claude -p "<follow-up>" --resume <cli_session_id>` реально продолжает ту же сессию (проверено: корректно процитировала решения из предыдущего рана без перечтения файлов, $0.018/1 turn). Для §3 ниже («Доработать артефакты») это значит: follow-up run — это **новый `runs`-ряд с тем же `cli_session_id`**, что и исходный run (не новый UUID), запущенный с `--resume` вместо `--session-id`.
- **Открытый вопрос, НЕ закрытый этим спайком**: эксперимент AO-005 проводился прямо в терминале на хосте (не из контейнера `worker`), поэтому вариант «worktree внутри `/target_repo`» из факта AO-003 выше **не проверен на практике**. Хуже того: контейнеры `api`/`worker` (см. `orchestrator/api/Dockerfile`) сейчас вообще не содержат бинарник Claude Code CLI и не имеют доступа к авторизованной сессии подписки — `claude login` только на хосте оператора. Монтирование `~/.claude` хоста внутрь контейнера признано в AO-005 рискованным (конфликт с одновременно работающей интерактивной сессией на той же машине) и не тестировалось. **Это блокер для §1/§2 этой фазы**, который нужно решить одним из способов до начала реализации: (а) установить CLI-бинарь в образ `api`/`worker` и завести отдельный `claude login`/`setup-token` для процесса-воркера (не шарить сессию оператора), либо (б) продолжать спавнить `ClaudeAdapter`-процесс на хосте вне докер-сети, обращаясь к БД через проброшенный порт Postgres. Выбор — вход в проектирование этой фазы, не факт, который уже есть.
- **Таксономия `run_events.type`** (реализована в Phase 2, `api/src/core/claude_adapter.py::classify_event`): `system_init`, `rate_limit`, `assistant_thinking`, `assistant_tool_use`, `assistant_text`, `assistant` (смешанный content), `tool_result`, `permission_denied`, `thinking_tokens`, `result`, `unknown` (fallback на нераспознанный `type`/`subtype`, с сырым JSON — не роняет стрим). §5 (живой чат) может строить UI прямо на этих типах, не изобретая свою классификацию.
- **`rate_limit_event.rate_limit_info.unifiedWindows.{five_hour,seven_day}.utilization`** — уже структурированный сигнал квоты, наблюдается в каждом прогоне (не только при исчерпании). Сигнатура самого исчерпания лимита не наблюдалась (открыто для AO-007), но сам канал сигнала уже есть и пишется в `run_events` без дополнительной работы.
- Модели `Run`/`RunEvent`, `RunRepository`/`RunEventRepository`, `ClaudeAdapter.start/stream`, эндпоинты `POST /runs`/`GET /runs/{id}/events` и страница `frontend/src/app/runs/[id]/page.tsx` (REST-поллинг) уже существуют в кодовой базе оркестратора (`orchestrator/openspec/changes/phase2-headless-spike/`) — эта фаза их расширяет (WS вместо поллинга, множественные `runs` на стадию, git worktree lifecycle), а не создаёт с нуля.

## 1. Git worktree lifecycle (AO-002 §8)

- При клике «Взять в работу» на задаче (Phase 1 UI-стаб оживает):
  - создать ветку `agent/<task_id>` от актуального `main` целевого репозитория;
  - создать git worktree в отдельной директории вне основного пути пользователя (например `~/.orchestrator/worktrees/<task_id>` — конкретный путь вынести в конфиг);
  - записать `branch_name`/`worktree_path` на уровне задачи (или на каждый `run` — см. схему `runs` в AO-002 §4, там уже есть оба поля).
- Повторное «взятие в работу» той же задачи переиспользует существующий worktree, если он ещё не удалён, а не создаёт новый.
- Удаление worktree — не автоматизируется в этой фазе (см. Phase 5, там же финальная судьба ветки).

## 2. Стадия 2 — OpenSpec

- «Взять в работу» → создаёт `run` (agent=claude, stage=openspec) → worker стартует `ClaudeAdapter` по контракту из Phase 2 в свежесозданном worktree.
- Комментарий, введённый пользователем при взятии в работу (поле из AO-001 «Взятие в работу»), передаётся как часть промпта/входных данных этого run'а.
- Живой чат (см. §5) отображает события run'а по мере поступления.
- По завершении run'а (успешно дошёл до approval-гейта) — `stage.status = waiting_decision`.

## 3. Стадия 3 — Гейт принятия решения

UI по точной спецификации AO-001 («Подтверждение OpenSpec»):
- Одно текстовое поле — либо ответ на открытые вопросы агента, либо комментарий на apply.
- Кнопка **«Доработать артефакты»** — disabled, если поле пустое. При клике: создаёт новый `run` той же стадии `openspec` с текстом поля как follow-up входом (используя механизм резюмирования сессии, если он подтверждён в отчёте Phase 2, либо новый run с явной передачей контекста предыдущего — в зависимости от вывода спайка). `stage.status` возвращается в `active` на время этого run'а, затем снова `waiting_decision`.
- Кнопка **«Приступить»** — всегда enabled (комментарий на этом шаге опционален). При клике: пишет строку в `decisions` (`action=proceed`, `comment_text` = содержимое поля, может быть пустым), `stage(openspec).status = done`, создаёт `run` для стадии `developing`.

## 4. Стадия 4 — Разработка

- Один `run` (agent=claude, stage=developing), запускающий headless-эквивалент `openspec-apply-change` в том же worktree. Именно на этом шаге сам агент внутри своей сессии следует `AGENTS.md` целевого репозитория (Router/execution units/делегирование подагентам) — оркестратор в это не вмешивается, только показывает единый поток событий этого run'а.
- Если отчёт Phase 2 показал, что автономный прогон не проходит весь цикл за один headless-вызов (гипотеза не подтвердилась) — здесь реализуется альтернатива из отчёта (например, серия run'ов с явными шагами); в этом случае количество и логика `run`'ов на этой стадии должны быть переопределены по факту, а не по буквальному «один run».

## 5. Живой чат / работа над задачей (AO-002 §6)

- Полноценный стрим вместо polling из спайка: worker публикует событие в Redis-канал `run:<run_id>` **и** пишет в `run_events`; `api` отдаёт `WS /runs/{id}/stream` (relay) + `GET /runs/{id}/events` (история/reconnect).
- Экран «Работа над задачей»: список активных `runs` под задачей — агент, стадия, статус, с учётом требования AO-001 «видеть каждого агента, их количество». Если под одной стадией параллельно несколько `runs` (см. QG ниже) — каждый в своей вкладке/карточке, не смешивать ленты.

## 6. Стадия 5 — Quality Gate

- На основе вывода Phase 2/отчёта решить: один `run` (единый headless-прогон `code-review`) или несколько параллельных `run`'ов по lane-модели (`QG-BE`/`QG-FE`/`QG-CONTRACTS`/... из `AGENTS.md`) — зафиксировать выбор в этом же файле по факту реализации (дописать ниже, в блоке «Решения по факту реализации»).
- Результат — отчёт (файл в целевом репозитории, обычно `docs/reports/**`), обнаруживаемый через diff worktree (см. §7) и попадающий в `artifacts`.
- `stage(qg).status = done` при успешном прохождении. Обработка провала QG (findings, повторные ранов) — минимально: провал возвращает стадию `developing` в `active` с новым `run`, конкретный UX (что видит пользователь) — на усмотрение исполнителя, не блокирует DoD этой фазы, если базовый цикл «QG упал → снова разработка» технически работает.

## 7. Обнаружение артефактов

- После завершения каждого `run`'а worker считает diff worktree относительно базовой ветки (`git diff --name-status <base>...HEAD` внутри worktree).
- Новые/изменённые файлы, попадающие под известные паттерны (`openspec/changes/**`, `docs/reports/**`), — вставляются как строки в `artifacts` (`task_id`, `run_id`, `path`, `kind`, `discovered_at`).
- Вкладка «Артефакты» в детальном экране задачи (Phase 1 заглушка) теперь отдаёт реальный список.

## Definition of Done

- [x] От клика «Взять в работу» до завершения OpenSpec-стадии — реальный worktree создан, реальный run прошёл, чат отображает события живьём (через WS, не polling).
- [x] Approval-гейт: «Доработать» действительно недоступна на пустом поле и запускает follow-up run при заполненном; «Приступить» фиксирует decision и переводит стадию.
- [x] Стадия «Разработка» реально запускает headless-агента в том же worktree и стрим виден в чате.
- [x] Стадия QG отдаёт реальный отчёт, найденный и показанный как artifact.
- [x] Дашборд отражает актуальные статусы стадий по всему циклу без ручных правок в БД.
- [x] Раздел «Решения по факту реализации» ниже заполнен (выбор между одним QG-run и lane-моделью, и как решился вопрос из §4 про автономность headless-цикла).

## Решения по факту реализации (заполняется исполнителем)

- **QG: один run vs lane-модель — выбор и почему:** выбран **один `run` на стадию `qg`**, не отдельные `run`'ы на каждый lane (`QG-BE`/`QG-FE`/`QG-CONTRACTS`/...). Причина: AO-005 уже подтвердил, что делегирование Router→подагент внутри целевого репозитория происходит целиком внутри одной CLI-сессии через встроенный `Agent` tool — заводить отдельные процессы-`run`'ы под каждый lane на стороне оркестратора означало бы дублировать эту логику снаружи, что прямо запрещено §4 этого ТЗ. Промпт стадии `qg` — параметризуемая константа, ссылающаяся на скилл `code-review` целевого репозитория, без хардкода списка lane'ов; сам целевой репозиторий через свой `AGENTS.md` решает, сколько lane'ов реально понадобится. UI «несколько runs под одной стадией» сохранён и используется — но для последовательных повторов (rework, retry после провала QG), не для параллельных lane-процессов.
- **Автономность headless-цикла на стадии «Разработка»: подтвердилась ли, что реализовано вместо/в дополнение:** гипотеза AO-005 подтвердилась и реализована буквально — стадия `developing` запускается одним `run` (`api/src/core/worker_loop.py`), выполняющим headless-эквивалент `openspec-apply-change` в worktree задачи; оркестратор не вмешивается во внутреннюю Router/execution-unit декомпозицию — это делегируется `AGENTS.md` целевого репозитория внутри самой CLI-сессии агента. Альтернатива (серия явных run'ов с шагами от оркестратора) не понадобилась.
- **Архитектурный блокер AO-005 (CLI отсутствует в контейнерах, нет доступа к подписке) — как решён:** вариант **(а)** — Claude Code CLI установлен только в образ `worker` (не `api`), авторизация через выделенный `claude setup-token`/`CLAUDE_CODE_OAUTH_TOKEN`, никогда не `~/.claude` оператора. Следствие: `worker` стал реальным потребителем очереди `runs` (`SELECT ... FOR UPDATE SKIP LOCKED`), `api` больше не спавнит `ClaudeAdapter` инлайново.
- **Путь worktree (факт AO-003):** выбран отдельный именованный volume `ORCHESTRATOR_WORKTREES_PATH:/worktrees`, смонтированный в оба контейнера (`api`, `worker`) — не подпуть внутри `/target_repo`, чтобы worktree физически не засорял реальный чекаут пользователя.
- **Итоговый объём реализации:** 24 execution units (12 backend `BE-1..BE-12`, 3 frontend `FE-1..FE-3`, 2 manual QA `QA-1`/`QA-2` с повтором, 5 Quality Gate lanes `QG-BE/QG-FE/QG-CONTRACTS/QG-LIVE/QG-SYNTH`), из них 6 (`BE-8`, `BE-9`, `BE-10`, `BE-11`, `BE-12`, повтор `QA-2`) добавлены Router'ом по ходу фазы поверх исходного плана Planner'а — по реальным находкам `SMOKE-1`/`QA-1`/`QG-BE`/`QG-FE` (не пробелы планирования, а нормальный rework-цикл Quality Gate). Итоговый вердикт `QG-SYNTH`: **APPROVED**. Полный отчёт: `docs/reports/phase3-full-pipeline-quality-gate.md`. OpenSpec change заархивирован: `orchestrator/openspec/changes/archive/2026-09-14-phase3-full-pipeline/`, delta specs синхронизированы в `orchestrator/openspec/specs/{git-worktree-lifecycle,pipeline-stage-runs,run-live-stream,artifact-discovery}`.
- **Существенные находки, которые важны для следующих фаз (см. также AO-007/AO-008 ниже):**
  1. `git config --global --add safe.directory` обязателен в обоих Dockerfile (`api`, `worker`) для bind-mounted `/target_repo`/`/worktrees` — без этого `git worktree add` падает `dubious ownership` на каждом свежем контейнере.
  2. Ошибка спавна CLI-процесса (например несуществующий `worktree_path`/битый `CLAUDE_ADAPTER_CLI_COMMAND`) должна явно помечать `run.status=failed` — широкий `except Exception: logger.exception(...)` без этого оставляет `run` зависшим в `running` навечно без пути к retry. Это прямо relevant для Phase 4 (AO-007) — общая инфраструктура определения провала run'а уже есть, quota-специфичный статус `blocked_quota` должен использовать тот же путь маркировки, не изобретать новый.
  3. `docker compose cp` (для быстрой синхронизации кода в контейнер при итеративной разработке/тестировании) **не** заменяет `docker compose restart`/`build`: живой `uvicorn`-процесс не переимпортирует изменённые модули сам. Как минимум дважды за эту фазу это привело к ложным диагнозам «баг не пофикшен» при том, что код на диске был корректен.
  4. `TARGET_REPO_PATH` для любого live/smoke-прогона обязан быть одноразовым тестовым git-репозиторием, не продовым чекаутом `eqSiteCMS` — нарушение этого правила в паре live-verification unit'ов оставило 9 stale веток/worktree `agent/*` в реальном репозитории (устранены Router'ом вручную после подтверждения пользователем).
