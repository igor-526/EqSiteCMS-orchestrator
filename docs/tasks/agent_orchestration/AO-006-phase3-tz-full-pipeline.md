# AO-006 — ТЗ Phase 3: Полный пайплайн стадий 2–5

Часть плана [`AO-002-implementation_plan.md`](AO-002-implementation_plan.md), «Phase 3» из §9.

Предыдущая фаза: [`AO-005`](AO-005-phase2-tz-headless-spike.md) — **обязательно прочитать итоговый отчёт спайка** (раздел в конце файла AO-005) перед началом: он фиксирует реальный формат вызова/событий и подтверждает или опровергает гипотезу автономного Router-цикла. Если гипотеза не подтвердилась, реализовывать нужно предложенную в отчёте альтернативу, а не схему из этого ТЗ буквально.
Следующая фаза: [`AO-007`](AO-007-phase4-tz-quota-handling.md).

## Контекст

Это самая крупная фаза — здесь пайплайн становится реально сквозным: от клика «Взять в работу» до отчёта Quality Gate, с живым чатом по каждому агенту. Строится на:
- `tasks`/`stages` из Phase 1,
- `runs`/`run_events` и рабочем `ClaudeAdapter` из Phase 2,
- реальной команде/формате событий, зафиксированных в отчёте Phase 2.

## 1. Git worktree lifecycle (AO-002 §8)

- При клике «Взять в работу» на задаче (Phase 1 UI-стаб оживает):
  - создать ветку `agent/<task_id>` от актуального `main` целевого репозитория;
  - создать git worktree в отдельной директории вне основного пути пользователя (например `~/.orchestrator/worktrees/<task_id>` — конкретный путь вынести в конфиг);
  - записать `branch_name`/`worktree_path` на уровне задачи (или на каждый `run` — см. схему `runs` в AO-002 §4, там уже есть оба поля).
- Повторное «взятие в работу» той же задачи переиспользует существующий worktree, если он ещё не удалён, а не создаёт новый.
- Удаление worktree — не автоматизируется в этой фазе (см. Phase 5, там же финальная судьба ветки).

## 2. Стадия 2 — OpenSpec

- «Взять в работу» → создаёт `run` (agent=claude, stage=openspec) → worker стартует `ClaudeAdapter` по контракту из Phase 2 в свежесозданном worktree.
- Комментарий, введённый пользователем при взятии в работу (поле из AO-001 «Взятие в работу»), передаётся как часть промпта/входных данных этого run'а.
- Живой чат (см. §5) отображает события run'а по мере поступления.
- По завершении run'а (успешно дошёл до approval-гейта) — `stage.status = waiting_decision`.

## 3. Стадия 3 — Гейт принятия решения

UI по точной спецификации AO-001 («Подтверждение OpenSpec»):
- Одно текстовое поле — либо ответ на открытые вопросы агента, либо комментарий на apply.
- Кнопка **«Доработать артефакты»** — disabled, если поле пустое. При клике: создаёт новый `run` той же стадии `openspec` с текстом поля как follow-up входом (используя механизм резюмирования сессии, если он подтверждён в отчёте Phase 2, либо новый run с явной передачей контекста предыдущего — в зависимости от вывода спайка). `stage.status` возвращается в `active` на время этого run'а, затем снова `waiting_decision`.
- Кнопка **«Приступить»** — всегда enabled (комментарий на этом шаге опционален). При клике: пишет строку в `decisions` (`action=proceed`, `comment_text` = содержимое поля, может быть пустым), `stage(openspec).status = done`, создаёт `run` для стадии `developing`.

## 4. Стадия 4 — Разработка

- Один `run` (agent=claude, stage=developing), запускающий headless-эквивалент `openspec-apply-change` в том же worktree. Именно на этом шаге сам агент внутри своей сессии следует `AGENTS.md` целевого репозитория (Router/execution units/делегирование подагентам) — оркестратор в это не вмешивается, только показывает единый поток событий этого run'а.
- Если отчёт Phase 2 показал, что автономный прогон не проходит весь цикл за один headless-вызов (гипотеза не подтвердилась) — здесь реализуется альтернатива из отчёта (например, серия run'ов с явными шагами); в этом случае количество и логика `run`'ов на этой стадии должны быть переопределены по факту, а не по буквальному «один run».

## 5. Живой чат / работа над задачей (AO-002 §6)

- Полноценный стрим вместо polling из спайка: worker публикует событие в Redis-канал `run:<run_id>` **и** пишет в `run_events`; `api` отдаёт `WS /runs/{id}/stream` (relay) + `GET /runs/{id}/events` (история/reconnect).
- Экран «Работа над задачей»: список активных `runs` под задачей — агент, стадия, статус, с учётом требования AO-001 «видеть каждого агента, их количество». Если под одной стадией параллельно несколько `runs` (см. QG ниже) — каждый в своей вкладке/карточке, не смешивать ленты.

## 6. Стадия 5 — Quality Gate

- На основе вывода Phase 2/отчёта решить: один `run` (единый headless-прогон `code-review`) или несколько параллельных `run`'ов по lane-модели (`QG-BE`/`QG-FE`/`QG-CONTRACTS`/... из `AGENTS.md`) — зафиксировать выбор в этом же файле по факту реализации (дописать ниже, в блоке «Решения по факту реализации»).
- Результат — отчёт (файл в целевом репозитории, обычно `docs/reports/**`), обнаруживаемый через diff worktree (см. §7) и попадающий в `artifacts`.
- `stage(qg).status = done` при успешном прохождении. Обработка провала QG (findings, повторные ранов) — минимально: провал возвращает стадию `developing` в `active` с новым `run`, конкретный UX (что видит пользователь) — на усмотрение исполнителя, не блокирует DoD этой фазы, если базовый цикл «QG упал → снова разработка» технически работает.

## 7. Обнаружение артефактов

- После завершения каждого `run`'а worker считает diff worktree относительно базовой ветки (`git diff --name-status <base>...HEAD` внутри worktree).
- Новые/изменённые файлы, попадающие под известные паттерны (`openspec/changes/**`, `docs/reports/**`), — вставляются как строки в `artifacts` (`task_id`, `run_id`, `path`, `kind`, `discovered_at`).
- Вкладка «Артефакты» в детальном экране задачи (Phase 1 заглушка) теперь отдаёт реальный список.

## Definition of Done

- [ ] От клика «Взять в работу» до завершения OpenSpec-стадии — реальный worktree создан, реальный run прошёл, чат отображает события живьём (через WS, не polling).
- [ ] Approval-гейт: «Доработать» действительно недоступна на пустом поле и запускает follow-up run при заполненном; «Приступить» фиксирует decision и переводит стадию.
- [ ] Стадия «Разработка» реально запускает headless-агента в том же worktree и стрим виден в чате.
- [ ] Стадия QG отдаёт реальный отчёт, найденный и показанный как artifact.
- [ ] Дашборд отражает актуальные статусы стадий по всему циклу без ручных правок в БД.
- [ ] Раздел «Решения по факту реализации» ниже заполнен (выбор между одним QG-run и lane-моделью, и как решился вопрос из §4 про автономность headless-цикла).
