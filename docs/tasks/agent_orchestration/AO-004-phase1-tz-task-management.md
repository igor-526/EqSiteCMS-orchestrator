## Репозиторий оркестратора (факт по итогам AO-003)

- Расположение: `orchestrator/` рядом с `eqSiteCMS` (`/home/igor/projects/eqSiteCMS/orchestrator/` на машине оператора) — отдельный git-репозиторий, физически вложенный в директорию eqSiteCMS, но исключённый из её git через `/orchestrator/` в `.gitignore` (по аналогии с `/services/`). Не путать с git worktree — это обычный самостоятельный репозиторий.
- Модули backend: `api/src/core` (доменная логика), `api/src/api` (HTTP-роуты, сейчас только `health.py`), `api/src/repositories` (доступ к БД) — новые сущности `tasks`/`stages` из этого ТЗ кладутся сюда же по этой же схеме.
- Стек БД: SQLAlchemy + Alembic, `DATABASE_URL` уже пробрасывается в контейнеры `api`/`worker` через `docker-compose.yml`; в `api/pyproject.toml` есть и `asyncpg` (рантайм), и `psycopg2-binary` (нужен Alembic — синхронный движок). Новую миграцию `tasks`/`stages` добавлять файлом в `api/alembic/versions/` (сейчас там пусто, только `.gitkeep`).
- `TARGET_REPO_PATH` из `.env` (host-путь к чекауту `eqSiteCMS`) смонтирован bind-volume'ом **внутрь контейнеров `api` и `worker` по фиксированному пути `/target_repo`**. Это значит: весь файловый browsing/редактирование из §2 этого ТЗ (`GET/PUT /files/...`) внутри backend-кода должен резолвить пути относительно `/target_repo`, а не относительно host-пути `TARGET_REPO_PATH` — host-путь виден только вне контейнеров.
- Порты по умолчанию: API — `8000`, frontend — `3000` (переопределяются через `.env`, см. `.env.example`).
- `make migrate` уже отработан и создаёт только служебную `alembic_version` — таблицы `tasks`/`stages` из этого ТЗ будут первой настоящей доменной миграцией репозитория.

## Контекст

Цель Phase 1 — дать рабочий UI для стадии 1 из AO-001 («Формирование задачи») и дашборд со списком задач, **полностью без вызова какого-либо агента**. Это чистая CRUD-часть: файловый браузер, md-редактор, список задач со статусами стадий. Реальный запуск агента (клик «Взять в работу» реально стартует OpenSpec-ран) появляется только в Phase 3 — здесь эта кнопка допускается как визуальный стаб.

Целевой репозиторий (`TARGET_REPO_PATH` из Phase 0) — чекаут `eqSiteCMS`. В Phase 1 файловый браузер/редактор работает **прямо с основным чекаутом** этого репозитория (не с git worktree — изоляция через worktree начинается только при реальном взятии в работу, см. AO-002 §8, реализуется в Phase 3). Считайте, что до `git add`/коммита пользователь сам отвечает за свои несохранённые правки — так же, как если бы он редактировал файл в обычном текстовом редакторе.

## 1. Модель данных

Добавить в БД оркестратора (миграция Alembic):

```
tasks
  id, task_md_path (относительный путь внутри TARGET_REPO_PATH, например docs/tasks/075_foo.md),
  title, status (enum: forming, in_pipeline, done), created_at, updated_at

stages
  id, task_id, stage_type (enum: forming, openspec, decision, developing, qg, completion, release),
  status (enum: pending, active, waiting_decision, blocked_quota, done, skipped),
  started_at, finished_at
```

При создании `task` — сразу создать все 7 строк `stages` со статусом `pending`, кроме `forming`, который получает `active` (задача формируется прямо сейчас). Это единственная автоматическая логика статусов в этой фазе — дальше статусы не меняются автоматикой, только вручную через UI-заглушки (см. §4).

`runs`, `run_events`, `artifacts`, `decisions` из AO-002 §4 — **не создавать в Phase 1**, они появятся начиная с Phase 2/3, когда возникнет реальный смысл их заполнять.

## 2. API (backend)

- `GET /files?path=docs/tasks` — листинг файлов/директорий внутри `TARGET_REPO_PATH` (ограничить только поддеревом `docs/tasks/**` — не открывать произвольный путь ФС).
- `GET /files/content?path=...` — содержимое файла (текст).
- `PUT /files/content` — сохранить содержимое md-файла по пути (создаёт файл, если не существовал).
- `GET /tasks` — список задач с текущими статусами всех 7 стадий (для дашборда).
- `POST /tasks` — зарегистрировать задачу в БД оркестратора по существующему или только что созданному `task_md_path` (парсит title из первого `# ` заголовка файла, если есть, иначе — из имени файла).
- `GET /tasks/{id}` — детали задачи + список стадий.
- Валидация путей: любой `path`, выходящий за пределы `docs/tasks/**` внутри `TARGET_REPO_PATH` (в т.ч. через `..`), — отклонять 400. Это внутренний инструмент с одним оператором, но файловый browsing по абсолютным путям ФС — риск, который не нужен даже здесь.

## 3. Frontend — экраны

### 3.1 Дашборд (главный экран)
Список всех зарегистрированных задач: título, путь к файлу, 7 значков стадий с цветовой индикацией статуса (`pending`/`active`/`done`/...). Клик по задаче → переход на детальный экран.

### 3.2 Файлы задач (отдельный раздел, по AO-001 «вынести в отдельный раздел»)
Дерево/список файлов `docs/tasks/**` целевого репозитория. Открытие файла → md-редактор (обычный textarea/CodeMirror с подсветкой markdown — конкретная реализация на усмотрение исполнителя) с кнопкой «Сохранить» → `PUT /files/content`. Кнопка «Создать задачу из этого файла» на файлах, которые ещё не зарегистрированы в `tasks` (нет соответствующей строки в БД) → `POST /tasks`.

### 3.3 Детальный экран задачи
- Вкладка «Стадии» — 7 стадий с текущим статусом (пока статичным, кроме `forming`).
- Вкладка «Артефакты» — в Phase 1 может быть пустой заглушкой («появится в Phase 3») либо (опционально, не обязательно) уже сейчас показывать read-only список уже существующих в целевом репозитории файлов по конвенции (`openspec/changes/**`, `docs/reports/**`), если по названию их можно связать с задачей — не обязательный пункт, не блокирует DoD.
- Кнопка «Взять в работу» + поле комментария — присутствует визуально, при клике **ничего не вызывает на backend** кроме отметки (опционально, на усмотрение исполнителя) `task.status = in_pipeline` для наглядности на дашборде. Реальный запуск агента — Phase 3.

## Definition of Done

- [ ] Миграция создаёт таблицы `tasks`/`stages`.
- [ ] Файловый браузер показывает реальное содержимое `docs/tasks/**` целевого репозитория (проверить на живом чекауте `eqSiteCMS`).
- [ ] Md-редактор создаёт новый файл и сохраняет правки в существующий — изменения видны в `git status` целевого репозитория снаружи оркестратора.
- [ ] Новый/существующий файл можно зарегистрировать как задачу, после чего она появляется на дашборде с 7 стадиями.
- [ ] Path traversal за пределы `docs/tasks/**` целевого репозитория отклоняется backend'ом (проверить `../`-путь вручную).
- [ ] Кнопка «Взять в работу» присутствует и не вызывает ошибок, но не запускает никакого агента.

## Явно вне скоупа Phase 1

- Любой вызов CLI-агента (Phase 2+).
- Git worktree / ветки (Phase 3).
- Живой чат/стрим (Phase 2+).
- Автоматическое изменение статусов стадий кроме `forming` при создании задачи.
