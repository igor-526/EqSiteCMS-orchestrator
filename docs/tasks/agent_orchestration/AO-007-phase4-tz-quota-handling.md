Часть плана [`AO-002-implementation_plan.md`](AO-002-implementation_plan.md), «Phase 4» из §9. Закрывает явное требование AO-001 (стр. 26): «в любой момент выполнения задачи у агента могут закончиться лимиты».

Предыдущая фаза: [`AO-006`](AO-006-phase3-tz-full-pipeline.md) — полный пайплайн должен уже реально работать на живых run'ах, чтобы здесь были доступны настоящие наблюдения (или их отсутствие) сигнатуры лимита.
Следующая фаза: [`AO-008`](AO-008-phase5-tz-completion-stub.md).

Репозиторий оркестратора (по итогам AO-003): `orchestrator/` рядом с `eqSiteCMS`, отдельный git-репозиторий; backend-код — `api/src/{core,api,repositories}`.

## Факт по итогам AO-004 (Phase 1)

- `StageStatus` (`api/src/core/models.py`) уже содержит `blocked_quota` с Phase 1 — значение стадии для §2 схему менять не нужно.
- `TaskStatus` (тот же файл) содержит только `forming`/`in_pipeline`/`done` — отдельного статуса задачи под «лимит исчерпан» нет. Если для дашборда (визуальный индикатор блокировки, §2) нужен признак на уровне задачи, а не только стадии — решить: выводить его на фронтенде из статусов дочерних `stages` (без изменения схемы) или добавлять новое значение в `TaskStatus` отдельной миграцией; по умолчанию предпочтителен первый вариант (без изменения enum'а), т.к. `blocked_quota` — состояние конкретной стадии/run'а, а не задачи в целом.
- Ни один эндпоинт Phase 1 не пишет в `stage.status` — переходы `blocked_quota`/восстановление реализует эта фаза поверх `StageRepository`, следуя тому же паттерну репозиториев, что и `TaskRepository` (`api/src/repositories/tasks.py`).

## Факт по итогам AO-005 (Phase 2, спайк)

Полный отчёт — в конце `AO-005-phase2-tz-headless-spike.md`.

- **Сигнатура исчерпания лимита не наблюдалась** за 4 прогона спайка (`rate_limit_info.status` был `"allowed"` во всех, утилизация 5-часового окна не превышала ~0.41). §1 ниже остаётся в силе буквально: собирать сигнатуру нужно из реальных наблюдений Phase 3 (AO-006) или намеренно спровоцированных прогонов здесь, не изобретать заранее.
- **Важная находка, меняющая приоритет источника сигнала для `is_quota_exceeded`**: каждое событие `rate_limit_event` (наблюдалось в каждом прогоне, не только при исчерпании) несёт структурированное поле `rate_limit_info.unifiedWindows.{five_hour,seven_day}.utilization` (0.0–1.0) и `resetsAt` (unix timestamp), плюс `rate_limit_info.status` (наблюдалось только `"allowed"`, но по названию поля предполагает как минимум ещё одно значение для исчерпанного состояния). Это значит: детектор не обязан парсить текст ошибки/exit code как единственный источник — `rate_limit_info.status != "allowed"` (или высокая `utilization`, если `status` не меняется, а лимит всё равно отражается через 429/иной сигнал на API-уровне) может быть более надёжным и структурированным сигналом, чем текстовая сигнатура. Зафиксировать оба канала при первом реальном наблюдении: и точный текст/exit code (как требует DoD), и то, что показывает `rate_limit_info.status` в этот момент.
- **Резюмирование по `cli_session_id` подтверждено экспериментально** (см. AO-005 §3 отчёта: `--resume <uuid>` продолжает ту же сессию, корректно ссылается на контекст предыдущего рана, без повторного чтения файлов). Практическое следствие для §3 ниже: ветка «если механизм не подтверждён — честный fallback» **не применяется** — резюмирование реализуется как основной путь, а не запасной. Follow-up/resume-run — это новый `runs`-ряд с **тем же** `cli_session_id`, что и прерванный run (не новый UUID), запущенный с флагом `--resume` вместо `--session-id`.
- `--permission-mode bypassPermissions` (обязательный флаг, зафиксирован в AO-005/AO-006) не имеет отношения к квоте напрямую, но означает, что при `blocked_quota` процесс остановился не из-за отказа в разрешениях — детектор не должен путать `system/permission_denied` события с исчерпанием лимита; это разные типы событий в `run_events` (`permission_denied` vs `rate_limit`/сигнатура в `result`).

## Факт по итогам AO-006 (Phase 3)

Полный отчёт — `docs/reports/phase3-full-pipeline-quality-gate.md`; OpenSpec change (реализация, все решения и test matrix) — `orchestrator/openspec/changes/archive/2026-09-14-phase3-full-pipeline/`.

- **Сигнатура исчерпания лимита всё ещё не наблюдалась.** Все live/smoke/QA execution units этой фазы (`SMOKE-1`, `QG-LIVE`, `QA-1`, `QA-2`) намеренно использовали committed-стаб `worker/fixtures/fake_claude_cli.py` вместо реального `claude` CLI, чтобы не тратить лимит подписки — стаб детерминированно эмитит `system/init → assistant/text → result(success)` и не воспроизводит `rate_limit`-события. §1 этого файла остаётся в силе буквально: сигнатуру нужно собирать из реального прогона (в этой фазе или намеренно спровоцированного здесь), не изобретать заранее.
- **Отдельное наблюдение не по адаптеру, а по самой оркестрирующей CLI-сессии Router'а** (не то же самое, что сигнатура для `ClaudeAdapter.is_quota_exceeded`, но полезный референс формата): в ходе выполнения AO-006 несколько subagent-сессий самого Router'а (не `orchestrator`'а) упали с HTTP 429 и телом вида `You've hit your session limit · resets <время конкретного часового пояса>`. Это ограничение уровня CLI-подписки/harness, а не `stream-json`-событие `rate_limit` от спавненного процесса — не путать источники при проектировании детектора `ClaudeAdapter.is_quota_exceeded`, который должен парсить именно вывод спавненного `worker`-процесса.
- **`RunStatus`/`StageStatus.blocked_quota` подтверждены как уже существующие значения enum'ов** (`api/src/core/models.py`, Phase 1) — Phase 3 их не использовала и не трогала. Заодно подтверждён полный набор значений `RunStatus`: `queued`, `running`, `waiting_input`, `blocked_quota`, `succeeded`, `failed`, `stopped` — `waiting_input`/`stopped` тоже не задействованы Phase 3, доступны для §3 этого файла (fallback-ветка «резюмирование недоступно» может использовать готовое значение `stopped`, а не изобретать своё).
- **Общий паттерн маркировки провала run'а уже реализован и должен переиспользоваться, не изобретаться заново**: `api/src/core/worker_loop.py::run_one()` (Phase 3, `BE-4`/`BE-8`) явно ловит ошибку спавна процесса (`asyncio.create_subprocess_exec` бросает `FileNotFoundError` и подобные) и помечает `run.status=RunStatus.failed` + `finished_at` — это тот же код-путь, куда должен встроиться детектор `blocked_quota` из §2: не новый механизм маркировки, а новая ветка внутри существующей обработки результата run'а (успех/провал/квота — три исхода одного и того же места, а не три разных).
- **Важный незакрытый пробел, прямо релевантный §3 этого файла:** Phase 3 закрыла только сценарий «процесс не смог даже стартовать» (`run.status=failed` при ошибке спавна). Сценарий §3 («`run.status=running`, но реального процесса больше нет — воркер перезапустился и потерял handle») **не реализован и не проверялся** в Phase 3 — это открытый вопрос именно этой фазы (AO-007), не решённый как побочный эффект Phase 3.
- **Резюмирование по `cli_session_id` подтверждено не только на уровне спайка (AO-005), но и в реальном production-коде с прошедшими тестами**: `POST /stages/{id}/decisions` с `action=rework` (`api/src/api/stages.py`, `BE-5`) создаёт follow-up `run` с тем же `cli_session_id`, что и предыдущий `run` той же стадии; `ClaudeAdapter.build_command()` сам решает использовать `--resume <cli_session_id>` вместо `--session-id`, если находит «sibling»-run с тем же `cli_session_id` (через `RunRepository`). Это готовый, покрытый тестами путь — §3 этого файла может переиспользовать именно этот механизм (создать новый `run` той же стадии с тем же `cli_session_id`), а не проектировать resume с нуля.
- **`git config --global --add safe.directory /target_repo`/`/worktrees` обязателен build-time в любом образе, который шеллит git внутри worktree** (`api/Dockerfile`, `worker/Dockerfile`, Phase 3 `BE-8`) — учесть, если Phase 4 добавляет новые контейнеры/образы, трогающие worktree.
- **Операционное правило, стоившее Phase 3 нескольких ложных диагнозов:** `docker compose cp` (быстрая синхронизация кода в уже запущенный контейнер для итеративного тестирования) не заменяет `docker compose restart`/`build` — живой `uvicorn`/`worker`-процесс не переимпортирует изменённые модули сам. При любой live-проверке в Phase 4 — сначала `restart`/`build`, потом делать выводы о поведении.

## Контекст

Два разных сценария восстановления, которые нельзя путать в UI и в коде:
1. **Лимит подписки исчерпан** — агент явно сообщает об этом (или это следует из кода завершения). Это не ошибка реализации, run не должен помечаться `failed`.
2. **Процесс/сессия прервались не из-за лимита** (воркер перезапустился, контейнер упал, сеть оборвалась) — здесь нужно резюмирование по `cli_session_id`, если оно подтверждено в отчёте Phase 2 (AO-005).

## 1. Детектор исчерпания лимита

- Собрать все реальные наблюдения сигнатуры лимита из отчётов Phase 2 (AO-005) и Phase 3 (AO-006), если они случались. Если ни разу не наблюдалось за время предыдущих фаз — **не изобретать сигнатуру заранее**: намеренно спровоцировать или дождаться реального исчерпания лимита в тестовом прогоне и зафиксировать точный текст/exit code перед тем, как писать детектор.
- `ClaudeAdapter.is_quota_exceeded(event) -> bool` — проверка по зафиксированным сигнатурам (регэксп/сравнение кода завершения).

## 2. Переходы статусов

- При срабатывании детектора во время активного `run`: `run.status = blocked_quota`, `stage.status = blocked_quota`. Никакого автоматического повторного запуска.
- Дашборд: строка задачи получает визуальный индикатор блокировки (иконка/цвет, отличный от обычного `active`).
- Детальный экран задачи: баннер «Лимит агента исчерпан на стадии `<X>`» с двумя действиями:
  - **«Повторить»** — создаёт новый `run` для той же стадии тем же агентом (`claude`). Успешное завершение нового run'а снимает `blocked_quota` со стадии.
  - **«Сменить агента»** — элемент присутствует в UI, но **disabled** в MVP (единственный рабочий адаптер — Claude); включится, когда появится второй рабочий `AgentAdapter` (Phase 6, вне текущего плана).

## 3. Resume прерванной (не quota-blocked) сессии

- Если Phase 2 подтвердил механизм резюмирования по `cli_session_id`: при обнаружении, что `run.status = running`, но реального процесса больше нет (воркер перезапустился и потерял handle), worker при старте должен попытаться переподключиться к сессии по сохранённому `cli_session_id`, а не тихо считать run зависшим навечно.
- Если механизм не подтверждён (или подтверждён частично) — реализовать честный fallback: такой run помечается `stopped` с понятной причиной в `run_events` (`type=system`, текст вида «сессия прервана, резюмирование недоступно»), и пользователю доступна кнопка «Повторить» (создаёт новый run с нуля) — то есть тот же UI-путь, что и для `blocked_quota`, но с другой причиной в баннере.

## Definition of Done

- [ ] Детектор основан на реально наблюдённой сигнатуре (задокументировано, откуда она взята — ссылка на отчёт Phase 2 или новое наблюдение, сделанное в рамках этой фазы).
- [ ] Искусственно спровоцированное (или дождавшееся реального лимита) срабатывание переводит run/stage в `blocked_quota`, не в `failed`, и показывает баннер.
- [ ] «Повторить» создаёт новый run и корректно снимает блокировку после успеха.
- [ ] «Сменить агента» присутствует визуально и явно disabled с понятной причиной (tooltip/подпись), а не просто скрыта — так закладывается контракт под Phase 6.
- [ ] Поведение при потере процесса воркером (перезапуск контейнера во время активного run) проверено вручную и приводит к одному из двух согласованных исходов (успешный resume или честный `stopped` + «Повторить»), а не к вечно висящему `running`.

## Явно вне скоупа Phase 4

- Автоматический периодический опрос «сбросился ли лимит» — сознательно не делаем (AO-002 §7).
- Реальная реализация второго адаптера (Codex/MiMo) — только то, что UI-контракт под него не ломается.
