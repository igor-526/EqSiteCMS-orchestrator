# Клиент Яндекс.Метрика

## Контекст

В сервисе `ya-metrica-service` начата реализация клиента Яндекс.Метрика

Его предназначение будет в том, чтобы брать сырые данные с сервиса Яндекс.Метрика, после чего сохранять их

Идея в том, что SEO сервис будет инициировать задания на парсинг, а сервис метрики парсить, агрегировать и сохранять

## Задачи

### Базовый клиент

Рядом с основным клиентом yandex-metrica реализован парсер

Они используют идентичные методы `make_request`

Давай вынесем базовый API клиент и будем наследоваться от класса с реализованным клиентом

### Хранение данных

Необходимо продумать структуру БД, в которой можно будет хранить полученные метрики

Мы реализовываем структуру хранения под 2 следующих запроса:

**Набор 1:**

```
metrics = ["ym:s:visits", "ym:s:users", "ym:s:pageviews", "ym:s:bounceRate", "ym:s:pageDepth", "ym:s:avgVisitDurationSeconds"]
dimensions = ["ym:s:date", "ym:s:startURL"]
```

**Набор 2:**

```
metrics = ["ym:s:visits", "ym:s:users", "ym:s:pageviews", "ym:s:bounceRate", "ym:s:pageDepth", "ym:s:avgVisitDurationSeconds"]
dimensions = ["ym:s:date", "ym:s:lastSearchPhrase"]
```

Посмотри вывод API и форматы данных

Я хочу хранить чистые неагрегированные статистики, чтобы потом мы могли их агрегировать самостоятельно по дням, диапазонам дат, месяцам и тд

Тут важно понимать, что может быть запрос отсортировать по одному из показателей

При хранении нужно продумать ещё и фильтрацию, чтобы мы могли отфильтровать все показатели в рамках одной конюшни без передачи в SQL запросе всех запросов или страниц, так как запросов или страниц может быть несколько тысяч. В рамках сервиса должны резолвиться все запросы и страницы одной конюшни

При сохранении записи может быть конфликт. Например, мы сегодня в течение дня парсим метрики за сегодня, а уже завтра спарсим за сегодня. Эти метрики могут быть разными. В таком случае запись необходимо обновлять

То есть уникальна должна быть следующая комбинация:

*   конюшня
*   дата
*   метрика

### Запуск и управление

Давай пока что сделаем запуск с помощью сервисного API эндпоинта, который будет принимать UUID конюшни и выполнять парсинг этих двух групп

Сервис будет делать запрос в `yandex-service` для получения кредов по конюшне

Сейчас там есть эндпоинт, который возвращает расшифрованный токен. Давай доработаем и сделаем так чтобы токен возвращался зашифрованным, а расшифровывал его уже сам сервис по аналогии с получением кредов по счётчикам

### Сохранение

Сохранение должно происходить в ELT стиле. То есть после парсинга метрики или одной страницы метрики необходимо сразу зафиксировать результат в БД и не держать результаты в оперативной памяти

### Работа с пагинацией

Посмотри в документации про работу с пагинацией. За один заход парсим максимум записей, заносим в БД и при наличии второй страницы идём за ней. И так пока не закончится

### Работа с датами

Я хочу, чтобы можно было явно передавать диапазон дат для парсинга

Но и чтобы можно было не передавать. В таком случае даты должны резолвиться по последней записанной статистике включая этот день. Но с лимитом 2 года

### Архитектура

SEO сервис даёт в NATS сообщение о необходимости парсинга данных по такой-то конюшне

Yandex Metrica сервис декомпозирует эти задачи по следующим признакам:

*   диапазон дат не менее 1 дня и не более 5 дней на задание
*   отдельно страницы отдельно запросы

То есть задача на парсинг метрики за 20 дней должна превратиться в такие задачи

1.  Парсинг страниц 1-5 день
2.  Парсинг запросов 1-5 день
3.  Парсинг страниц 6-10 день
4.  Парсинг запросов 6-10 день
5.  Парсинг страниц 11-15 день
6.  Парсинг запросов 11-15 день
7.  Парсинг страниц 16-20 день
8.  Парсинг запросов 16-20 день

Для каждой задачи должен быть доступен статус. В очереди, в работе, успешно, не успешно

Нужно продумать ретраи там, где это разумно (если креды неактуальны, то автоматический ретрай не нужен)

Всё должен резолвить сервисный слой. Воркер и клиент должен получать уже готовые для парсинга задачи (счётчик, расшифрованный токен, и тд). 

### Логирование

Логируй начало работы, её завершение и количество insert'ов. А также все ошибки

### Страницы и запросы

Для получения страниц и запросов необходимо использовать специальный эндпоинт в SEO сервисе. В сервисе метрики SEO-сущности не храним

### Ограничения, асинхронность и многопоточность

Яндекс метрика не разрешает асинхронные запросы с одного аккаунта. Учти это при планировании очереди

По количеству одновременно выполняемых задач давай пока 1. Но необходимо заранее учесть, что воркер может быть заскейлен и что потом может появиться необходимость поддержки асинхрона в рамках разных аккаунтов

### Итог

В этой задаче необходимо реализовать только хранение данных и их парсинг. Предложи хорошую архитектуру для этого. API, управление, агрегация, кэширование и прочее не в этом scope. Кроме эндпоинта на запуск парсинга
