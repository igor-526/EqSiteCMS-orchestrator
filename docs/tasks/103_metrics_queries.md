# Вывод текущих метрик по поисковым запросам

## Контекст

В задаче 101 реализован парсинг данных Яндекс.Метрики, а в задаче 102 — вывод и SQL-агрегация метрик для вкладки SEO «Страницы».

Теперь нужно аналогично расширить вкладку SEO «Запросы». Использовать окончательные решения задачи 102, а не её первоначальный пример DTO: повторно использовать универсальный `metrics_table`, SEO period resolver, реестр показателей, форматирование и frontend renderer. Второй движок таблиц метрик не нужен.

Это постановка будущей задачи, не план реализации. Вкладка «Страницы», её поведение и нормализация в объём изменений не входят.

## Задачи

### Вёрстка

1.  Вкладки находятся слева, справа на вкладке «Запросы» — только пагинация и кнопка «Сбросить» по общему образцу CMS. Кнопку «Нормализация» для запросов не добавлять.
2.  Под вкладками расположить отдельную строку обязательных фильтров метрик. Вкладки, действия, фильтры и заголовок таблицы остаются видимыми при прокрутке; вертикально прокручивается только тело таблицы.
3.  Сохранить возможность горизонтальной прокрутки динамических колонок; основные колонки закрепить слева. Целевой экран CMS — desktop от 1366×768.

### Источник данных и гранулярность

Источником является `**metrica_search_query_stats**`, а не `metrica_page_stats` (`services/ya-metrica-service/src/models/metrica_stats.py`). Идентификатор сущности — `search_query_id`; уникальная запись статистики определяется сочетанием `equestrian_id + stat_date + search_query_id`.

Строка списка SEO — сущность `search_queries` с полями `id`, `query`, `created_at`. Сопоставление статистики выполняется по `search_query_id` и `id` строки в пределах одной конюшни. Запросы нормализованы и уникальны внутри конюшни по `query_hash`.

В таблице статистики запросов нет `page_id` или `counter_id`. Не придумывать гранулярность «запрос × страница × счётчик», не соединять статистику со страницами или задачами парсинга так, чтобы размножать строки. `parse_task_id` — служебная ссылка на происхождение данных, а не дополнительное измерение отчёта. Один запрос должен оставаться одной строкой списка независимо от числа дней статистики.

### Фильтры

Все три фильтра обязательны, имеют значения по умолчанию и не очищаются:

**Режим** (`mode`): по дням / по неделям / по месяцам / по годам (`day|week|month|year`). По умолчанию — по дням.

**Показатель** (`metric`): по умолчанию — «Визиты» (`visits`). Доступны фактические показатели модели статистики запросов:

| Ключ | Название |
| --- | --- |
| `visits` | Визиты |
| `users` | Посетители |
| `pageviews` | Просмотры |
| `bounces` | Отказы |
| `visit_duration_seconds` | Суммарное время визитов |
| `bounce_rate` | Доля отказов |
| `page_depth` | Глубина просмотра |
| `avg_visit_duration_seconds` | Время на сайте |

Технические поля модели не являются показателями. Набор совпадает со страницами по текущей модели, а не вследствие слепого копирования вкладки.

**Диапазон дат** (`date_from`, `date_to`): обе даты передаются вместе; если обе отсутствуют, SEO вычисляет период по умолчанию. Одна дата без второй, обратный диапазон или некорректный режим/показатель должны давать `400`.

| Режим | Максимум календарных единиц | По умолчанию, включая текущую единицу |
| --- | --- | --- |
| По дням | 31 день | 7 дней |
| По неделям | 16 недель | 4 недели |
| По месяцам | 12 месяцев | 6 месяцев |
| По годам | 5 лет | 2 года |

Период разрешает **seo-service** существующим механизмом `seo-metrics-period`. Использовать собственную настройку `SEO_UTC_OFFSET_HOURS`, согласованную по значению с `YA_METRICA_UTC_OFFSET_HOURS`, без чтения чужой переменной окружения. «Сегодня» определяется сервером в этом часовом поясе.

*   Без дат конец периода — сегодня; начало — начало первой из нужного числа календарных единиц. Например, четыре недели — текущая и три предыдущие, два года — текущий и предыдущий.
*   Для недель, месяцев и лет выбранный диапазон расширяется до границ соответствующих календарных единиц. Неделя — понедельник–воскресенье, а не скользящие семь дней.
*   Лимит отсчитывается от выровненного начала: при превышении сокращается **вторая дата**, первая остаётся на начале своей единицы. Затем конец ограничивается сегодняшним днём. Например, для дней `01.09–26.10` получается `01.09–01.10`, а не последние 31 день.
*   Будущие даты в колонки не попадают. Все единицы целиком, кроме текущей недели/месяца/года, заканчивающейся сегодня. Будущее начало сервер приводит к сегодняшнему дню согласно существующему resolver.
*   Frontend запрещает выбор будущего, ориентируясь на `period.today` ответа. Первое открытие и смена режима запрашивают серверные значения по умолчанию, без самостоятельного расчёта периодов.
*   Возвращённые `period.date_from/date_to` всегда применяются к фильтру без лишнего повторного запроса. Уведомление показывается **только при** `**clamped=true**` — сокращении по лимиту. Выравнивание и ограничение сегодняшним днём (`adjusted`) не вызывают уведомления.

### Таблица и форматирование

Сохранить основные колонки «Запрос» (`query`) и «Создано». В «Создано» показывать только дату `DD.MM.YYYY`, без времени; сортировать по полному timestamp создания.

Справа добавить динамические колонки выбранного показателя для всех единиц разрешённого периода в хронологическом порядке. Использовать существующий контракт `metrics_table` с `row_key="id"`: метаданные показателя, итоговый период и сортировка, массив колонок и ячейки по UUID строки текущей страницы. Отсутствие статистики показывать как `—`, а реальный ноль — как ноль.

Заголовки и значения формирует SEO существующими formatters, frontend выводит готовые `text` и подсказки:

*   дни — без года (`25 окт`); недели — диапазоном; месяцы — краткими названиями;
*   у недель и месяцев добавлять двузначный год, если он отличается от текущего; для недели через границу лет — у обеих дат. Колонка года — четырёхзначный год;
*   заголовок описывает календарную единицу целиком, а подсказка — фактические даты с полным годом, в том числе для текущей неполной единицы;
*   целые — с группировкой тысяч; десятичные — округление half-up до двух знаков, запятая и без незначащих нулей; проценты — со знаком `%`; длительности — сокращёнными единицами `ч`, `мин`, `с` по существующим правилам.

### Поиск, сортировка и сброс

*   Сохранить поиск по тексту запроса в колонке «Запрос».
*   Поддержать прямую и обратную сортировку по запросу, дате создания и каждой динамической колонке. Одновременно активна только одна пользовательская сортировка, выполняемая в SQL **до пагинации**, а не в пределах уже полученной страницы. Технический tie-breaker по UUID допустим для стабильности.
*   Сортировка метрик — по числовому агрегату выбранной колонки, не по форматированному тексту. Запросы без данных идут последними в обоих направлениях; индикатор отражает фактически применённую сервером сортировку. Если колонка больше не входит в период, снять её сортировку по правилам таблицы страниц.
*   Не добавлять date filters в «Создано» и динамические колонки: диапазон задаётся только общей панелью метрик.
*   «Сбросить» снимает только применённый поиск по запросу, его черновик и сортировку, возвращает на первую страницу. Режим, показатель, даты и `pageSize`/`limit` сохраняются. Сброс выполняет один запрос.

### Агрегация и архитектура

Цепочка остаётся прежней: frontend → основной backend → seo-service → ya-metrica-service.

Расширить существующие списочные endpoint'ы `GET /api/seo/search-queries` основного backend и `GET /api/search-queries` SEO параметрами метрик и атрибутом ответа `metrics_table`, сохранив поиск, пагинацию и список сущностей. Не создавать отдельную frontend-таблицу или параллельный контракт для запросов.

*   **SEO** вычисляет период и готовые buckets, выполняет поиск, сортировку и пагинацию сущностей в SQL своей БД; преобразует готовые значения Метрики в универсальный DTO. Агрегацию статистики и сортировку строк в памяти не выполнять.
*   **Метрика** получает готовые границы buckets и UUID запросов, агрегирует данные и при необходимости ранжирует запросы для сортировки. Не вычисляет периоды по умолчанию, лимиты, календарные границы или текстовые фильтры SEO. Конкретные новые peer endpoint'ы определить при проектировании будущего изменения, не выдавать их за уже существующие.
*   **Основной backend** проверяет доступ и входные параметры, берёт конюшню из сессии, валидирует и проксирует DTO. Периоды и форматирование не дублирует.
*   **Frontend** повторно использует универсальный renderer, применяет серверный период, управляет фильтрами, одной сортировкой и пагинацией; устаревшие ответы не должны перезаписывать новое состояние.

Вся фильтрация, агрегация и ранжирование выполняются в SQL ответственных сервисов, без отдельных запросов на каждую строку или колонку. Использовать правила парсинга/слияния и сохранённые базовые счётчики:

*   `visits`, `users`, `pageviews`, `bounces`, `visit_duration_seconds` — суммы за bucket;
*   `bounce_rate = SUM(bounces) * 100 / SUM(visits)`;
*   `page_depth = SUM(pageviews) / SUM(visits)`;
*   `avg_visit_duration_seconds = SUM(visit_duration_seconds) / SUM(visits)`;
*   при нулевой сумме визитов производные показатели равны нулю.

Не усреднять готовые дневные проценты или средние. `users` здесь — сумма сохранённых дневных счётчиков по действующим правилам, не вычисление уникальных посетителей за весь период. Повторно не суммировать уже слитые данные через задачи парсинга, страницы или счётчики; текущую логику парсинга и нормализации не менять.

### Доступ

Это приватная административная аналитика, а не Public Read для сайтов-потребителей. Сохранить существующее исключение защищённого GET: доступ основного backend — строго `ADMIN`, без автоматического допуска иных повышенных ролей.

| method | path | access class | roles | expected without auth | expected with auth |
| --- | --- | --- | --- | --- | --- |
| GET | backend `/api/seo/search-queries` | Protected GET exception | только `ADMIN` | `401` | `200` для ADMIN; `403` без ADMIN; невалидные параметры `400`; сбой downstream `502` |
| GET | SEO `/api/search-queries` | Internal Trusted Network Read exception | доверенный backend | `200` с валидным `X-Equestrian-Id`; отсутствующий/невалидный selector — `401` | то же; пользовательские credentials не заменяют selector; невалидные параметры `400`; сбой Метрики `502` |

Внутренний selector — несекретная подсказка идентичности, не авторизация. Peer API не публиковать наружу. При будущем проектировании дополнить матрицу конкретными новыми/изменёнными endpoint'ами Метрики, их статусами и причинами исключений по существующей peer-политике задачи 102.

### Проверки результата

*   Проверить все показатели по фактической модели запросов, формулы на неравных дневных объёмах, нулевые значения и отсутствие данных; сопоставление UUID не должно давать дублей или утечки другой конюшни.
*   Проверить четыре режима, defaults, лимиты, вторую дату при clamp, календарное выравнивание, границы недель/месяцев/лет и timezone около полуночи; будущие даты недоступны, возвращённые даты применяются, уведомление появляется только при clamp.
*   Проверить глобальную SQL-сортировку в обоих направлениях до пагинации, стабильный порядок, поиск и сброс без изменения фильтров метрик и размера страницы.
*   При тестировании включить SQL-логирование в SEO и Метрике и подтвердить отсутствие N+1: число SQL-запросов и peer-вызовов не растёт пропорционально числу строк или колонок. Проверить разные размеры страницы и максимальное число колонок; одно лишь визуально быстрое открытие не является доказательством.
*   Проверить anonymous/authenticated поведение по матрице, отказ без ADMIN до downstream, tenant isolation и невозможность выбрать чужую конюшню через клиентский ввод. Отдельно проверить внутренний API без пользовательской авторизации с валидным и невалидным selector; для будущих peer endpoint'ов — оба режима согласно их матрице.
*   Проверить sticky-панель, прокрутку только тела, форматирование, пустой результат и ошибки downstream на desktop 1366×768. Убедиться, что вкладка «Страницы» и её кнопка/процесс нормализации работают без изменений.
