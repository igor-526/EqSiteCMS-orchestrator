## Контекст

В `docs/tasks` находятся 23 верхнеуровневых Markdown-файла без числового идентификатора. Связанные планы и отчёты размещены во вложенных каталогах `docs/plans/**` и `docs/reports/**`, причём часть отчётов имеет служебные префиксы и суффиксы (`FEATURE-`, `BUGFIX-`, `-review`, `-final-review`).

Подтверждённое правило порядка: текущий filesystem `mtime`, при равенстве — имя файла. Нумеруются только `docs/tasks/*.md`, начиная с `001`; связанные Markdown-артефакты получают номер своей задачи с сохранением каталога и смыслового суффикса. API, БД и сервисный код не затрагиваются.

По снимку на момент планирования `documents_numeration.md` занимает позицию 22, поэтому этот план сразу создан как `docs/plans/022_documents_numeration.md`. Перед реализацией порядок необходимо повторно сверить с зафиксированным manifest: чтение или редактирование файлов может изменить `mtime`.

## Цель

Получить однозначную и проверяемую нумерацию задач `001`–`023`, синхронно префиксовать только достоверно связанные планы и отчёты, обновить ссылки и не потерять файлы, историю Git или пользовательские изменения.

Критерии приёмки:

- каждый верхнеуровневый `docs/tasks/*.md` имеет уникальный трёхзначный префикс согласно manifest ниже;
- связанные Markdown-файлы в `docs/plans/**` и `docs/reports/**` имеют тот же префикс, каталоги и суффиксы сохранены;
- `TEMPLATE.md`, `.gitkeep`, изображения, JSON и скрипты не переименованы;
- отсутствуют коллизии путей, битые относительные ссылки и незапланированные изменения содержимого;
- повторный dry-run не предлагает новых переименований.

### Построение manifest артефактов

Перед любым переименованием сформировать отдельный dry-run список `source -> target` для Markdown-файлов в `docs/plans/**` и `docs/reports/**`.

Нормализация для сопоставления выполняется без изменения реального имени:

1. привести basename к нижнему регистру и заменить `-` на `_`;
2. убрать уже существующий начальный шаблон `^[0-9]{3}_` для идемпотентной проверки;
3. для отчётов разрешить убрать служебный начальный маркер `feature_` или `bugfix_` и служебные хвосты `review`, `backend_review`, `final_review`, `repeat_review`, `smoke_final_<date>`, `smoke_retest_<date>`;
4. сопоставлять с нормализованным task stem по самому длинному полному совпадению на границе токенов, чтобы `horses_management` не перехватывал `horse_pedigree_management`;
5. автоматически включать только ровно одно соответствие; ноль или несколько кандидатов выводить в unresolved и не переименовывать без ручной фиксации manifest;
6. `TEMPLATE.md` всегда исключать. План `022_documents_numeration.md` уже имеет итоговый префикс и должен остаться без повторного префикса.

Для каталогов с несколькими файлами одной работы (например, `docs/plans/parsing_from_old_site/step*.md`) номер добавляется каждому подтверждённому артефакту, а каталог сохраняется. Не-Markdown-файлы не входят в scope.

### Безопасность переименования

- До изменений сохранить `git status --short` и полный manifest; не затрагивать существующие несвязанные изменения (`.gitignore`, `.codex/`, `openspec/` и другие пользовательские файлы).
- Проверить уникальность всех target paths и отсутствие уже существующего иного файла по каждому target.
- Для tracked-файлов использовать `git mv`; для untracked-файлов — обычное безопасное перемещение только после проверки target.
- Выполнять переименования по manifest, а не через неограниченный glob. При потенциальном цикле/коллизии сначала использовать уникальное временное имя внутри того же каталога.
- После переименований искать старые basenames по всему репозиторию и точечно обновлять Markdown-ссылки и документированные пути. Содержимое, не являющееся ссылкой/путём, не переписывать механически.
- Не менять timestamps для пересортировки и не вычислять номера заново после первого перемещения.

1. Сравнить фактический список `docs/tasks/*.md` с 23 строками manifest; новые/пропавшие файлы являются блокером до обновления плана.

4. Проверить, что каждый префиксованный artifact с установленной связью использует номер соответствующей задачи.

6. Через `rg` проверить остаточные ссылки на старые пути; обновлённые относительные ссылки должны разрешаться.
7. Сравнить до/после количество файлов отдельно для tasks, plans и reports; удаления или появления лишних файлов быть не должно.
8. Проверить `git diff --summary`, `git diff --name-status`, `git status --short`; ожидаются только renames и точечные правки ссылок.
