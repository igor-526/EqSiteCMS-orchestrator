## Краткий контекст

Не самые сложные задачи стали выходить за пятичасовой rolling-бюджет Codex. Диагноз из задачи 062 подтвердился при чтении инструкций: декомпозиция была оптимизирована под **ownership correctness** («кто имеет право менять файлы») и никак — под **execution boundedness** («сколько работы один запуск агента выполняет до возврата управления Router»).

Три разных уровня схлопнулись в один:

```text
acceptance scenario → OpenSpec checkbox → agent execution unit
```

Источник схлопывания — правило Planner «минимум 30 unit + 30 smoke, каждый пункт атомарный checklist item». Оно превращало любую backend-фичу в секцию `### Backend` на 90+ пунктов, которую Router воспринимал как один deliverable, а `agents/backend.md` предписывал агенту «продолжай до завершённого deliverable, не жди дополнительных инструкций». Отсюда пятичасовые марафоны в `callback-requests-management-055` (`1.1–1.95`) и `vk-service-initialization-059`.

Изменения затрагивают только `AGENTS.md` и `agents/**`, как и требовала задача. Карта агентов и специализации не менялись — они не были причиной проблемы.

## Что сделано

### 1. Введена сущность Execution Unit (`AGENTS.md`)

Зафиксирована несворачиваемая иерархия:

```text
OpenSpec Change → Deliverable (ownership) → Execution Unit (одна агентная сессия) → Agent invocation
```

- **Deliverable** отвечает на вопрос «кто владеет файлами и specs».
- **Execution Unit** отвечает на вопрос «сколько работы один invocation выполняет до возврата управления».
- Один deliverable может содержать несколько units одного профиля (`BE-1`, `BE-2`, `BE-3`) — ownership не меняется, меняется lifetime execution context.
- Явно записано: `services/vk-service/**` — хороший ownership boundary и плохой execution boundary.

### 2. Бюджет execution unit как circuit breaker

Один unit — это один сервис **или** один архитектурный slice, примерно **8–12 существенных действий**, **одна группа verification**, один независимо сдаваемый результат. Нарушен хотя бы один критерий — unit делится **до** делегирования. Числа зафиксированы как эвристика-предохранитель, а не как метрика.

Канонический DAG вынесен в `AGENTS.md`:

```text
BE-1 → BE-2 → BE-3 ─┬→ BE-4 ──────┐
                    └→ INTEG-1 ───┴→ SMOKE-1
```

### 3. Router делегирует unit, а не секцию

- Шаги пайплайна 5–8 переписаны: сначала deliverables, затем execution units, делегирование — **ровно один unit одному запуску агента**.
- В список «Запрещено» добавлено: делегировать секцию `### Backend` / deliverable / ownership-зону целиком; начинать следующий unit без handoff предыдущего; отклонять предложенный агентом split.
- Шаблон передачи контекста расширен полями `🧩 Execution Unit`, `🎯 Границы unit`, `✅ Verification`, `🔁 Handoff предыдущего unit`.
- Чеклист Router дополнен проверками бюджета, handoff и точечных `contextFiles`.

### 4. Обязательный checkpoint и handoff между units

Введён фиксированный короткий формат handoff (`Unit / Статус / Изменённые файлы / Verification / Отмеченные tasks / Решения / Остаток`). Агент завершает unit, запускает verification **своего** unit'а, отмечает только реально выполненные checkbox и **останавливается**. Router не начинает следующий unit, не прочитав handoff.

Формат продублирован в протоколах завершения работы всех четырёх исполнителей.

### 5. Circuit breaker самого агента

Если после чтения задания unit не помещается в бюджет, агент выполняет безопасную атомарную часть, отмечает только реально сделанное и возвращает статус `partial` с предложением split вида `BE-3 → BE-3a + BE-3b`. Router **обязан** принять split; ответ «доделай всё в этой сессии» запрещён.

### 6. Снято противоречие с анти-зависанием

Правило «продолжай и не жди дополнительных инструкций» было прямой причиной марафонов: оно требовало доводить до конца весь deliverable. Теперь оно действует **в границах execution unit**, и добавлено явное: остановка с корректным handoff после завершённого unit — это не зависание, а ожидаемое поведение.

### 7. Правило `30 unit + 30 smoke` удалено (`agents/planner.md`)

Квота убрана из всех девяти мест (вопросы анализа, раздел 2.1, структура артефактов, формат чеклиста, пример, список запретов). Вместо неё — **risk-based test matrix**:

- матрица живёт в `design.md` (`## Test matrix`) с ID `UT-*` / `SM-*`, а не в `tasks.md`;
- восемь обязательных осей покрытия (happy path, валидация и границы, ошибки внешних зависимостей, транзакционность/идемпотентность/конкурентность, access matrix, реальная PostgreSQL, контракт ответа, регрессии);
- неприменимая ось помечается с причиной, ось без риска не заполняется ради количества;
- матрица больше ~25 сценариев на фичу = сигнал, что это несколько фич.

### 8. Acceptance tests отделены от tasks

Формально зафиксированы три разных уровня:

| Сущность | Где живёт | Гранулярность |
|---|---|---|
| Acceptance scenario | delta spec | одно поведение |
| Test matrix row | `design.md` → `## Test matrix` | один тест-сценарий с ID |
| Checklist task | `tasks.md` | одно действие агента (группа сценариев) |

`tasks.md` теперь структурируется по execution units с заголовком `## <N>. <UnitID> — <название> (профиль: ...)` и финальным пунктом `<UnitID>.V` (verification + handoff). Тестовые пункты группируются по диапазонам ID. Пример из планировщика: **18 сценариев = 18 строк матрицы и 3 checklist-пункта**, а не 18 пунктов.

Прежний пример чеклиста на 90 строк заменён компактным. Frontend-минимумы (3/4/5 тестов) сохранены, но переопределены как минимумы **строк матрицы**, а не checklist-пунктов.

### 9. Quality Gate раздроблен на lanes

Gate остаётся логически одним (один отчёт, один вердикт), физически — пять lanes, каждый отдельный execution unit:

| Lane | Что проверяет | Применим |
|---|---|---|
| `QG-BE` | Clean Architecture, unit/integration тесты, миграции, access policy на коде, Celery/Redis | есть diff в Python-сервисах |
| `QG-FE` | `npm test`, lint, `tsc --noEmit`, build, UI-тесты, manual QA | есть diff в `services/frontend` / `site-*` |
| `QG-CONTRACTS` | AsyncAPI, access matrix, ownership, Makefile-контракт, соответствие specs/tasks | всегда |
| `QG-LIVE` | SMOKE через `.claude/skills/api-smoke-test`, реальные PostgreSQL/NATS, timings | есть runtime API diff |
| `QG-SYNTH` | сведение findings, единый вердикт, один отчёт | всегда |

`QG-BE` / `QG-FE` / `QG-CONTRACTS` независимы, `QG-LIVE` после них, `QG-SYNTH` последним. Отчёт создаёт и вердикт ставит только `QG-SYNTH`. Findings возвращаются как новые units (`BE-FIX-1`), после исправлений повторяются только затронутые lanes. Неприменимый lane помечается `неприменимо` с обоснованием, молчаливый пропуск запрещён.

Проверка тестов переведена с подсчёта количества на трассировку: каждый ID матрицы → реальный тест или выполненный smoke-сценарий; расхождение матрицы и покрытия — blocking finding.

### 10. Экономия контекста

Задача отдельно отмечала: если речь про общий rolling-бюджет, дробление без экономии контекста не поможет — параллельность может съесть бюджет быстрее.

- В `AGENTS.md` добавлен раздел «Экономия контекста»: context pack на unit, запрет формулировок «прочитай весь change», «прочитай все specs», «изучи, что уже сделано»; handoff вместо повторного восстановления состояния по diff; явное предупреждение, что параллельность экономит wall-clock, но не токены.
- В `agents/backend.md` (971 строка) и `agents/frontend.md` (667 строк) добавлен `## 0. Протокол чтения`: таблица «ядро читается всегда» + таблица «что делает unit → какие секции дочитать». Требование «прочитай этот файл полностью» снято — оно означало десятки килобайт одинакового контекста в каждом invocation.
- Planner обязан выдавать точечный `contextFiles` set **на каждый unit**, из которого Router собирает context pack.

## Ожидаемый эффект на бюджет

| Источник перерасхода | До | После |
|---|---|---|
| Один invocation на весь backend-deliverable | `1.1–1.95` в одной сессии | 4–6 units по ~8–12 действий с checkpoint между ними |
| Искусственные тестовые tasks | ≥60 верхнеуровневых пунктов на фичу | 2–4 сгруппированных пункта + матрица в `design.md` |
| Повторное чтение контекста | «прочитай файл агента полностью» × каждый invocation | ядро + релевантные секции по протоколу чтения |
| Восстановление состояния | «изучи, что уже сделано» по diff | handoff предыдущего unit |
| Монолитный Quality Gate | один проход по всему change | 4 параллелизуемых lane + короткий synthesis |

## Замечания и риски

1. **Открытое противоречие в main specs.** `openspec/specs/notification-settings-api/spec.md:98,103` по-прежнему требует «не менее 30 unit scenarios» и «не менее 30 smoke scenarios». Это утверждённый main spec, он вне scope задачи 062 (`AGENTS.md` + `agents/`) и меняется только через OpenSpec workflow. До правки он перекрывает новое risk-based правило для этой capability. Рекомендация: отдельный change, заменяющий квоту на требование покрытия применимых осей test matrix.
2. **Legacy `docs/plans/**`** содержит старую квоту (`003`, `004`, `007`, `009`, `010`, `014`). Файлы read-only и на новые change'и не влияют — правка не требуется.
3. **`orchestrator/AGENTS.md`** фиксирует для `plan_parser` плоские секции `### Backend` / `### Frontend` / `### Quality Gate`. Противоречия нет: парсер читает `docs/plans/<TICKET>.md` (legacy), а плоские секции явно сохранены в rework-чеклистах `docs/reports/`. В OpenSpec `tasks.md` структура — по execution units.
4. **Числа бюджета (8–12 действий, ~25 сценариев) — эвристики.** Их стоит откалибровать по фактическому расходу на первых двух-трёх change'ах после внедрения.
5. **Проверка на практике не проводилась.** Изменены только инструкции; реальный выигрыш по бюджету подтвердится на следующем change, прошедшем полный цикл Planner → units → QG lanes.
