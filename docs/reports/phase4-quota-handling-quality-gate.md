## Краткое summary скоупа фазы

Phase 4 закрывает два пробела, явно зафиксированных Phase 3 как незакрытые: (1) исчерпание лимита подписки Claude неотличимо от настоящего сбоя (`run.status=failed`), (2) `_RUNNING_PROCESSES` — process-local словарь, рестарт контейнера `worker` теряет хендл и `run` остаётся `running` навсегда.

- **Детектор квоты** (`BE-1`) — реальный headless-прогон `claude` CLI (не стаб) подтвердил структурный канал `rate_limit_info.status` (наблюдался только `"allowed"`); текстовая/exit-code сигнатура исчерпания не наблюдалась (см. ниже, DoD-1).
- **Третья ветка исхода** (`BE-1`/`BE-2`) — `ClaudeAdapter.stream()` и `apply_stage_transition()` получили безусловную ветку `blocked_quota`, не ломающую существующую диспетчеризацию по `stage_type`.
- **Retry endpoint** (`BE-3`) — единый `POST /stages/{id}/retry`, ветвление по `blocked_quota` (resume того же `cli_session_id`) vs `stopped` (свежий `cli_session_id`) vs `409`.
- **Авто-восстановление при рестарте `worker`** (`BE-2`) — `recover_orphaned_runs()` до входа в цикл опроса очереди, переиспользует существующий resume-механизм (`--resume`/`has_sibling_with_session`), с честным `stopped`-fallback при провале спавна.
- **UI** (`FE-1`) — баннер блокировки/обрыва сессии, кнопки «Повторить» (активна) и «Сменить агента» (disabled с тултипом).

Вне скоупа фазы (Non-Goals, не пересматривались): автоматический периодический опрос сброса лимита, реальный второй адаптер (Codex/MiMo), изменение `TaskStatus`, новая схема БД.

## Открытые вопросы / технический долг, передаваемые в следующую фазу (AO-008)

Не блокируют текущий вердикт:

1. **Текстовая/exit-code сигнатура исчерпания лимита не наблюдалась** (DoD-1, частично). Детектор сегодня работает исключительно на структурном канале `rate_limit_info.status != "allowed"`. Если реальный формат exit-code/текста разойдётся с предположением (`status` — единственный аналог соседнего `overageStatus`), потребуется расширение `is_quota_exceeded` при первом органическом наблюдении исчерпания в реальной эксплуатации. Явно зафиксировано в `design.md` → Решение 1 и Open Questions, не выдумано.
2. **Гипотетический риск многорепличного `worker`** (`design.md` → Risks): `recover_orphaned_runs()` сегодня безопасен только потому, что `worker` единственный (Phase 3 MVP). Если появится вторая реплика, потребуется `SELECT ... FOR UPDATE SKIP LOCKED` в `recover_orphaned_runs()`, аналогично `claim_next_queued()` — не в скоупе этой фазы.
3. **Ротация/мониторинг `CLAUDE_CODE_OAUTH_TOKEN`** — техдолг, зафиксированный ещё Phase 3 design.md Open Questions, по-прежнему не в скоупе.
4. **Стаб-CLI `FAKE_CLAUDE_QUOTA_MODE` может разойтись с реальным форматом квоты** — задокументировано как дополнение к, не замена, ручной проверке на реальном CLI (тот же класс риска, что Решение 5 Phase 3 для happy path).
